    Part 1 — 배포 전략¶

    한 줄 요약¶

    설치는 플랫폼별 표준 조합으로, 갱신은 채널과 하한선 두 다이얼로, 확산은 링으로 통제합니다. 개인이 curl | bash 한 줄로 끝내던 일이 500대 앞에서는 배포·서명·버전·롤백을 모두 설계해야 하는 문제로 바뀝니다.

    왜 알아야 하나¶

    1주차와 2주차는 전부 내 노트북 안의 이야기였습니다. 설치는 스크립트 한 줄이면 됐고, 버전은 자동 갱신이 알아서 맞춰줬고, 설정은 내 홈 디렉토리에 있었고, 뭔가 잘못되면 지우고 다시 깔면 됐습니다. 이 전제가 전부 무너지는 순간이 있습니다. "우리 회사 개발자 500명에게 이걸 깔아주세요" 라는 요청을 받는 순간입니다.

    그때부터 질문의 성격이 달라집니다. 어떤 채널로 깔아야 MDM으로 밀 수 있는가, 다운로드 URL이 방화벽에서 열려 있는가, 서명 검증은 누가 하는가, 어제까지 잘 되던 게 자동 갱신 후 깨졌을 때 어떻게 되돌리는가, 보안팀이 "이 바이너리 어디서 받았는지 감사 로그 주세요"라고 하면 무엇을 낼 수 있는가. 전부 도구의 기능이 아니라 배포 시스템의 설계에 관한 질문입니다.

    이 파트는 그 관점 전환을 다룹니다. 개발자용 문서에서는 한 줄이던 설치가 관리자용 문서에서는 하나의 챕터가 되는 이유이기도 합니다.

    ▲ 교재 슬라이드 3 — Admin이 마주하는 도전

    현장 메모

    인프라 쪽에서 일해봤다면 이 목록이 낯익을 겁니다. 사내에 새 개발 도구를 들일 때 매번 반복되는 그 체크리스트 — 배포 채널, 서명, 버전 핀, 롤백 절차, 감사 로그 — 와 정확히 같습니다. Claude Code라서 특별한 게 아니라, 조직에 도입되는 모든 실행 파일이 통과해야 하는 관문이 여기서도 똑같이 적용될 뿐입니다. 오히려 이 챕터가 쉽게 느껴진다면 그건 이미 아는 문제를 새 대상에 적용하는 것이기 때문입니다.

    1. 설치 채널 4계열 — 무엇으로 500대를 깔 것인가¶

    설치 방법이 여러 개인 이유는 취향의 문제가 아니라 설치를 실행하는 주체와 환경이 다르기 때문입니다. 관리자가 MDM으로 밀어넣는 상황, 서버 플릿에 Ansible로 뿌리는 상황, 개발자가 자기 맥북에 알아서 까는 상황, CI 러너 이미지에 굽는 상황은 요구사항이 전부 다릅니다. "무엇이 최선인가"가 아니라 "이 대상에는 무엇이 맞는가" 로 접근해야 합니다.

    각 갈래를 조직 관점에서 풀어보면 이렇습니다.

    • Native 설치 스크립트: claude.ai/install.sh가 단일 바이너리를 내려받아 배치합니다. Node 런타임 의존이 없고 자동 갱신이 내장돼 있어, 교재가 표준 권장으로 꼽는 경로입니다. MDM에서는 이 스크립트를 감싸 배포 스크립트로 만들면 됩니다.

    • OS 패키지 저장소: apt, dnf, apk 공식 저장소를 등록하는 방식입니다. GPG 서명 검증이 패키지 매니저 차원에서 강제되고, 설치 이력이 시스템 로그에 남습니다. 리눅스 서버 플릿에 적합합니다.

    • 패키지 매니저: macOS의 Homebrew cask, Windows의 WinGet입니다. 개발자가 이미 익숙한 명령으로 스스로 설치하는 셀프서비스 경로이고, 사내 표준을 강제하기보다 편의를 제공하는 성격입니다.

    • 컨테이너: 표준 이미지나 devcontainer에 미리 구워둡니다. CI 러너와 통제된 개발 환경용이고, 뒤에서 따로 다룹니다.

    여기에 하나가 더 붙습니다. 교재는 npm 설치를 레거시로 분류하지만, 공식 문서 기준으로는 정정이 필요합니다. npm 패키지도 네이티브 설치와 동일한 네이티브 바이너리를 설치하고, 설치된 claude 실행 파일 자체는 Node를 호출하지 않습니다. Node 런타임이 필요한 건 설치 시점(npm install 실행)뿐이고, 현재 공식 문서는 npm을 "레거시"나 "신규 배포 비권장"으로 분류하지 않습니다. 기존 Node 파이프라인에 자연스럽게 얹을 수 있다는 것이 오히려 이 경로의 장점입니다 — 다만 설치 시점의 Node 버전 요건(22.15 이상)은 챙겨야 합니다.

    ▲ 교재 슬라이드 4 — 설치 채널 4계열 / 조직 관점

    현장 메모

    1주차 실습에서 제 머신은 npm 설치인데 자동 업데이트가 정상 동작하고 있었습니다. "Native만 자동 갱신된다"고 단정했다가 제 실습 로그에 반증당한 사례입니다. 채널별 특성을 외울 때 "이 채널은 X가 안 된다"는 부정형 주장은 특히 조심해야 합니다 — 실제로는 되는데 권장되지 않을 뿐인 경우가 섞여 있습니다. 조직 표준을 문서로 쓸 때는 "안 된다"와 "지원하지 않는다"와 "권장하지 않는다"를 구분해서 적어두는 편이 나중에 문의를 줄입니다.

    2. Linux 플릿 — GPG 지문 대조가 신뢰의 출발점¶

    리눅스 서버에 저장소를 등록하는 절차 자체는 정형화돼 있습니다. 키를 받고, 저장소를 추가하고, 설치합니다. 중요한 건 그 사이에 끼어 있는 한 줄의 검증입니다.

    # fleet provisioning (apt)
sudo install -d -m 0755 /etc/apt/keyrings
sudo curl -fsSL https://downloads.claude.ai/keys/claude-code.asc \
    -o /etc/apt/keyrings/claude-code.asc

gpg --show-keys /etc/apt/keyrings/claude-code.asc
# 지문 대조: 31DD DE24 DDFA B679 F42D 7BD2 BAA9 29FF 1A7E CACE

echo "deb [signed-by=/etc/apt/keyrings/claude-code.asc] \
    https://downloads.claude.ai/claude-code/apt/stable stable main" \
    | sudo tee /etc/apt/sources.list.d/claude-code.list
sudo apt update && sudo apt install claude-code

    gpg --show-keys로 지문을 뽑아 공표된 값과 눈으로 맞춰보는 단계는 생략해도 설치가 됩니다. 그래서 자주 생략됩니다. 하지만 이 단계를 빼면 "방금 받은 키가 진짜 Anthropic의 키인가"를 아무도 확인하지 않은 채 그 키로 서명된 모든 패키지를 신뢰하게 됩니다. 키 배포 경로가 한 번 오염되면 이후의 모든 서명 검증이 통과하면서도 의미를 잃습니다. 신뢰 사슬의 뿌리가 여기라서, 이 한 줄이 절차의 핵심입니다.

    저장소 경로에 stable이 들어가 있는 것도 놓치면 안 되는 부분입니다. 제품 기본값은 latest이지만, 플릿에는 stable을 조직이 명시적으로 설정해서 씁니다. 이 선택이 6절의 버전 통제와 이어집니다. dnf, apk도 키 배치 위치와 저장소 정의 파일 형식만 다를 뿐 같은 패턴이며, 실무에서는 이 절차 전체를 Ansible 롤로 코드화해 두고 신규 노드 프로비저닝에 태웁니다.

    현장 메모

    지문 대조를 Ansible로 코드화할 때 흔한 실수가 있습니다. 지문을 태스크 안에 하드코딩해두고 assert로 검증하게 만들어 놓으면, 키가 정상적으로 롤오버됐을 때 전 플릿의 프로비저닝이 한꺼번에 실패합니다. 지문 상수를 별도 변수 파일로 빼고 그 파일의 변경을 리뷰 대상으로 두는 구성이 안전합니다. 검증을 없애는 게 아니라, 검증 기준값을 바꾸는 행위 자체를 사람이 승인하게 만드는 겁니다.

    3. 사내 미러 — 다운로드 경로를 조직 안으로¶

    외부 다운로드가 아예 막힌 망, 수백 대가 동시에 갱신될 때 회선을 걱정해야 하는 조직, "이 바이너리를 언제 누가 받았는지 대라"는 감사 요구가 있는 조직. 이 세 상황은 각각 다르게 들리지만 해법은 하나로 수렴합니다. 공식 저장소를 사내 아티팩트 서버로 미러링하는 것입니다.

    미러링 대상은 apt·rpm 저장소와 native 설치 자산이고, 필요하면 npm 패키지도 포함합니다. 방식은 Artifactory나 Nexus의 remote repository(프록시 저장소) 로 상류를 캐시하는 구성입니다. 미러 서버가 직접 패키지를 보관하는 게 아니라, 클라이언트 요청이 들어오면 상류에서 받아와 전달하면서 사본을 남기는 형태입니다. 클라이언트 쪽에서 할 일은 sources.list와 설치 스크립트 URL을 사내 주소로 치환하는 것뿐이라, 설치 절차 자체는 그대로 유지됩니다.

    여기서 절대 타협하면 안 되는 원칙이 서명 유지입니다. 미러를 거치더라도 GPG 검증은 그대로 살아 있어야 하고, 그러려면 미러가 패키지뿐 아니라 서명 파일도 함께 제공해야 합니다. 미러 구성을 편하게 하려고 서명 검증을 끄는 순간([trusted=yes] 같은 옵션), 폐쇄망을 만든다면서 오히려 무결성 검증을 스스로 제거한 꼴이 됩니다.

    미러를 두면 부수적으로 따라오는 것이 감사 로그입니다. 누가 언제 어떤 버전을 받아갔는지가 아티팩트 서버의 액세스 로그에 남습니다. 감사 대응 때문에 미러를 도입하는 조직도 실제로 있습니다.

    ▲ 교재 슬라이드 6 — 사내 미러 운영

    현장 메모

    Artifactory나 Nexus를 이미 운영하고 있다면 remote repo 하나 더 파는 건 30분 작업입니다. 문제는 뒷정리입니다. remote repo는 상류에서 받아온 걸 계속 쌓기 때문에 리텐션 정책을 안 걸어두면 몇 달 뒤 스토리지 알람으로 돌아옵니다. 그리고 미러를 도입한 조직에서 반드시 한 번은 겪는 일이 있습니다 — 개발자가 로컬에서 npm config 를 직접 바꿔 미러를 우회하고, 그 사람만 다른 버전을 쓰다가 재현 안 되는 이슈를 만듭니다. 미러는 띄우는 것보다 강제하는 것이 어렵습니다. MDM으로 클라이언트 설정을 일괄 배포하고, 방화벽에서 외부 레지스트리를 실제로 막아야 미러가 의미를 갖습니다.

    현장 메모

    그리고 미러가 "한 번 통과하면 전부 캐시된다"는 전제는 패키지 구조에 따라 성립하지 않을 수 있습니다. 아래 직접 해보기에서 실제로 확인한 함정입니다. 에어갭을 계획하고 있다면 미러를 띄운 것으로 끝내지 말고, 상류를 실제로 끊어놓고 설치가 되는지까지 검증해야 합니다.

    4. Windows 대량 배포 — WinGet과 레지스트리 정책¶

    Windows 플릿은 배포 채널과 정책 채널이 분리돼 있다는 점에서 다른 플랫폼과 결이 다릅니다.

    배포는 WinGet으로 합니다. Intune이나 SCCM의 배포 스크립트에서 무인 설치 플래그를 붙여 호출하는 형태입니다.

    # Intune, SCCM 배포 스크립트 골격
winget install Anthropic.ClaudeCode --silent `
    --accept-package-agreements

    정책은 설치와 별개로 HKLM 레지스트리(HKLM\SOFTWARE\Policies\ClaudeCode)에 배치합니다. HKCU가 아니라 HKLM인 것이 핵심입니다. 쓰기에 관리자 권한이 필요하므로 일반 사용자가 자기 정책을 임의로 바꿀 수 없고, 그래서 변조 저항이 생깁니다. 정책의 상세 항목은 Part 5에서 다루고, 여기서는 "Windows에서 정책이 사는 곳은 레지스트리"라는 위치만 잡아두면 됩니다.

    WSL을 병행하는 조직에는 하나가 더 필요합니다. Windows에 정책을 걸어놨는데 개발자가 WSL 안에서 Claude Code를 실행하면 그건 리눅스 환경이라 Windows 정책이 적용되지 않습니다. wslInheritsWindowsSettings: true로 두면 Windows 정책이 WSL까지 상속되어 정책이 일원화됩니다. Windows 개발자가 실질적으로 WSL에서 작업하는 조직이라면 이 키를 빠뜨리는 순간 정책에 구멍이 뚫립니다.

    MSI 패키징이 필요한 조직(WinGet을 쓰지 않는 배포 인프라)은 별도 문의 경로가 있습니다.

    현장 메모

    HKLM 정책은 "관리자 권한이 있어야 바꿀 수 있다"는 뜻이지 "아무도 못 바꾼다"는 뜻이 아닙니다. 개발자 장비에 로컬 관리자 권한을 주는 조직이라면 이 방어는 성실한 사용자에게만 유효합니다. 정책 우회를 실제로 막고 싶다면 로컬 관리자 권한 회수가 먼저고, 그게 현실적으로 어렵다면 차단이 아니라 탐지로 전략을 바꾸는 편이 낫습니다 — 정책 레지스트리 값의 변경을 EDR이나 구성 관리 도구에서 드리프트로 잡아내는 방식입니다. 이건 Part 6의 관측 주제와 이어집니다.

    5. 표준 컨테이너 이미지 — 재현 가능성을 굽는다¶

    CI 러너와 통제된 개발 환경에서는 컨테이너 이미지가 배포 단위가 됩니다. 이미지에는 세 가지 원칙이 들어갑니다.

    FROM ubuntu:24.04
RUN apt-get update && apt-get install -y \
    curl git ca-certificates ripgrep jq
RUN curl -fsSL https://claude.ai/install.sh | bash -s 2.1.201
ENV PATH="/root/.local/bin:${PATH}"
ENV DISABLE_AUTOUPDATER=1
COPY managed-settings.json /etc/claude-code/
WORKDIR /workspace

    • 버전 고정: install.sh에 버전을 인자로 넘겨 특정 버전을 박습니다. 같은 이미지 태그로 빌드하면 항상 같은 Claude Code 버전이 나와야 CI 결과가 재현됩니다.

    • 자동 갱신 차단: DISABLE_AUTOUPDATER=1. 이게 없으면 컨테이너가 기동될 때마다 버전이 달라질 수 있고, 그러면 방금 고정한 버전이 무의미해집니다. 이미지 불변성을 지키는 건 버전 고정과 갱신 차단이 짝을 이룰 때입니다.

    • 정책 내장: managed-settings.json을 /etc/claude-code/에 미리 복사해 굽습니다. 런타임에 정책을 주입하는 대신 이미지에 포함시키면 정책 없이 뜨는 컨테이너가 존재할 수 없게 됩니다.

    같은 이미지를 devcontainer로 배포하면 개발자들이 각자 설치한 서로 다른 버전 대신 조직 표준 개발 환경을 공유하게 됩니다. CI와 로컬이 같은 이미지를 쓰면 "제 로컬에서는 되는데요"의 상당 부분이 사라집니다.

    현장 메모

    ripgrep과 jq가 베이스 이미지에 들어 있는 걸 그냥 지나치지 마세요. Claude Code는 코드 검색에 rg를 적극적으로 쓰고, 헤드리스 실행 결과(--output-format json)를 파이프라인에서 다루려면 jq가 필요합니다. 최소 이미지(alpine, distroless 계열)로 줄이겠다고 이 둘을 빼면 에이전트가 조용히 느려지거나 파이프라인이 깨집니다. 컨테이너를 다이어트할 때는 "쓰는지 안 쓰는지"를 실행 로그로 확인하고 빼는 게 안전합니다.

    6. 버전 통제 두 다이얼 — 채널과 최소 버전¶

    500대의 버전을 어떻게 관리할 것인가는 두 개의 독립된 손잡이로 정리됩니다. 하나는 얼마나 빨리 올릴 것인가(속도), 다른 하나는 얼마나 낮은 버전까지 허용할 것인가(하한선)입니다. 이 둘을 섞어 생각하면 정책이 꼬입니다.

    flowchart LR
    M["<b>managed-settings.json</b><br/>개인이 바꿀 수 없는 정책 채널"]
    M --> D1["<b>다이얼 1 · autoUpdatesChannel</b><br/>갱신 속도<br/>stable = 플릿에 명시 설정<br/>latest = 얼리어답터 링만"]
    M --> D2["<b>다이얼 2 · requiredMinimumVersion</b><br/>기동 차단형 하한선<br/>미달 버전은 아예 시작 못 함"]
    D1 --> F["<b>완전 고정</b><br/>DISABLE_AUTOUPDATER=1<br/>+ 버전 지정 설치<br/>CI · 컨테이너 전용"]
    D2 --> F
    style M fill:#673ab7,stroke:#4527a0,stroke-width:3px,color:#fff
    style D1 fill:#e3f2fd,stroke:#1976d2,color:#000
    style D2 fill:#e3f2fd,stroke:#1976d2,color:#000
    style F fill:#fff3e0,stroke:#f57c00,color:#000

    다이얼 1 — autoUpdatesChannel. 제품 기본값은 latest이지만, 플릿에는 stable을 명시적으로 설정합니다. 새 기능을 며칠 늦게 받는 대신 검증을 거친 빌드만 받습니다. latest는 롤아웃 링 중 얼리어답터 그룹에만 열어둡니다. 전사에 latest를 걸면 문제 버전이 나왔을 때 전원이 동시에 맞습니다.

    다이얼 2 — 버전 하한선은 두 계열의 키로 나뉩니다. minimumVersion은 갱신 시점의 하한입니다 — 백그라운드 자동 갱신과 claude update가 이 값 아래로는 설치하지 못하게 막는, 즉 다운그레이드 방지용입니다. 이미 그 아래 버전이 깔려서 돌고 있는 걸 막지는 못합니다. 진짜 강제(보안 픽스가 급해서 구버전을 아예 못 쓰게 하고 싶을 때)가 필요하면 requiredMinimumVersion/requiredMaximumVersion을 씁니다 — 이 범위 밖 버전은 기동 자체를 거부합니다. minimumVersion보다 한 단계 더 강한 키입니다. 채널이 액셀이라면, minimumVersion은 뒷걸음질 방지 턱이고 requiredMinimumVersion은 바닥입니다.

    완전 고정은 별개의 선택지입니다. DISABLE_AUTOUPDATER=1에 버전 지정 설치를 더하면 되지만, 이건 백그라운드 자동 확인만 끄는 것이라 claude update나 claude install을 수동으로 치면 여전히 올라갑니다. 정말 어떤 경로로도 못 올라가게 하려면(사내 미러로만 배포하고 그 버전에 고정하고 싶을 때) DISABLE_UPDATES까지 같이 걸어야 합니다. 다만 교재는 완전 고정 조합을 CI 전용으로 한정합니다. 개발자 장비에 완전 고정을 걸면 재현성은 얻지만 보안 픽스도 같이 막히고, 결국 사람이 수동으로 올려주기 전까지 아무도 안 올라갑니다.

    세 종류의 키 모두 managed settings에 넣어 개인이 못 바꾸게 하는 것이 전제입니다. 사용자 설정에 두면 통제가 아니라 권고가 됩니다.

    7. 점진 롤아웃 — 파일럿에서 전사까지 4링¶

    500대에 한 번에 까는 건 배포가 아니라 사고입니다. 링 단위로 넓히면서 각 관문에서 채택 지표와 사고 여부를 확인하는 것이 표준 형태입니다. 각 링은 정책과 버전을 독립적으로 조정할 수 있다는 점이 중요합니다 — 링 0은 latest, 나머지는 stable 같은 구성이 가능해집니다.

    flowchart LR

    R1["<b>Ring 1 · 파일럿 팀 50명</b><br/>stable 전환<br/>managed 정책 초판 적용"]

    R3["<b>Ring 3 · 전사</b><br/>표준 온보딩<br/>지원 체계 정착"]

    각 링의 성격이 다릅니다. 링 0(챔피언 10명) 은 버전 검증보다 피드백 채널을 만드는 단계입니다. latest를 물려 문제를 먼저 맞아주는 대신, 이들이 나중에 각 팀의 전파자가 됩니다. 링 1(파일럿 50명) 에서 처음으로 managed 정책 초판이 적용됩니다. 정책이 실제 업무를 막지 않는지 확인하는 구간이라, 여기서 나온 정책 충돌을 해소하지 않고 넘어가면 링 2에서 200명분의 문의가 한꺼번에 옵니다. 링 2(부문 200명) 부터는 교육 자료와 지표 관측이 중심이 되고, 링 3(전사) 은 표준 온보딩 절차와 지원 체계를 정착시키는 단계입니다.

    현장 메모

    링 롤아웃에서 실제로 어려운 건 링을 나누는 게 아니라 관문에서 멈추는 것입니다. 일정이 정해진 도입 프로젝트에서는 링 1에서 문제가 나와도 "링 2 가면서 같이 고치죠"가 되기 쉽습니다. 그래서 관문 조건은 미리 숫자로 못 박아두는 게 좋습니다 — "치명 이슈 0건, 2주간 일 1회 이상 사용률 N% 이상" 식으로요. 그리고 링을 조직도(부서 단위)로 나누기보다 기술 스택과 환경(폐쇄망 여부, OS, WSL 사용 여부)이 섞이도록 나누는 편이 문제를 일찍 발견합니다. 링 3에 가서야 처음으로 폐쇄망 팀이 들어오면 그때 첫 에어갭 이슈를 만나게 됩니다.

    8. 오프라인·에어갭 — 설치는 되지만 추론은 다른 문제¶

    여기가 이 파트에서 가장 오해가 많은 지점입니다. "미러를 구축했으니 폐쇄망 대응 끝"이 아닙니다. 미러가 해결하는 것은 설치 자산이고, Claude Code는 설치된 뒤에 모델 엔드포인트와 통신해야 동작하는 도구이기 때문입니다.

    문제를 네 갈래로 갈라서 봐야 합니다.

    • 설치 자산: 사내 미러와 이미지 레지스트리로 완전히 내재화할 수 있습니다. 이건 앞 절들에서 다룬 대로 해결됩니다.

    • 추론 경로: 완전 격리망에서 모델 호출을 어떻게 할 것인가가 진짜 문제입니다. 현실적인 답은 Bedrock + PrivateLink 같은 클라우드 프라이빗 연결입니다. 인터넷으로 나가지 않고 VPC 엔드포인트를 통해 모델에 도달하는 경로를 만드는 것이고, 상세는 Part 2에서 다룹니다.

    • 정책 배포: 파일 기반 managed-settings.json을 형상 관리로 배포합니다. 외부 정책 서버에 붙을 필요가 없다는 뜻이라, 폐쇄망에서도 정책 채널은 문제없이 동작합니다.

    • 한계 인지: 웹 검색처럼 외부 의존이 본질인 기능은 폐쇄망에서 동작하지 않습니다. 여기서 중요한 건 "안 되니까 어쩔 수 없다"가 아니라, 도메인 정책으로 차단을 명시해 두는 것입니다. 되는 줄 알고 썼다가 조용히 실패하는 것보다 처음부터 막혀 있는 편이 낫습니다.

    ▲ 교재 슬라이드 11 — 오프라인, 에어갭 환경

    현장 메모

    에어갭 반입 절차를 실제로 돌려본 적이 있다면 알겠지만, 병목은 기술이 아니라 승인입니다. 반입 매체에 담을 아티팩트 목록을 사전에 확정해야 하는데, 미러를 통째로 뜨는 방식은 "이 안에 정확히 뭐가 들어 있는지" 설명하기가 어렵습니다. 그래서 실무에서는 반입 대상 버전을 못 박고, 그 버전에 필요한 파일 목록과 체크섬을 명세로 만들어 함께 반입합니다. 아래 실습에서 확인했듯 "미러에 캐시된 것"과 "설치에 실제로 필요한 것"이 일치하지 않을 수 있으므로, 반입 명세는 미러 storage를 신뢰해서 뽑지 말고 상류를 끊은 상태에서 설치가 성공하는지로 검증해서 만들어야 합니다.

    현장 메모

    폐쇄망에서 자동 갱신을 그대로 켜두면 매번 갱신 서버에 도달하지 못해 실패하고, 그 실패가 로그를 채우거나 기동을 지연시킵니다. 에어갭 환경은 5절의 컨테이너와 같은 원칙 — 버전 고정 + 갱신 차단 + 정책 내장 — 을 장비에도 적용하고, 갱신은 정기 반입 주기에 맞춰 사람이 밀어넣는 이벤트로 다루는 편이 깔끔합니다.

    9. 플랫폼별 표준 조합과 도입 전 산정¶

    지금까지의 내용을 OS별로 접으면 조직의 표준 조합이 나옵니다. macOS는 Native 설치 + MDM 스크립트에 plist 정책을 얹고 Jamf나 Kandji로 배포합니다. Windows는 WinGet + Intune에 HKLM 정책, WSL 병행 조직이면 상속 키를 함께 겁니다. Linux는 apt/dnf 저장소에 /etc/claude-code 정책을 두고 Ansible로 코드화합니다. 컨테이너는 표준 이미지에 정책을 내장하고 갱신을 차단해 CI와 devcontainer에 씁니다.

    플랫폼마다 정책이 사는 곳이 다르다는 게 이 표의 핵심 부담인데, 검증 방법은 하나로 통일됩니다. 전 플랫폼에서 /status를 실행하면 정책이 어느 소스에서 왔는지(remote / plist / HKLM / file) 확인할 수 있습니다. 배포 후 "정책이 실제로 먹었는가"를 확인하는 단일 창구가 있다는 뜻이라, 롤아웃 관문 체크에 그대로 쓸 수 있습니다.

    도입 전 용량 산정은 네 가지를 봅니다. 좌석 수는 전체 인원이 아니라 활성 개발자 기준으로 잡고 파일럿 실측으로 배수를 보정합니다. 토큰 추정은 1인 1일 세션 수와 세션당 평균 규모를 파일럿에서 실측해 곱하는 방식이고, 책상에서 계산한 값은 거의 맞지 않습니다. 모델 배분은 sonnet 중심에 opus를 얼마나 섞느냐가 결정적입니다 — opus 비중이 비용의 지배 변수입니다. 피크 대비는 클라우드 경로를 쓸 때 특히 중요한데, 리전별 쿼터와 스로틀 한도를 사전에 확인해두지 않으면 도입 첫날 오전에 한도를 맞습니다.

    현장 메모

    용량 산정에서 가장 자주 빗나가는 건 총량이 아니라 분포입니다. 평균 사용량으로 쿼터를 잡으면 상위 10%의 헤비 유저가 그 쿼터를 혼자 씁니다. 파일럿 실측 데이터가 있다면 평균과 함께 p95를 보고, 리전 쿼터는 피크 기준으로 신청하세요. 쿼터 증설은 신청부터 반영까지 시간이 걸리므로 롤아웃 링 2가 시작되기 전에 미리 올려두는 것이 안전합니다. 실사용 기반 보정은 Part 6의 관측 파트에서 다룹니다.

    10. 배포 전 체크리스트¶

    교재는 출발 전에 확인할 항목을 정리해 둡니다. 앞의 내용이 실제로 하나의 결정 목록으로 모이는 자리입니다.

    • 채널과 버전: stable + 하한선 버전을 결정하고 관리 설정 초안에 반영했는가.
    • 설치 경로: 플랫폼별 표준 조합을 확정하고 MDM·Ansible 스크립트로 만들었는가.
    • 미러: 필요 여부를 판단하고, 쓴다면 서명 파일까지 함께 배포되는지 확인했는가.
    • 정책 파일: managed-settings 초판과 배포 채널을 정했는가(Part 5에서 완성).
    • 롤백: 이전 버전 재설치 절차를 문서화했는가 — 버전 지정 설치를 활용합니다.

    이 중 실무에서 가장 자주 비어 있는 항목이 롤백입니다. 배포 계획은 다들 세우는데 되돌리는 절차는 사고가 난 다음에 만들기 시작합니다. 버전 지정 설치가 가능하다는 것과, 그 명령을 지금 당장 실행할 수 있게 문서로 갖고 있는 것은 다른 이야기입니다.

    직접 해보기¶

    핸즈온랩 Task 1을 따라 사내 npm 미러(Verdaccio)를 실제로 띄우고, 그 미러를 경유해 Claude Code를 설치했습니다. npmjs에 직접 나갈 수 없는 사내망을 가정한 실습입니다.

    실행 환경: macOS 26.5.1 / Claude Code v2.1.233 / 2026-08-15

    $ npm install -g verdaccio                     # 성공, 316 packages
$ verdaccio --listen 4873 &
$ npm ping --registry http://localhost:4873
npm notice PONG 14ms                            # 미러 정상 확인
$ npm install -g @anthropic-ai/claude-code --registry http://localhost:4873
added 2 packages in 2s
$ claude --version
2.1.233 (Claude Code)                           # 미러 경유 설치 성공

    전역 registry를 바꾸지 않고 --registry 플래그로 이번 설치에만 미러를 적용했습니다. 여기까지는 랩 시나리오 그대로이고 문제없이 끝났습니다.

    랩의 다음 단계는 "미러가 실제로 캐시하고 있는지" 확인하는 것입니다. /tmp/verdaccio.log를 열어보면 미러가 무엇을 했는지 그대로 드러납니다.

    info --- making request: 'GET https://registry.npmjs.org/@anthropic-ai/claude-code-darwin-arm64/-/claude-code-darwin-arm64-2.1.233.tgz'
http <-- 200, ... req: 'GET /@anthropic-ai/claude-code-darwin-arm64/-/claude-code-darwin-arm64-2.1.233.tgz', bytes: 0/87100440

    원본 npmjs에서 87MB짜리 압축 tarball(설치되면 306MB 바이너리)을 한 번 받아와 ~/.local/share/verdaccio/storage/@anthropic-ai/claude-code-darwin-arm64/에 그대로 캐시합니다. 캐시가 진짜로 동작하는지는 같은 명령으로 다시 설치해서 확인할 수 있습니다 — 이번엔 원본 npmjs로 나가는 making request 로그가 단 한 줄도 없이, storage 캐시만으로 전부 서빙됐습니다. npmjs가 끊겨도 사내 배포가 계속된다는 랩의 핵심 주장이 로그로 그대로 증명됩니다.

    함정 — '설치는 됐는데 로그에 tgz 요청이 안 보여요'

    이미 같은 버전의 claude-code가 설치돼 있는 개발 머신에서 이 실습을 반복하면, 미러를 거쳤는데도 로그에 .tgz 요청이 전혀 안 잡힐 수 있습니다. 범인은 미러가 아니라 npm 자신의 로컬 디스크 캐시(~/.npm/_cacache)입니다 — 요청한 버전을 예전에 한 번이라도 내려받은 적 있으면, npm은 레지스트리(미러든 원본이든)에 묻지도 않고 로컬 캐시에서 바로 서빙합니다. 이 상태만 보고 "미러가 캐싱을 안 한다"고 결론 내리면 틀립니다.

    재현 가능한 검증을 하려면 설치 대상과 npm 캐시를 모두 새로 격리하세요. 

    $ npm install -g @anthropic-ai/claude-code \
    --registry http://localhost:4873 \
    --prefix ./fresh-install \
    --cache ./fresh-npm-cache
    한 번도 claude-code를 설치한 적 없는 신입 직원의 새 노트북에는 이런 오염이 애초에 없으므로 이 플래그가 필요 없습니다 — 기존 개발 머신에서 미러 동작을 별도로 검증할 때만 쓰는 디버깅 도구로 기억해두면 됩니다.

    현장 메모

    "미러를 통과했다"와 "미러가 캐시하고 있다"는 다른 주장이고, 검증 방법도 다릅니다. 전자는 설치 성공 여부만 보면 되지만 후자는 접근 로그에서 원본으로 나간 요청이 있는지, 재설치 시 그 요청이 사라지는지를 직접 봐야 합니다. 이건 npm 미러에 국한된 이야기가 아닙니다 — Docker 레지스트리 미러, pip 인덱스 미러 모두 매니페스트/메타데이터 프록시와 실제 대용량 자산 캐싱이 분리 설정될 수 있는 구조라, 폐쇄망 전환 전에는 반드시 접근 로그로 "클라이언트가 최종적으로 어느 호스트에서 파일을 받는가"를 확인해야 합니다.

    흔한 오해 바로잡기¶

    • "미러를 띄웠으니 폐쇄망 대응이 끝났습니다" — 미러는 설치 자산만 해결합니다. Claude Code는 설치된 뒤 모델 엔드포인트와 통신해야 동작하므로, 추론 경로(Bedrock + PrivateLink 등)를 별도로 설계해야 합니다. 그리고 위 실습에서 봤듯 캐시가 실제로 동작하는지는 재설치 로그로 직접 확인해야 합니다 — 클라이언트 쪽 캐시(npm 자체 디스크 캐시 등)가 결과를 가릴 수 있기 때문입니다.

    • "npm으로 설치하면 자동 갱신이 안 됩니다" — 1주차 실습에서 npm 설치 환경인데 자동 갱신이 정상 동작하는 것을 직접 확인했습니다. 애초에 npm 패키지도 네이티브와 같은 바이너리를 설치하고 실행 시점엔 Node를 부르지 않으니, "npm이라서 뭔가 부족하다"는 전제 자체가 성립하지 않습니다. 교재는 npm을 레거시로 분류하지만 현재 공식 문서는 그렇게 구분하지 않습니다 — "안 된다"와 "교재가 그렇게 분류했다"를 구분해서 문서화하세요.

    • "전 장비에 버전을 고정하면 가장 안전합니다" — 완전 고정(DISABLE_AUTOUPDATER=1 + DISABLE_UPDATES + 버전 지정 설치)은 교재가 CI 전용으로 한정한 선택지입니다. 개발자 장비에 걸면 재현성을 얻는 대신 보안 픽스까지 막히고, 결국 아무도 올리지 않는 상태가 고착됩니다. 개발자 장비는 stable 채널 + minimumVersion(다운그레이드 방지) 조합이 맞고, 정말 강제로 막아야 하면 그때 가서 requiredMinimumVersion을 고려하세요.

    • "WinGet으로 배포했으니 Windows 통제가 끝났습니다" — 배포 채널(WinGet/Intune)과 정책 채널(HKLM 레지스트리)은 별개입니다. 게다가 WSL을 쓰는 조직은 wslInheritsWindowsSettings를 켜지 않으면 개발자가 실제로 작업하는 환경에 정책이 적용되지 않습니다.

    • "GPG 지문 대조는 형식적인 단계입니다" — 이 단계를 생략하면 이후의 모든 서명 검증이 통과하면서도 의미를 잃습니다. 검증이 신뢰하는 뿌리가 그 키이기 때문입니다. 자동화할 때도 없애지 말고, 기준 지문 값의 변경을 사람이 승인하는 구조로 만드세요.

    정리¶

    Chapter 3의 첫 파트는 관점 전환에서 시작합니다. 1~2주차가 "내 노트북에서 어떻게 쓰는가"였다면 여기서부터는 "500대에 어떻게 깔고 어떻게 유지하는가"입니다. 설치 채널이 네 계열(+레거시 npm)로 나뉘어 있는 것도 대상 환경과 설치 주체가 다르기 때문이고, 선택 기준은 "무엇이 최선인가"가 아니라 "이 대상에는 무엇이 맞는가"입니다.

    갱신은 두 개의 독립된 다이얼로 통제합니다. autoUpdatesChannel이 속도를, 버전 하한선이 바닥을 잡고, 둘 다 managed settings에 넣어야 통제가 됩니다. 완전 고정은 CI와 컨테이너의 선택지이지 개발자 장비의 기본값이 아닙니다. 확산은 챔피언·파일럿·부문·전사 4링으로 넓히면서 각 관문에서 지표와 사고를 확인하고, 링별로 채널과 정책을 독립 조정합니다.

    폐쇄망은 설치와 추론을 분리해서 봐야 합니다. 설치는 미러와 이미지 레지스트리로 내재화할 수 있지만 추론은 프라이빗 연결이 필요하고, 웹 검색처럼 외부 의존이 본질인 기능은 아예 차단을 명시하는 편이 낫습니다. 그리고 이번 실습이 보여준 것처럼 미러를 통과했다는 사실과 미러가 캐시하고 있다는 사실은 별개입니다 — 격리된 환경에서 재설치했을 때 원본 요청이 로그에 없는지 확인하기 전까지는 에어갭 준비가 끝났다고 말할 수 없고, 이 검증 자체도 클라이언트 쪽 캐시에 오염되지 않도록 통제해야 합니다.

    플랫폼마다 정책이 사는 위치는 다르지만 검증 창구는 /status 하나로 통일됩니다. 다음 파트에서는 설치된 도구가 실제로 모델에 도달하는 경로 — 공급자 선택과 자격증명 설계 — 를 다룹니다. 키를 500명에게 나눠주지 않고도 인증이 되게 만드는 방법입니다.
