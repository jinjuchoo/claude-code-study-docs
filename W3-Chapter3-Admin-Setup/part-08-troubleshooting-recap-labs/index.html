    Part 8 — 트러블슈팅, 정리와 실습 랩¶

    한 줄 요약¶

    관리자에게 오는 문의는 결국 인증·네트워크·성능 세 갈래로 갈리고, 진단 번들 하나(claude doctor//doctor, /status, /context, --debug-file 로그)가 1선부터 3선까지 공통어 역할을 합니다. 그리고 이번 주 실습에서는 랩 시나리오 자체보다 배포한 정책을 그대로 믿으면 안 된다는 것이 더 값진 교훈을 남겼습니다 — 시스템 전역 경로에 실제로 sudo로 정책을 배포했는데도, 그 안의 규칙 하나(Write(**))가 --debug 없이는 아무 경고 없이 조용히 무효화되고 있었습니다. "정책이 배포됐다"와 "정책이 의도대로 작동한다"는 별개라는 걸 몸으로 확인했습니다.

    1. 트러블슈팅 — 관리자에게 오는 문의의 지도¶

    관리자 문의는 크게 세 갈래로 갈립니다. 인증 문제는 의외로 원인이 단순한 편입니다. 로그인이 꼬이거나 계정이 혼선을 빚었다면 공식 1순위 처방은 /logout 후 /login 재시도이고, Enterprise 옵션이 안 보인다면 대부분 claude update 후 터미널을 재시작하지 않은 구버전 증상입니다. "조직 미배정" 메시지는 좌석에 Code 권한 자체가 포함되지 않은 경우라 어드민 콘솔에서 좌석을 갱신해야 하고, Bedrock 자격 실패는 aws sso login 세션 만료가 제일 흔하니 aws sts get-caller-identity로 신원부터 확인합니다. apiKeyHelper처럼 스크립트가 키를 공급하는 구조라면 볼트 권한이나 TTL 캐시를 의심하기 전에 그 스크립트를 단독으로 실행해 보는 게 빠릅니다.

    네트워크 문제는 Part 4에서 다룬 진단표를 그대로 요약판으로 씁니다 — 타임아웃이면 프록시 3변수와 방화벽 도메인을, TLS 체인 오류면 사내 CA 미등록을, 407 응답이면 인증 프록시를, 스트리밍이 끊기면 MTU와 검사 장비 버퍼링을, 일부 기능만 죽었다면 도메인 부분 차단을, sandbox 자체가 막았다면 allowedDomains 누락을 확인하는 순서입니다. curl -v로 계층을 분리하는 습관이 모든 네트워크 문의의 출발점이라는 점은 Part 4와 동일합니다.

    성능 문제는 "느리다"는 한마디를 네 갈래로 쪼개는 데서 시작합니다.

    세 갈래 중 어디가 원인이든 결론까지 가는 경로는 같습니다 — 진단 수집을 표준화해 두는 것입니다. 문의를 접수할 때 요청할 표준 세트는 claude doctor(셸에서 읽기 전용 환경 진단 — Claude Code가 아예 안 뜰 때 이걸로 시작), 세션이 뜬다면 세션 안에서 /doctor(같은 진단에 더해 수정 제안까지 하고, 확인 후 적용할 수 있음), claude --version, /status(공급자·모델·managed 소스 확인)와 /context(컨텍스트 점유 현황), 그리고 재현 후 claude --debug-file claude-debug.log로 뽑은 로그입니다(--verbose는 턴 출력을 상세히 보여줄 뿐 진단 로그 수집용이 아닙니다). 여기에 네트워크 문제라면 curl -v https://api.anthropic.com/ 결과까지 얹으면, 시각·사용자·저장소 경로와 함께 접수 양식이 고정됩니다.

    에스컬레이션은 3선으로 나뉩니다. 1선 헬프데스크는 진단표 매칭과 계정·좌석 확인까지, 2선 플랫폼팀은 정책·네트워크·게이트웨이 같은 조직 인프라 영역을, 3선은 AWS Support(Bedrock 쿼터·서비스 이슈)와 Anthropic 지원 채널(제품 결함·문서 괴리)로 갈립니다. 표준화된 진단 번들이 이 세 선을 잇는 공용어 역할을 합니다.

    현장 메모

    진단 번들을 접수 양식으로 강제하는 게 실제로는 가장 큰 지렛대입니다. 1선이 "느려요"라는 문의를 받고 claude doctor + /context 캡처만 첨부하게 만들어도, 2선으로 넘어오는 티켓의 상당수가 "컨텍스트 비대, 사용자가 /clear 안내로 해결"로 그 자리에서 끝납니다. 에스컬레이션 정책을 문서로만 두지 말고 헬프데스크 티켓 템플릿에 진단 번들 필드를 강제로 넣어두는 편이 실무에서 훨씬 잘 지켜졌습니다.

    2. Chapter 3 핵심 요약¶

    아홉 파트를 다시 여섯 갈래로 묶으면 이렇게 정리됩니다. 배포는 플랫폼별 표준 조합과 stable + minimumVersion 두 다이얼, 링 롤아웃으로 완성됩니다. 자격증명은 사람에게 SSO, 기계에게 볼트 헬퍼, CI에게 OIDC를 맡겨 키 배포 0을 지향하는 것이 핵심이었습니다. 게이트웨이는 그 SSO 로그인·그룹별 모델 라우팅·지출 한도·OTLP를 하나의 자체 호스팅 완제품으로 묶어주는 조각이었고, 네트워크는 프록시·CA로 들어오는 길을 열고 sandbox 도메인·DLP로 나가는 길을 좁히는 이중 구조였습니다. 거버넌스는 managed 4채널과 배열 병합 규칙, 잠금 키, Policy as Code로 정책을 "코드처럼" 다루는 법을 보여줬고, 관측은 OTel 전사 계측과 귀속 태그, 예산 알람, 분기 리뷰로 숫자가 다음 정책 판을 결정하게 만드는 루프였습니다.

    이 여섯 갈래를 관통하는 한 문장이 있다면 "개인의 도구를 조직의 플랫폼으로 바꾸는 건 기능 추가가 아니라 강제력의 설계"라는 것입니다. Chapter 1, 2가 다룬 모든 것 — 설치, 인증, 권한, 에이전트 — 은 Chapter 3에서 "개인이 선택할 수 있는가, 조직이 강제할 수 있는가"라는 질문을 한 번씩 다시 통과합니다.

    3. FAQ — 관리자 문의 상위 6¶

    "개인이 정책을 우회할 수 있나요?" — managed deny는 제거할 수 없고, disableBypassPermissionsMode로 --dangerously-skip 우회 자체도 막을 수 있습니다(Part 5 병합 규칙).

    "Bedrock인데 서버 관리 설정(Server-managed)이 되나요?" — Server-managed는 좌석제(Teams/Enterprise) 전용이라 Bedrock 같은 서드파티 공급자 조직에는 전달되지 않습니다. 폴백은 파일 기반 하나만이 아니라 파일 기반 / plist·HKLM(OS 레벨) / 자체 호스팅 apps gateway 경유 원격 배포 세 가지 중에서 고를 수 있습니다(Part 3, Part 5 혼합 전략).

    "개인별 지출 캡이 되나요?" — Bedrock 직결만으로는 안 되고, apps gateway의 한도 Admin API가 있어야 일·주·월 캡을 실시간 강제할 수 있습니다(Part 3).

    "코드가 학습에 쓰이나요?" — 상업 경로(Team/Enterprise/API/클라우드)는 미사용이 기본 정책입니다. ZDR(요청 완료 후 무저장)은 Enterprise 플랜에 자동 포함된 기능이 아니라, 자격을 갖춘 계정에 한해 Anthropic이 조직 단위로 개별 활성화하는 별도 옵션입니다(Part 7).

    "curl 우회는 어떻게 막나요?" — 권한 규칙이 아니라 sandbox의 allowedDomains가 막습니다. Bash를 허용해두면 WebFetch를 deny해도 curl로 우회할 수 있다는 게 이 갭의 핵심입니다(Part 4).

    "적용 확인은 어떻게 하나요?" — 전 플랫폼 공통으로 /status 한 줄이 판정 기준입니다. 소스 표기 괄호 안에 remote, plist, HKLM, HKCU, file 중 무엇이 찍히는지가 어느 채널이 이겼는지를 알려줍니다(Part 5).

    4. 실습 랩 — 무엇을, 왜 그렇게 했는가¶

    교재 PDF는 이 챕터의 랩을 Lab 1(managed 정책 배포) / Lab 2(Bedrock SSO 전환) / Lab 3(OTel 관측 배선) 세 종으로 소개합니다. 실제 수행은 별도 제공되는 핸즈온랩 HTML(ClaudeCode_Ch3_HandsOnLab.html)의 준비 + Task 5개 구성을 기준으로 삼았습니다 — Task 1(사내 npm 미러), Task 2(Bedrock + SSO), Task 3(managed-settings 조직 정책), Task 4(DLP Hook), Task 5(OTel 텔레메트리)입니다. PDF의 Lab 1(managed 정책 배포, /status 확인, .env deny, 개인 설정으로 제거 시도)은 HTML의 Task 3에 대응하고, PDF의 Lab 2는 Task 2를, PDF의 Lab 3은 Task 5를 각각 더 세분화한 관계입니다. PDF에는 없는 Task 1(npm 미러)과 Task 4(DLP Hook)가 HTML에 추가돼 있는데, Task 1은 Part 1 배포 전략의 사내 미러 개념을, Task 4는 Lab 1의 권한 규칙 통제를 내용 기반 통제로 한 단계 확장한 실습으로 보입니다. 이번 정리는 HTML 기준으로 실습했습니다.

    Task 3, 4는 sudo가 필요합니다

    진짜 Managed 스코프는 시스템 전역 경로(Linux/WSL /etc/claude-code/, macOS /Library/Application Support/ClaudeCode/)에 파일을 써야 하므로 관리자 권한 없이는 재현할 수 없습니다. sudo가 없는 환경이라면 핸즈온랩이 제시하는 대체 경로(~/.claude/settings.json, User 스코프)로도 병합·차단 메커니즘 자체는 체험할 수 있지만, "사용자가 못 바꾼다"는 강제성까지는 확인할 수 없습니다.

    5. 실행 로드맵 30 / 60 / 90¶

    도입 첫 분기의 마일스톤은 30일 단위로 세 구간입니다. 0~30일(기반)은 공급자를 확정하고 파일럿 링을 돌리며 정책 초판을 만드는 구간입니다. 31~60일(통제)은 managed 전 채널을 갖추고 sandbox와 OTel까지 배선해 실제 강제력을 갖추는 구간이고, 61~90일(규모화)은 전사 링으로 확산하고 게이트웨이를 올리며 분기 리뷰 1회차를 도는 구간입니다. 각 구간 말미마다 /status 전수 검증과 경영 보고를 고정 이벤트로 박아두는 게 로드맵의 핵심 장치입니다 — 링을 넓히기 전에 "정말 정책이 걸렸는지"를 매번 다시 확인하지 않으면, 파일럿에서만 통했던 설정이 전사에서 조용히 무력화된 채로 퍼질 수 있습니다.
