    3주차 — Chapter 3: Admin Setup¶

    이 챕터는 개인 개발자에게 조직 관리자가 되라고 요구하지 않습니다. W1의 개인 설치·로그인·권한 확인과 W2의 Subagent 권한 경계·Hook을 바탕으로, 팀과 조직에서 누가 무엇을 책임지는지 살펴봅니다. 개인 개발자, 팀 리드, 플랫폼 관리자라는 역할에 따라 배포·자격증명·게이트웨이·네트워크·거버넌스·관측·컴플라이언스·트러블슈팅을 다룹니다.

    원본: Claude Code Deep Dive Workshop / Chapter 3 — Admin Setup (9파트, 112 슬라이드. 이 정리에서는 교재 Part 8·9를 파트 8 하나로 합쳐 아래 8개 파일로 구성했습니다) 기준 버전: Claude Code v2.1.233 / 2026년 7월 교재 · 공식 문서 code.claude.com/docs 반영

    먼저: 내 역할과 실습 경로¶

    같은 내용을 읽어도 지금 할 일은 역할에 따라 다릅니다.

    역할 이 챕터에서 가져갈 판단 지금 직접 하지 않을 것 실습 경로
    개인 개발자 개인 설정과 조직 정책은 다른 책임이라는 점, 무엇을 플랫폼팀에 요청해야 하는지 회사 방화벽·IdP·전사 정책을 임의로 바꾸기 로컬 관찰 가능: Task 1에서 미러의 tarball 캐시와 격리 재설치를 확인합니다. Task 4의 시스템 Managed 스코프 배포와 강제성 검증에는 sudo가 필요합니다. 권한이 없으면 User 스코프에서 가짜 키 패턴 차단과 대조군 통과라는 차단 메커니즘만 관찰하고, 조직 강제성을 검증했다고 판단하지 않습니다. 플랫폼팀에는 "우리 조직의 미러·DLP 정책은 어디에 배포되고 어떤 로그로 검증하는가?"를 남깁니다.
    팀 리드 팀의 위험·비용·도입 기준을 정책 요구사항으로 바꾸기 조직 인증·감사 체계를 혼자 구축하기 개인 클라우드 필요: Task 2의 AWS 계정 실습
    플랫폼 관리자 배포·인증·정책·관측을 조직 책임으로 설계하고 검증하기 검증 없이 전사에 강제 정책 배포하기 조직 관리자 전용: IdP, CloudTrail, gateway, 전사 managed settings

    각 파트는 최소 개념, 조직 구성, 실제 장애·검증 사례 순서로 읽으면 됩니다. 역할과 권한이 갖춰졌을 때 볼 내용은 선택 심화로 표시했습니다.

    W1의 개인 /login, 설정 파일, 권한 확인은 여기서 "개인이 고르는 설정"으로 이어집니다. W2의 허용 목록과 PreToolUse Hook은 "조직이 추가로 강제·감사하는 통제"의 출발점입니다. 개인 설정을 알아야 조직 정책도 안전하게 읽을 수 있습니다.

    처음 보는 용어는 이렇게만 잡고 시작해도 충분합니다. AWS는 서버·권한·비용을 빌려 쓰는 Amazon의 클라우드이고, IAM은 그 안에서 "누가 무엇을 할 수 있는가"를 정하는 권한 체계입니다. SSO는 한 번 로그인으로 여러 서비스에 들어가는 방식, OIDC는 그 로그인 신원을 서비스에 전달하는 표준입니다. DLP는 민감 정보의 외부 유출을 막는 통제이며, OTel(OpenTelemetry)은 사용량·성능 같은 관측 데이터를 표준 형식으로 내보내는 도구입니다.

    회고와 검증 범위¶

    이 챕터를 공부하며 "관리자 문서는 개발자 문서의 상위 호환이 아니다"라는 점을 실감했습니다. 1~2주차의 내용을 더 많이 아는 것이 아니라, 다른 질문을 하는 법을 배우는 챕터였습니다. 개발자는 "이 기능이 어떻게 동작하는가"를 묻고, 관리자는 "개인이 바꾸지 못하게 하려면 어디에 둬야 하는가"를 묻습니다. 같은 설정 파일도 역할에 따라 보는 지점이 달랐습니다.

    managed-settings와 DLP Hook은 시스템 전역 경로에 sudo로 실제 배포해서 검증했습니다. deny는 기대대로 강력해서 CLI 플래그로도 못 뚫었지만, 반대로 ask 규칙 하나(Write(**))는 경로 패턴이 안 맞아 조용히 무효화되고 있었습니다. "배포했다"와 "의도대로 작동한다"가 다르다는 걸 보여준 지점입니다(상세는 Part 4·5).

    npm 미러와 permission_denials 필드에서도 예상과 실측이 달랐습니다. 미러는 제대로 캐싱했지만 검증 과정은 npm 자체 캐시의 영향을 받기 쉬웠고, managed deny로 차단된 도구 호출은 permission_denials 배열에 잡히지 않았습니다. 그래서 다음 주부터는 이 필드만 보지 않고 stream-json 원시 이벤트도 확인하려 합니다(상세는 Part 1·5).

    Bedrock SSO는 개인 AWS 계정으로 처음부터 재현했습니다. IAM Identity Center 설정부터 Permission Set 권한, Model access 정책, 쿼터까지 단계마다 예상과 다른 함정이 있었고(상세는 Part 2), 이 문서를 쓰는 시점엔 마지막 실제 모델 호출만 AWS 쿼터 승인 대기로 남아 있습니다.

    공식문서는 두 차례 대조했습니다. 8/9의 1차 대조에서 🔴 6 + 🟡 6건, 이번 주 재검증에서 🔴 10 + 🟡 24건을 추가로 찾았습니다. 특히 Part 3(apps gateway)는 클라이언트 연결 방식·모델 거부 동작·지출 한도 API가 실제와 달라 문서 절반을 다시 썼습니다. 자세한 내용은 각 파트의 🔴/🟡 콜아웃에 남겼습니다.

    Part 2(Bedrock SSO)는 위에서 적었듯 개인 계정으로 로그인·STS 확인까지 실제로 끝냈고, 남은 건 쿼터 승인뿐이라 거의 다 채워졌습니다. 아쉬운 점은 Part 7(신원·데이터·컴플라이언스)과 Part 3(apps gateway)의 실습 공백입니다. Part 3은 게이트웨이 컨테이너·한도용 Postgres·사내 IdP OIDC 클라이언트 등록까지 필요해 이번 주 실습 범위 밖이었고, Part 7은 진짜 조직 IdP 테넌트와 조직 CloudTrail이 있어야 재현되는 영역이라 둘 다 개념 정리로 남겨뒀습니다. 미완을 미완으로 정직하게 표기하는 편이, 나중에 이 문서를 다시 볼 때 훨씬 쓸모 있다고 판단했습니다.

    30초 요약¶

    Chapter 3은 "이 설정을 개인이 바꿀 수 있는가, 조직이 막을 수 있는가"를 묻습니다. 1~2주차가 내 노트북에서의 사용법이었다면, 이번 주는 같은 도구를 회사 전체에 배포하고 개인이 되돌리지 못하게 하는 방법을 다룹니다.

    사람에게는 로그인 한 번으로 여러 서비스에 접속하는 SSO를 쓰고, 기계와 CI 파이프라인에는 고정 키 대신 매번 발급되고 곧 만료되는 임시 자격증명을 쓰는 것을 이 문서의 권장 아키텍처로 삼습니다. 제품은 apiKeyHelper·API 키 경로도 지원하므로, 예외가 필요하면 그 경로의 보관·회전 책임을 따로 문서화합니다. 노트북에 복사되면 그대로 유출될 수 있는 키 파일을 남기지 않는 것이 목표입니다. 또 관리자가 정책 파일을 시스템 폴더에 배포하면 개인 설정과 관계없이 그 정책이 적용됩니다. 개인은 규칙을 더 엄격하게 만들 수 있어도, 조직이 막은 항목을 되돌릴 수는 없습니다.

    이 두 가지를 바탕으로 배포 채널, 네트워크 통제, 모니터링, 신원 관리가 연결됩니다. SSO·OIDC·managed settings 같은 용어는 각 파트에서 처음 나올 때 설명합니다.

    시작하기 전에 확인할 것¶

    Chapter 3은 Chapter 1(기본 사용법)과 Chapter 2(서브에이전트)를 전제로 하지만, 관점은 다릅니다. 앞 두 챕터가 "내가 어떻게 쓰는가"였다면 이 챕터는 "다른 사람이 바꾸지 못하게 하려면 무엇을 어디에 둬야 하는가"를 다룹니다. 그래서 버전보다 먼저 확인할 것은 권한입니다. 이번 Task 3·4에서는 sudo로 시스템 전역 경로에 managed settings와 DLP Hook을 실제 배포해 Managed의 강제성을 검증했습니다. 관리자 권한이 없는 독자는 User 스코프 대체 경로(~/.claude/settings.json)에서 병합·차단 메커니즘까지 확인할 수 있지만, 사용자가 바꿀 수 없는 Managed의 강제성은 그 대체 실습으로 검증할 수 없습니다.

    두 번째로 자주 혼동하는 것은 "신원"입니다. Claude 계정 레벨(SSO·SCIM·좌석 배정, claude.ai 콘솔)과 클라우드 IAM 레벨(Bedrock 호출 권한, Permission Set)은 이름만 비슷한 별도 시스템입니다. Part 7 §1의 구분을 먼저 보면 나머지 파트도 덜 헷갈립니다.

    세 번째는 필요한 인프라입니다. Bedrock SSO(Part 2)는 개인 AWS 계정에서 IAM Identity Center부터 재현할 수 있었지만, apps gateway(Part 3)와 조직 IdP·CloudTrail 연동(Part 7)은 조직 AWS 계정 관리자 권한이나 조직 IdP 없이는 끝까지 재현할 수 없습니다. 각 파트의 "직접 해보기" 절에 실제 확인 범위와 개념 정리 범위를 표시했습니다.

    다음 주차(W4)로 넘길 네 개의 다리¶

    1. Settings — W3에서 본 managed settings는 "누가 값을 강제하는가"였습니다. W4에서는 설정 소스와 우선순위를 직접 확인합니다.
    2. Permissions — W3의 allow·ask·deny와 잠금 키는 조직 경계였습니다. W4에서는 프로젝트에서 권한 규칙과 예외를 설계합니다.
    3. Hooks — W3의 DLP·감사 Hook은 조직 통제 사례였습니다. W4에서는 이벤트가 언제 발생하고 Hook을 어떻게 안전하게 운영하는지 다룹니다.
    4. MCP — W3의 허용 목록과 네트워크 경로는 확장 지점의 통제였습니다. W4에서는 MCP를 구성하고, 권한·장애를 점검합니다.

    W4에서는 조직 관리자 권한이 없어도 프로젝트 범위에서 이 네 가지를 재현할 수 있습니다. 여기서 배운 질문—"이 값은 누가 바꾸는가?", "이 도구는 누가 호출할 수 있는가?", "실행 전후에 무엇을 검사하는가?", "외부 서버와 어디까지 연결하는가?"—을 그대로 가져가면 됩니다.
