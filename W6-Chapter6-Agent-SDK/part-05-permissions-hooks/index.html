    Part 5 — 권한과 훅¶

    한 줄 요약¶

    도구 호출을 막거나 승인하는 관문이 SDK엔 두 개 있습니다 — 아직 결론이 안 난 요청만 받는 canUseTool과, 자동 승인된 것까지 전부 지나가는 PreToolUse 훅입니다.

    왜 알아야 하나¶

    감사 로그를 남기려고 canUseTool 콜백 안에 로깅을 넣었는데 allow 규칙으로 이미 통과된 Write 호출은 로그에 한 줄도 안 찍혔습니다 — 콜백 자체가 안 불렸기 때문입니다. 쓰기를 허용할지 묻는 콜백 하나에 정책을 다 넣으면, 이미 allow 규칙이나 권한 모드로 승인된 호출은 그 콜백을 지나지 않습니다. 모든 호출을 예외 없이 감사하거나 차단해야 하는 정책이라면 canUseTool보다 앞선 관문인 PreToolUse 훅을 써야 합니다.

    ▲ 교재 슬라이드 43 — 통제 4수단 지형

    1. 두 관문의 코드는 이렇게 다릅니다¶

    이 챕터의 코드는 대부분 canUseTool처럼 결과를 콜백 함수 안에서 return(반환)하는 형태입니다. 반환값은 그 함수가 일을 마치고 호출한 쪽에 돌려주는 값이고, { behavior: "allow" }처럼 { 이름: 값 }으로 묶어서 여러 정보를 한 번에 돌려줍니다. canUseTool은 behavior라는 이름(필드)으로 답하고, PreToolUse 훅은 hookSpecificOutput.permissionDecision이라는 다른 이름으로 답합니다. 반환 형식부터 다릅니다.

    // canUseTool: 아직 결론이 안 난 요청만 여기로 온다
options: {
  canUseTool: async (toolName, input) => {
    if (toolName === "Write") return { behavior: "allow", updatedInput: input };
    return { behavior: "deny", message: "쓰기는 허용 목록에 있는 경로만" };
  },
}

    // PreToolUse 훅: 자동 승인된 호출까지 포함해 전부 지나간다
hooks: {
  PreToolUse: [{ hooks: [async () => ({
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "정책 위반",
    },
  })] }],
}

    canUseTool(toolName, input, options)는 PermissionResult를 Promise로 돌려줍니다. 허용은 { behavior: 'allow', updatedInput: input }(updatedInput은 타입상 선택값이지만, 입력을 그대로 돌려주더라도 명시해 두는 편이 여러 버전에서 안전합니다), 거부는 { behavior: 'deny', message: '사유' }입니다.

    직접 해보기¶

    같은 Write 요청을 두 가지 방식으로 막아봤습니다.

    $ node permission-hooks.mjs callback
CAN_USE_TOOL Write {"file_path":"/Users/jade/claude-lab/ch6/permission-probe.txt","content":"approved"}
완료했습니다. `/Users/jade/claude-lab/ch6/permission-probe.txt` 파일에 `approved`를 정확히 작성했습니다.
{"subtype":"success","is_error":false,"num_turns":2}

    $ node permission-hooks.mjs hook-deny
PRE_TOOL_USE Write {"file_path":"/Users/jade/claude-lab/ch6/permission-probe-deny.txt","content":"approved"}
파일 쓰기가 차단되었습니다.
{"subtype":"success","is_error":false,"num_turns":2}

    첫 실행은 canUseTool 콜백이 Write 요청을 받아 허용했습니다. 두 번째 실행은 같은 Write 호출을 PreToolUse가 아예 먼저 가로채 막았습니다 — 콜백까지 갈 필요도 없었습니다.

    ▲ 교재 슬라이드 44 — canUseTool 콜백

    2. 왜 훅이 먼저 걸렸는지 — 평가 순서는 여섯 단계입니다¶

    방금 본 두 실행의 차이는 우연이 아니라 정해진 순서 때문입니다. 공식 문서 기준 순서는 hooks → deny 규칙 → ask 규칙 → permission mode → allow 규칙 → canUseTool입니다. 여섯 단계 모두가 canUseTool까지 내려가는 건 아닙니다 — deny 규칙에 걸리면 그 자리에서 차단되고, allow 규칙이나 권한 모드가 이미 결론을 냈으면 canUseTool을 거치지 않고 바로 실행됩니다. 아직 결론이 안 난 요청(ask 규칙에 걸린 경우)만 canUseTool로 넘어갑니다. 훅이 allow를 반환해도 뒤에 있는 deny 규칙을 건너뛰지는 않습니다.

    flowchart TD
  A["도구 요청"] --> B["PreToolUse 훅"]
  B -->|deny| X["차단"]
  B --> C["deny 규칙"]
  C -->|일치| X
  C --> D["ask 규칙"]
  D -->|일치, 미결론| F["canUseTool"]
  D --> E["권한 모드 · allow 규칙"]
  E -->|허용| G["실행"]
  F -->|allow| G
  F -->|deny| X
  style X fill:#ffebee,stroke:#c62828,color:#000
  style G fill:#e8f5e9,stroke:#388e3c,color:#000

    이미 자동 승인된 호출에는 canUseTool 콜백 자체가 오지 않습니다.

    ▲ 교재 슬라이드 49 — 평가 순서 정리

    현장 메모

    서비스 계정으로 돌아가는 에이전트는 사람이 눌러 줄 승인 창이 없습니다. dontAsk와 최소 allow 목록으로 기본 실패를 차단 쪽에 두고, 조직 정책처럼 반드시 검사해야 하는 규칙은 PreToolUse에 둡니다.

    흔한 오해 바로잡기¶

    "canUseTool 콜백 하나만 있으면 모든 도구 호출을 통제할 수 있다" — 아닙니다. allow 규칙이나 권한 모드로 이미 결론이 난 호출은 이 콜백을 거치지 않습니다. 예외 없이 전부 감사하거나 차단해야 하는 정책이라면 그보다 앞단인 PreToolUse 훅을 써야 합니다.

    "훅이 허용(allow)을 반환하면 그걸로 끝이다" — 아닙니다. 평가 순서상 훅이 allow해도 그 뒤의 deny 규칙에 걸리면 그 자리에서 차단됩니다. 훅은 맨 앞 관문일 뿐이고 뒷단의 deny 규칙을 건너뛰게 만들지는 못합니다.

    정리¶

    요점은 셋입니다. ① 관문은 canUseTool과 PreToolUse 둘이고 반환 형식부터 다릅니다. ② 요청은 hooks→deny→ask→mode→allow→canUseTool 순서로 흐르고 이미 결론 난 호출은 뒷단(canUseTool)까지 가지 않습니다. ③ 권한 모드는 현재 여섯 가지(default, dontAsk, acceptEdits, plan, auto, bypassPermissions)입니다 — 교재의 다섯 가지 표기는 다른 챕터의 여섯 가지와도 어긋나므로, 현행 SDK 권한 문서 기준으로 읽습니다. bypassPermissions는 별도 위험 허용 옵션이 필요한 예외로 취급합니다.
