    Part 4 — 구조화 출력¶

    한 줄 요약¶

    구조화 출력은 모델 문장을 나중에 억지로 파싱하는 방법이 아니라, 호출할 때부터 답의 모양을 JSON Schema로 약속하는 방법입니다.

    왜 알아야 하나¶

    다음 프로그램이 if (status === 'down')으로 분기해야 하는데 모델 답이 "장애 같습니다"면, 결국 정규식으로 문장을 긁게 됩니다. 문구가 조금만 바뀌어도 조용히 오탐이 납니다. 필요한 건 down인지 degraded인지처럼 비교 가능한 값 — 가능한 상태와 필드를 호출 전에 JSON Schema로 정해두면 게이트 코드는 모델 문장을 해석할 필요가 없습니다. (아래 "직접 해보기"에서는 그 스키마 자체가 --json-schema is not a valid JSON Schema로 거부당하는 걸 먼저 겪었습니다.)

    ▲ 교재 슬라이드 36 — 왜 구조화 출력인가

    1. Zod와 JSON Schema는 역할이 다릅니다¶

    스키마(schema)는 "이 데이터는 어떤 항목을 어떤 형식으로 가져야 한다"를 적은 규격서입니다 — IAM 정책 문법 검사나 CloudFormation 파라미터 정의와 같은 역할입니다. Zod 스키마는 Node 애플리케이션이 값의 타입을 검사할 때 씁니다. JSON Schema는 그 규격을 JSON으로 표현하는 별도 표준이고 SDK가 Claude Code에 전달하는 출력 계약이 바로 이 형식입니다. 같은 상태 모델에서 두 표현을 만들면 모델 출력과 애플리케이션 검증의 기준이 갈라지지 않습니다.

    const reportSchema = z.object({
  status: z.enum(["healthy", "degraded", "down"]), // 이 셋 중 하나만 허용
  summary: z.string(),
});
const q = query({
  prompt: "서비스는 연결 거부 오류로 응답하지 않는다. 상태와 20자 이내 요약을 JSON 계약에 맞춰 답해.",
  options: {
    outputFormat: {
      type: "json_schema",
      schema: z.toJSONSchema(reportSchema, { target: "draft-7" }),
    },
    allowedTools: [], maxTurns: 1,
  },
});

    ▲ 교재 슬라이드 39 — 타입 세이프 / Pydantic

    Python도 output_format에 {type: 'json_schema', schema: ...}를 넘깁니다. 다만 Python의 Pydantic 모델과 TypeScript의 Zod는 각각 애플리케이션 쪽 타입 도구일 뿐이고 SDK 옵션 이름은 언어에 따라 output_format과 outputFormat으로 다릅니다.

    직접 해보기¶

    처음에는 Zod 4의 기본 변환을 그대로 넣었습니다. draft-07이나 2020-12는 JSON Schema라는 규격 자체의 버전 이름입니다(같은 내용을 다른 문법으로 쓸 수 있는 여러 판이 있다고 생각하면 됩니다). 현행 CLI는 구버전인 draft-07판만 읽을 수 있어서 Zod가 기본으로 만든 2020-12판 메타데이터를 받아들이지 못했습니다.

    $ node structured-output.mjs
Error: --json-schema is not a valid JSON Schema: no schema with key or ref "https://json-schema.org/draft/2020-12/schema"

    target: 'draft-7'을 명시해 다시 실행했습니다.

    $ node structured-output.mjs
{"subtype":"success","is_error":false,"structured_output":{"status":"down","summary":"연결 거부로 응답 없음"}}

    교재에는 없지만 공식문서엔 있던 조합 문제

    outputFormat 자체는 현행 TypeScript SDK에서 지원합니다. 실패 원인은 SDK 옵션이 아니라 Zod 4 기본 스키마의 draft 버전이었습니다 — 공식 문서도 "SDK는 JSON Schema draft-07로 검증하는데 Zod 4는 기본으로 draft 2020-12를 만든다"고 이 조합을 이미 명시하고 있습니다. 문서화된 제약이니 처음부터 target: 'draft-7'을 붙이는 게 맞고, 교재(2026.07판)는 이 옵션이 생기기 전이라 언급이 없었던 것으로 보입니다.

    흔한 오해 바로잡기¶

    "구조화 출력을 쓰면 모델이 거짓말을 못 한다" — 아닙니다. JSON Schema는 답의 모양(필드·타입)만 기계적으로 보장하지, 그 값이 사실인지는 보장하지 않습니다. status가 "down"으로 왔다고 해서 실제로 서비스가 죽었다는 뜻은 아닙니다 — 그 값을 뒷받침할 근거를 도구로 확인하는 건 별개의 일입니다(Part 3).

    "Zod로 스키마를 만들면 그대로 SDK에 넘기면 된다" — 아닙니다. 위 실습에서 확인했듯 Zod 4의 기본 변환은 draft 2020-12 메타데이터를 만드는데, SDK는 draft-07만 검증합니다. target: 'draft-7'을 명시해야 합니다.

    정리¶

    구조화 출력은 답의 사실성을 보장하지 않습니다. 대신 status가 셋 중 하나인지, summary가 존재하는지를 기계적으로 보장합니다. 그래서 정책 게이트는 문장 검색 대신 .structured_output.status === 'down'처럼 작성할 수 있습니다.
