    Part 7 — 호스팅과 프로덕션¶

    한 줄 요약¶

    SDK 앱을 운영한다는 건 모델 호출만 배포하는 일이 아닙니다. Claude Code 자식 프로세스, 세션 저장소, 동시성 한도, 관측 신호를 함께 운영하는 일입니다.

    왜 알아야 하나¶

    웹 요청 하나가 query를 호출하면 앱 프로세스는 Claude Code 자식 프로세스를 띄웁니다. 그런데 대화 기록(세션 트랜스크립트)은 그 컨테이너의 로컬 디스크(~/.claude/projects/ 아래)에만 쓰입니다. 컨테이너를 여러 개로 늘리면 다음 요청이 다른 컨테이너로 갈 수 있습니다. 그 컨테이너에는 이전 트랜스크립트가 없으니 resume이 실패합니다. 세션 ID만 어딘가에 잘 저장해 둬도 트랜스크립트 자체가 없으면 소용없다는 뜻입니다. 스케일링은 CPU 복제만의 문제가 아닙니다.

    ▲ 교재 슬라이드 59 — 서브프로세스 아키텍처

    1. 로컬 빌드가 첫 배포 게이트입니다¶

    SDK 패키지는 플랫폼별 Claude Code 바이너리를 optional dependency로 함께 받아옵니다(예: @anthropic-ai/claude-agent-sdk-linux-x64). 이미지 안에 CLI를 따로 설치할 필요는 없습니다. npm ci --omit=optional처럼 optional 패키지를 건너뛰는 설치만 피하면 됩니다. 컨테이너는 root로 실행하지 않고 로그는 표준 출력으로 보내며, API 키·OAuth 토큰·Bedrock 자격증명을 이미지에 복사하지 않습니다.

    FROM node:22-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
USER node
CMD ["node", "medic-lite.mjs"]

    이 Dockerfile은 구조를 보여 주는 스케치입니다. SDK의 Claude Code 배포 방식과 운영 인증은 실제 이미지에서 확인한 뒤 고정해야 합니다.

    실습 범위 밖 — 로컬 빌드 단계

    이 환경에는 Docker CLI 자체가 없습니다(zsh: command not found: docker). 이번 정리에서는 Docker 설치를 새로 하지 않고 실제 빌드·컨테이너 실행을 범위 밖으로 남겨두기로 했습니다. Kubernetes 배포는 처음부터 이 챕터의 필수선 밖이고, Bedrock 실배포는 W3부터 이어진 AWS 쿼터 승인 대기로 여전히 확인하지 못했습니다(아래 §2 참고) — 둘은 성격이 다릅니다. Dockerfile 스케치와 그 안에 담긴 원칙(비루트 실행, optional dependency로 바이너리 동봉, 자격증명 미포함)은 실제 환경에서 이미지를 빌드할 때 그대로 적용하면 됩니다.

    2. 동시성은 쿼터와 함께 계산합니다¶

    에이전트 한 요청은 여러 턴과 도구 호출을 만들 수 있습니다. 워커 수를 올려도 Bedrock의 RPM·TPM 또는 API 공급자의 rate limit가 그대로면 지연과 throttling만 늘어납니다. 공식 문서는 호스트 한 대가 감당할 동시 실행 수를 CPU가 아니라 메모리로 잡습니다 — 세션 하나당 RAM 상한을 정하고 (호스트 RAM − 오버헤드) ÷ 세션당 RAM 상한으로 계산하며, 시작 기준으로 세션당 1GiB RAM·5GiB 디스크·CPU 1개를 제시합니다. 상주 점검원처럼 오래 도는 워크로드는 같은 session_id가 항상 같은 컨테이너로 가도록 컨시스턴트 해싱을 걸어 두는 편이 안전합니다. 요청 큐, 요청별 maxTurns·예산, 공급자별 동시성 제한은 이 위에 얹습니다.

    ▲ 교재 슬라이드 65 — Bedrock 프로덕션 연결

    W3 실습 당시 Bedrock은 쿼터 승인 대기로 실제 호출까지 확인하지 못한 채 미완으로 남겨뒀습니다(W3 Part 2 참고). 그 상태가 이어지고 있어 이 원고에서도 Bedrock 경로의 실제 호출은 재시도하지 않았습니다. 환경변수만 설정됐다고 모델 용량이 준비된 건 아니라는 것을 두 챕터에서 똑같이 확인한 셈입니다.

    3. 관측은 요청 ID부터 연결합니다¶

    OTel(OpenTelemetry)은 로그·메트릭·트레이스를 한 추적 맥락으로 묶는 표준입니다. SDK는 이 설정을 코드로 새로 만들 필요가 없습니다 — 실행 환경의 OTel 환경변수를 그대로 물려받습니다. W3에서 CLI에 걸었던 것과 같은 CLAUDE_CODE_ENABLE_TELEMETRY=1, OTEL_METRICS_EXPORTER/OTEL_LOGS_EXPORTER=otlp 같은 변수를 SDK를 돌리는 컨테이너에도 심어두면 query() 호출마다 스팬·메트릭·로그가 그대로 나갑니다. 여기에 SDK 결과의 session ID, 모델, turns, 비용, 종료 이유를 애플리케이션 요청 ID와 함께 남기면 어느 호출이 늦었고 왜 재시도했는지 따라갈 수 있습니다. 프롬프트와 도구 입력은 기본적으로 export에 포함되지 않습니다.

    ▲ 교재 슬라이드 66 — 프로덕션 체크리스트

    현장 메모

    다중 레플리카 서비스가 세션 상태를 외부 저장소에 두지 않으면 재시작 때만 문제가 생기는 게 아닙니다. 같은 사용자의 다음 요청이 다른 Pod로 가는 순간에도 깨집니다. 공식 문서는 이 역할을 sessionStore 옵션(S3·Redis·Postgres 같은 외부 저장소에 트랜스크립트를 미러링하는 어댑터)으로 제시합니다. 스티키 세션은 임시 완화책이고, sessionStore·만료 정책·재개 실패 처리가 근본 계약입니다.

    흔한 오해 바로잡기¶

    "세션 ID만 어딘가에 저장해 두면 어느 컨테이너에서 재개해도 된다" — 아닙니다. 대화 기록(트랜스크립트) 자체가 그 컨테이너의 로컬 디스크에만 있습니다. ID를 알아도 트랜스크립트가 없는 컨테이너에서는 재개가 실패합니다 — 트랜스크립트를 sessionStore로 외부에 미러링해야 진짜로 풀리는 문제입니다.

    "동시성은 CPU 코어 수로 정하면 된다" — 아닙니다. 공식 문서는 세션 하나당 RAM 상한을 기준으로 동시 실행 수를 계산합니다((호스트 RAM − 오버헤드) ÷ 세션당 RAM 상한). CPU를 늘려도 메모리가 부족하면 새 세션을 못 띄웁니다.

    정리¶

    프로덕션 준비의 최소선은 로컬에서 이미지를 빌드하고 한 query를 실행해 보는 것입니다. 그 다음에야 외부 세션 저장소, 요청 큐, 비밀 주입, OTel, Kubernetes 배치를 논의할 수 있습니다. 실제 이미지 빌드와 Bedrock 실호출은 이번 정리에서는 범위 밖으로 남겨두고 그 앞 단계인 설계 원칙까지만 다뤘습니다.
