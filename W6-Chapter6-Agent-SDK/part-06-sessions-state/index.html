    Part 6 — 세션과 상태¶

    한 줄 요약¶

    세션 ID는 대화 이력의 좌표이고, 상태 저장소는 그 좌표를 프로세스 밖으로 내보내는 장소입니다. settingSources는 어떤 로컬 설정을 실행에 섞을지도 정합니다.

    왜 알아야 하나¶

    cron으로 매분 도는 medic-lite.mjs는 프로세스가 끝나는 순간 메모리에 있던 session_id도 같이 사라집니다. 어제 점검이 OK였다는 걸 오늘 실행이 알 방법이 없다는 뜻입니다. 이전 ID를 파일이나 DB에 저장해 두지 않으면 매번 처음 대화가 되어 "어제는 OK였는데 지금은 DOWN"이라는 변화 자체를 말할 수 없습니다.

    ▲ 교재 슬라이드 52 — 세션 외부 스토리지

    1. 상태는 세 층으로 나눕니다¶

    • 대화 이력: session_id가 가리키는 Claude Code 세션입니다. 다음 query의 resume 값이 됩니다.
    • 업무 상태: 마지막 점검 시각, 대상 ID, 재시도 횟수처럼 앱이 직접 관리하는 값입니다. JSON·DB·큐에 둡니다.
    • 실행 설정: CLAUDE.md, settings, MCP 등록처럼 실행 전에 읽히는 값입니다. 상태 저장소와 섞지 않습니다.

    이 셋을 한 파일에 몰아두면 세션을 다시 열고 싶은 것인지 실행 정책을 바꾸고 싶은 것인지 구분할 수 없어집니다.

    2. settingSources의 기본값을 직접 적어둡니다¶

    랩 HTML은 SDK 기본이 파일시스템 설정을 읽지 않는다고 설명합니다. 현재 공식 TypeScript/Python 문서와 0.3.260 타입 선언은 반대입니다. 생략하면 CLI처럼 user·project·local을 모두 읽습니다. []를 넣으면 이 세 파일시스템 소스는 꺼지지만 완전한 격리는 아닙니다 — managed policy, ~/.claude.json, auto memory, claude.ai의 MCP 커넥터는 settingSources와 무관하게 여전히 적용됩니다. 여러 사용자·테넌트가 같은 프로세스를 공유하는 격리가 목적이라면 settingSources: []만으로는 부족하고 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 같은 설정을 더 얹어야 합니다.

    // 외부 설정을 읽지 않는 재현 가능한 호출
options: { settingSources: [] }

// 프로젝트의 CLAUDE.md와 settings를 의도적으로 쓸 때
options: { settingSources: ["project"] }

    ▲ 교재 슬라이드 55 — Claude Code 자산 로드 / settingSources

    교재와 현행의 차이

    랩의 "기본 로드 안 함"은 현행 공식 문서와 맞지 않습니다. 지금은 생략하면 이미 project까지 다 읽고 있으므로 project를 꼭 넣어야 하는 경우는 settingSources를 명시적으로 지정할 때뿐입니다(그때 project를 빼면 CLAUDE.md가 안 읽힌다는 뜻이지, 생략 상태에서 project가 빠져 있다는 뜻이 아닙니다). 테스트는 []로 시작해서 필요한 source만 한 단계씩 추가하는 편이 원인을 좁히기 쉽습니다.

    직접 해보기¶

    Task 4는 .medic-session 파일에서 ID를 읽고 result마다 다시 씁니다. 상태 파일을 OK에서 DOWN으로 바꿔 두 번 실행하는 랩입니다. 랩 원문 그대로(maxTurns: 4)는 상한에서 끝까지 가지 못했습니다.

    $ echo 'service: OK' > status.txt
$ node medic-lite.mjs
--- 점검 완료, turns=5 cost=$0.0675692
Error: Claude Code returned an error result: Reached maximum number of turns (4)

    "점검 완료" 로그가 먼저 찍히고 그 다음에 Error가 뜨는 건 순서가 어긋난 게 아닙니다. 단발성 query()는 상한에 걸려도 result 메시지를 먼저 내보낸 뒤 그 실패 내용을 담아 예외를 던집니다. 그래서 세션 ID를 파일에 쓰고 turns·cost를 찍는 코드까지는 실행되고 그 다음에 catch하지 않은 예외로 프로세스가 죽습니다.

    result의 num_turns가 5인데 옵션의 maxTurns는 4였습니다. W5에서도 상한과 집계가 정확히 같은 숫자는 아니었습니다. maxTurns: 8로 올려 다시 실행하자 둘 다 상한 안에서 끝났습니다.

    $ echo 'service: OK' > status.txt
$ node medic-lite.mjs
**서비스 상태: OK (정상)**
이전 점검 기록은 파일 내에 없어 상태 변화는 확인할 수 없으며, 현재 DOWN이 아니므로 원인 후보나 조치는 불필요합니다.
--- 점검 완료, turns=4 cost=$0.068886

$ echo 'service: DOWN (connection refused)' > status.txt
$ node medic-lite.mjs
**상태 변화: 이전 점검(OK, 정상) → 현재 DOWN (connection refused)로 전환됨.**
**서비스 상태: DOWN** — 원인 후보는 ①대상 프로세스/서버 다운 ②포트 미개방 또는 방화벽 차단 ③잘못된 호스트·포트 설정이며, 첫 조치로 서버 프로세스 상태 확인(`ps`/`systemctl status`) 후 필요시 재기동을 권장합니다.
--- 점검 완료, turns=2 cost=$0.01569

    두 번째 실행이 .medic-session에 저장된 이전 session_id를 resume으로 이어받아 "OK였는데 지금은 DOWN"이라는 변화를 스스로 언급했습니다. 이 결과를 보면 "4턴이면 충분"이라는 교재 예시를 현재 모델·프롬프트에 그대로 적용할 수 없습니다. 상한은 실제로 재봐야 하는 운영값입니다.

    흔한 오해 바로잡기¶

    "settingSources를 생략하면 아무 로컬 설정도 안 읽는다" — 아닙니다. 랩 원문과 반대로, 현행 SDK는 생략하면 CLI처럼 user·project·local을 전부 읽습니다. 예측 가능한 실행을 원한다면 []를 직접 적어야 합니다.

    "settingSources: []면 완전히 격리된다" — 아닙니다. managed policy나 ~/.claude.json, auto memory, claude.ai의 MCP 커넥터는 이 옵션과 무관하게 여전히 적용됩니다. 여러 사용자가 같은 프로세스를 공유하는 진짜 격리가 목적이라면 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 같은 설정을 더 얹어야 합니다.

    정리¶

    세션을 파일에 적는 것만으로 운영 상태 관리가 끝나지는 않습니다. 세션 ID, 대상의 실제 상태, 실행 정책을 분리하고 각각의 보존 기간과 접근 권한을 정해야 합니다. 설정 출처도 상태처럼 명시해야 같은 코드가 다른 개발자의 로컬 설정 때문에 달라지지 않습니다.
