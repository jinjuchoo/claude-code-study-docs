    6주차 — Chapter 6: Agent SDK¶

    먼저 할 3가지¶

    Node.js 18 이상을 준비한 뒤, 로컬에서 query()를 한 번 실행합니다. result를 포착해도 멈추지 말고 스트림 끝까지 읽습니다.

    원본: Claude Code Deep Dive Workshop / Chapter 6 — Agent SDK (9파트, 약 84 슬라이드) 기준 버전: Claude Code 2.1.260 / @anthropic-ai/claude-agent-sdk 0.3.260 / 2026-09-04 · 교재는 2026년 7월판

    회고¶

    첫 hello.mjs는 생각보다 평범했습니다. 파일 목록을 읽고 한 줄로 답한 뒤, 마지막 메시지에 session ID와 비용을 담아 보냈습니다. CLI를 라이브러리로 바꾼다고 모델 호출을 처음부터 조립하는 것은 아니었습니다. 인증, 도구 실행, 세션 기록은 Claude Code 쪽에 이미 있고 프로그램은 그 흐름을 읽습니다.

    랩을 그대로 따라가니 교재와 현재 버전의 차이도 바로 보였습니다. claude /status는 이 실행 환경에서 쓸 수 없었지만 SDK의 첫 query는 기존 CLI 인증으로 성공했습니다. 가장 큰 차이는 settingSources였습니다. 랩은 이를 생략하면 파일시스템 설정을 읽지 않는다고 설명하지만, 현재 타입 선언과 공식 문서는 생략 시 user·project·local을 모두 읽는다고 명시합니다. 임베딩 프로그램의 실행을 예측 가능하게 하려면 []를 직접 적어야 합니다.

    세션 랩은 더 조심해서 읽게 됐습니다. 대화 재개는 sessionId를 갱신해 resume에 넘기는 세 줄로 실제로 이어졌습니다. 반면 상태 파일 점검원은 랩 원문의 maxTurns: 4에서 상한에 걸려 멈췄습니다. 성공 사례만 남기지 않고 이 실패도 기록한 이유입니다. 상한을 8로 올려 다시 실행하니 OK→DOWN 상태 변화까지 정확히 잡아냈습니다. 상한은 설명용 숫자가 아니라 실제 프롬프트와 모델로 확인해야 하는 운영값이었습니다.

    6주를 마치고 보니 좋은 에이전트는 프롬프트 한 줄만으로 만들 수 없었습니다. 입력 범위, 출력 계약, 도구 권한, 세션 보존 위치가 코드에 드러나야 다음 사람도 고칠 수 있습니다.

    W5에서 가져오는 지도¶

    W5에서 한 일 W6에서 같은 역할을 하는 것
    claude -p 실행 query() 호출
    stream-json 줄 읽기 한 호출에서 나오는 메시지 스트림 순회
    마지막 JSON 봉투 확인 result와 그 안의 structured_output을 포착한 뒤 스트림 종료 확인
    --resume resume: sessionId
    --allowed-tools 도구 등록 뒤 allowedTools로 실행 허용
    jq -e로 결과 분기 JSON Schema 출력 계약 뒤 JavaScript 조건문

    차이는 호출 위치입니다. W5에서는 셸이 호출·파싱·분기를 맡았고, W6에서는 프로그램이 같은 순서를 값과 함수로 다룹니다.

    이 챕터에서 이어지는 것¶

    5주차에서는 claude -p를 셸과 엮어 자동화했습니다. 6주차에서는 그 자동화 계약을 애플리케이션 코드로 옮깁니다. 도구 등록, 실행 허용, 쓰기 검사는 서로 다른 층입니다. 실제로 실행해 보니 Zod가 만든 스키마는 draft/2020-12 형식이라 거부됐고, maxTurns: 4는 부족해서 상한에 걸렸습니다. 이 원고는 로컬 최소 query()를 먼저 완성하고, 사내 배포 점검 도우미에 대화 재개, 규정 조회 도구, 상태 계약, 쓰기 차단, 상태 저장을 하나씩 더한 기록입니다.

    30초 요약¶

    SDK는 Claude Code의 대화·도구·권한·세션 기능을 TypeScript와 Python에서 호출하는 인터페이스입니다. 한 번의 query()는 여러 메시지를 차례로 내보내고, result는 에이전트 루프가 끝났음을 알립니다. 그 뒤에도 system event가 몇 개 올 수 있으므로 result를 포착해도 스트림 끝까지 읽습니다. 이 시간 순서를 이해한 뒤 필요한 도구와 정책을 붙입니다.

    먼저 실행 가능한 query를 만들고, 그다음 JSON Schema로 출력 모양을 고정합니다. 쓰기처럼 위험한 도구는 canUseTool 또는 PreToolUse 훅으로 통제합니다. 세션 ID는 메모리에서 대화를 잇고, 같은 호스트에서는 로컬 트랜스크립트와 함께 재개됩니다. 다른 호스트나 컨테이너에서는 ID만으로 재개할 수 없으므로 sessionStore로 트랜스크립트를 공유하거나 복원해야 합니다.

    목차¶

    # 파트 한 줄
    1 SDK 기본 최소 query()에서 result를 포착하고 trailing event까지 읽는 흐름을 봅니다.
    2 query와 멀티턴 점검 대화를 resume으로 잇습니다.
    3 커스텀 도구 배포 규정 조회 함수를 도구로 등록하고 허용합니다.
    4 구조화 출력 점검 상태를 문장이 아닌 계약된 값으로 받습니다.
    5 권한과 훅 쓰기 요청을 정책 관문에서 차단합니다.
    6 세션과 상태 대화 ID·점검 상태·실행 설정을 나눠 저장합니다.
    7 호스팅과 프로덕션 선택 심화: 컨테이너·다중 인스턴스·관측의 준비선을 봅니다.
    8 캡스톤과 Labs 배포 점검 도우미로 부품과 실습 결과를 다시 조립합니다.

    시작하기 전에 확인할 것¶

    Node.js 18 이상과 지원되는 인증 경로가 필요합니다. 이 랩에서는 별도 API 키를 만들지 않은 상태에서 작은 query()가 성공했지만, 이는 이 실습 환경의 관측값일 뿐 SDK의 일반 인증 계약은 아닙니다. 공식 문서가 명시한 제품·서비스용 경로는 ANTHROPIC_API_KEY·Bedrock·Vertex·Foundry입니다(Part 1·Part 7 참고). claude /status처럼 대화형 UI 명령은 실행 환경에 따라 사용할 수 없습니다. 이 랩에서 인증 상태를 확인한 근거는 작은 query()가 result를 냈다는 실행 기록입니다.

    SDK는 기본 설정을 상속할 수 있습니다. 로컬의 CLAUDE.md나 MCP 설정이 몰래 실행을 바꾸지 않게 하려면 settingSources: []를 적고 의도적으로 프로젝트 설정을 쓸 때만 ['project']를 넣습니다.

    필수 완료선과 선택 심화¶

    필수 완료선은 로컬에서 최소 query() 프로그램을 실행해 assistant 메시지와 result를 구분하고, result 뒤 event까지 스트림을 읽는 것입니다. 이 랩은 기존 CLI 로그인 상태와 Node.js 18 이상에서 시작했습니다. resume, 규정 조회 도구, 상태 스키마, 쓰기 차단, 상태 저장은 이 최소 프로그램을 사내 배포 점검 도우미로 확장하는 순서입니다.

    선택 심화는 컨테이너 이미지, Kubernetes, 다중 인스턴스 세션 저장소, 제품·서비스용 인증입니다. 이는 로컬 최소 프로그램의 완료 조건이 아닙니다. 이 원고에서 실제로 검증하지 못한 범위는 그대로 표시합니다.

    실습 기록¶

    이 정리의 실습은 2026-09-04에 직접 실행한 결과입니다. 환경: macOS 26.6.2 / Node 25.8.1 / Claude Code 2.1.260 / SDK 0.3.260 / Zod 4.5.4.

    Lab 상태 핵심 발견
    Task 0 — 설치·인증 ⚠️ 부분 완료 npm 기본 캐시는 root 소유 파일로 실패했고, 프로젝트 전용 캐시로 설치했습니다. /status는 이 환경에서 미지원이었습니다.
    Task 1 — 첫 query ✅ 완료 기존 CLI 인증으로 query 성공, 2턴·$0.1208436을 기록했습니다.
    Task 2 — 대화 메모리 ✅ 완료 resume에 넘긴 session_id로 두 번째 질문이 이름을 정확히 기억했습니다.
    Task 3 — 커스텀 도구 ✅ 완료 in-process MCP의 노트 검색과 금요일 배포 규칙을 확인했습니다.
    Task 4 — 점검원 ✅ 완료 랩의 maxTurns: 4는 부족해 상한에 걸렸고, 8로 올리자 OK→DOWN 상태 변화까지 정확히 잡아냈습니다.

    각 태스크의 원본 실행 로그는 해당 파트의 "직접 해보기" 절에 있습니다. 실패 원인과 공식문서 대조는 Part 8 — 캡스톤과 Labs에 정리했습니다.
