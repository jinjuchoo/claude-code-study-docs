    Part 3 — 커스텀 도구¶

    한 줄 요약¶

    tool()로 만든 함수를 createSdkMcpServer()에 넣으면 별도 서버 프로세스 없이 에이전트가 부를 수 있는 MCP 도구가 됩니다.

    왜 알아야 하나¶

    모델이 "금요일 배포는 피하세요"라고 답했다고 해봅시다. 이게 우리 회사 규정인지 모델의 추정인지, 호출 로그에 근거가 안 남으면 리뷰어가 검증할 방법이 없습니다. 사내 노트나 API를 읽는 함수를 도구로 만들고 그 도구의 결과만 근거로 답하게 하면, 근거가 코드와 호출 로그에 남습니다. (아래 "직접 해보기"에서는 그 근거 자체가 과거 일정이라, "다음"이라는 질문의 시간 전제와 도구가 준 사실을 분리해서 읽어야 했습니다.)

    MCP(Model Context Protocol)는 모델이 도구와 데이터를 같은 형식으로 호출하기 위한 약속입니다. 여기서 in-process MCP 서버란, 네트워크 포트나 별도 Node 프로세스를 열지 않고 현재 애플리케이션 메모리 안의 함수를 MCP 도구로 노출하는 방식을 말합니다.

    ▲ 교재 슬라이드 24 — tool의 4요소

    1. 입력 스키마부터 적습니다¶

    Zod는 JavaScript 값의 모양을 검사하는 라이브러리입니다. keyword: z.string()은 search_note가 문자열 키워드 하나만 받는다는 계약입니다. 아래 코드의 async ({ keyword }) => ({ ... })는 Part 1에서 본 화살표 함수(입력 => 결과 형태로 이름 없이 짧게 쓰는 함수)이고, { keyword }는 입력 봉투에서 keyword 항목만 꺼내 쓰겠다는 뜻입니다.

    const searchNote = tool(
  "search_note",
  "사내 노트에서 키워드가 포함된 문장을 찾는다",
  { keyword: z.string().describe("찾을 키워드") },
  async ({ keyword }) => ({
    content: [{ type: "text", text: findNote(keyword) }],
  }),
);
const shelf = createSdkMcpServer({ name: "shelf", version: "1.0.0", tools: [searchNote] });

    도구 함수가 예외를 던져도 SDK 루프 전체가 죽지는 않습니다. in-process MCP 서버가 처리 안 된 예외를 그대로 붙잡아 에러 결과로 바꾸고 모델은 그 예외 메시지를 읽은 뒤 루프를 계속합니다. isError: true로 직접 반환하느냐 그냥 throw하느냐의 차이는 "성공이냐 실패냐"가 아니라 "모델이 읽을 오류 문구를 내가 정할지, 날것의 예외 문자열을 그대로 보낼지"입니다. 사용자에게 보여줘도 되는 말로 실패를 설명하고 싶다면 isError: true와 직접 쓴 text로 반환하고, 디버깅 단계에서 원인을 빨리 보고 싶다면 그냥 throw해도 루프는 이어집니다.

    flowchart LR
  A["Zod 입력 스키마"] --> B["tool() 함수"]
  B --> C["createSdkMcpServer()"]
  C --> D["mcpServers: { shelf }"]
  D --> E["allowedTools: mcp__shelf__search_note"]

  style E fill:#e8f5e9,stroke:#388e3c,color:#000

    도구 이름은 mcp__서버명__도구명으로 허용 목록에 적습니다. 서버에 도구를 등록했다고 자동 실행이 허용되는 건 아닙니다.

    ▲ 교재 슬라이드 30 — 에러 규약

    직접 해보기¶

    랩의 notes-agent.mjs는 배열에 든 세 줄을 조회합니다. 첫 질문과 정책 질문을 실제로 실행했습니다.

    $ node notes-agent.mjs
노트에서 찾은 내용은 다음과 같습니다.

**7월 회식**: 7월 24일(목) 19시, 장소는 을지로 골뱅이집
--- turns=5

$ node notes-agent.mjs '금요일에 배포해도 돼?'
사내 노트에 따르면 안 됩니다.

- 배포 원칙: **금요일 오후에는 프로덕션 배포를 하지 않는다**
--- turns=4

    도구 호출이 한 번뿐인데도 turns가 5·4로 나온 이유로 가장 유력한 건 SDK가 기본으로 켜 두는 Tool Search입니다 — 도구 스키마를 필요한 시점에 나중에 불러오면서 결과에 ToolSearch 호출이 섞여 들어갈 수 있습니다(공식 문서는 "포함될 수 있다"고만 밝히고 항상 그렇다고 단정하지는 않습니다). 도구를 하나만 등록해도 이 현상이 나타날 수 있습니다.

    첫 답은 "다음 회식"이라는 현재성까지 스스로 단서를 달았습니다. 이 랩의 데이터는 과거 7월 일정이므로 도구 결과가 있다고 해서 질문의 모든 전제가 참이 되는 건 아닙니다. 도구가 제공한 사실과 모델의 해석은 분리해서 읽어야 합니다.

    현장 메모

    in-process 도구는 서비스 내부 API나 읽기 전용 정책 조회에 잘 맞습니다. 네트워크 경계가 없으므로 인증·타임아웃·감사 로그의 책임도 앱 프로세스에 남습니다. 외부 시스템까지 확장할 때는 함수에 주는 권한을 최소화합니다.

    흔한 오해 바로잡기¶

    "도구 함수에서 예외가 나면 그 순간 전체 요청이 실패한다" — 아닙니다. in-process MCP 서버가 처리 안 된 예외를 붙잡아 에러 결과로 바꾸고 모델은 그 메시지를 읽은 뒤 루프를 계속합니다. throw와 isError: true 반환의 차이는 "성공이냐 실패냐"가 아니라 "모델이 읽을 오류 문구를 누가 정하느냐"입니다.

    "도구 하나만 등록하면 turns는 항상 1로 끝난다" — 아닙니다. 위 실습에서 도구 호출 한 번에 turns가 5·4로 나왔습니다. SDK가 기본으로 켜 두는 Tool Search가 도구 스키마를 나중에 불러오면서 결과에 ToolSearch 호출이 섞여 들어갈 수 있기 때문으로 보입니다(공식 문서는 이 턴이 항상 추가된다고 단정하지는 않습니다).

    정리¶

    커스텀 도구를 만든다고 모델에게 무제한 권한이 생기는 건 아닙니다. tool() 자체는 이름·설명·입력 스키마·핸들러 네 요소로 정의되고, 그 도구가 실제로 불리려면 서버 등록(createSdkMcpServer)과 허용 목록(allowedTools) 두 단계를 더 거쳐야 합니다. 정의했다고 곧바로 실행되는 게 아니라는 이 두 단계가 근거 기반 응답의 경계가 됩니다.
