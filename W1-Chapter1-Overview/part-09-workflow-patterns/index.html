    Part 9 — 워크플로 패턴¶

    한 줄 요약¶

    패턴은 조합입니다. EPC(Explore-Plan-Code)를 축으로 리뷰와 병렬화, 자동화를 얹고, 비용과 컨텍스트 규율로 지속 가능하게 만듭니다.

    왜 알아야 하나¶

    여기까지 왔으면 도구는 다 배웠습니다. 그런데 도구를 안다고 잘 쓰는 건 아닙니다. Part 9는 "검증된 사용 순서" 를 다룹니다. 10가지 패턴이 나오지만 관통하는 원리는 하나입니다.

    명세를 함께 준다 — 무엇이 완료인지 Claude가 스스로 확인할 수 있게 만든다.

    이게 모든 패턴의 공통점입니다.

    Pattern 1 — Explore-Plan-Code (EPC)¶

    가장 기본이 되는 3단계 리듬입니다. 큰 변경일수록 단계 분리의 효과가 큽니다.

    실전 예시 — OAuth 지원 추가¶

    $ claude

# E: 탐색
> src/auth를 읽고 세션 처리 방식을 정리해줘. 아직 코드는 만들지 마.

# P: 계획 (Shift+Tab 두 번)
> 이 구조에 OAuth 지원을 추가하는 계획을 세워줘
# → 계획 검토, 항목 수정 요청, 승인

# C: 구현
> 승인한 계획대로 구현하고 테스트까지 실행해줘

    이 예시에서 눈여겨볼 게 네 가지 있습니다.

    첫째, "아직 코드는 만들지 마" 라고 명시했습니다. 탐색 단계임을 선언하지 않으면 Claude는 이해했다고 판단하는 순간 바로 고치기 시작합니다.

    둘째, 계획은 수정할 수 있습니다. 나온 계획을 그대로 승인하거나 거절하는 두 선택지만 있는 게 아닙니다. 항목을 빼거나 순서를 바꿔서 승인할 수 있습니다.

    셋째, opusplan alias를 쓰면 계획과 실행에 다른 모델이 자동 배분됩니다.

    넷째, 마지막 지시에 "테스트까지 실행해줘" 가 들어 있습니다. "구현 완료"의 기준에 검증을 포함시킨 겁니다. 이게 빠지면 "코드는 썼는데 돌아가는지는 모르는" 상태로 끝납니다.

    Pattern 2 — TDD Workflow¶

    실패하는 테스트가 곧 명세입니다.

    > validateCoupon 함수를 TDD로 만들자.
  1) 먼저 실패하는 테스트 작성:
     만료 쿠폰 거부, 중복 사용 거부, 정상 쿠폰 할인율 반환
  2) 테스트 실행해서 실패 확인
  3) 통과할 최소 구현 작성
  4) 재실행으로 전부 통과 확인 후 리팩토링

    네 단계 각각에 이유가 있습니다.

    실패를 먼저 확인(Red) 하는 이유는 테스트가 진짜로 그 동작을 검사하는지 증명하기 위해서입니다. 처음부터 통과하는 테스트는 아무것도 검증하지 않는 테스트일 수 있습니다.

    테스트가 곧 명세입니다. "만료 쿠폰은 거부", "중복 사용은 거부", "정상 쿠폰은 할인율 반환" — 이 세 문장이 요구사항 그 자체입니다. 자연어로 길게 설명하는 것보다 정확합니다.

    최소 구현을 요구하는 건 과설계를 막기 위해서입니다. 통과에 필요한 것만 만들게 하면 쓰지도 않을 추상화가 생기지 않습니다.

    리팩토링은 통과 후(Green) 에 합니다. 안전망이 확보된 상태에서 정리해야 뭘 깨뜨렸는지 즉시 압니다.

    왜 TDD가 AI 에이전트와 특히 잘 맞는가

    일반적인 코딩 요청에서는 "다 됐습니다"의 판정을 결국 사람이 해야 합니다. 코드를 읽어보고 맞는지 확인해야 하죠. 그런데 기대 출력을 테스트로 주면, 판정 주체가 사람에서 테스트로 넘어갑니다. Claude는 mock 데이터가 아니라 실제 실행 결과로 스스로 검증하고, 통과할 때까지 반복합니다. Part 10의 Lab 3이 정확히 이 구조였습니다. 실패하는 테스트를 주고 "테스트 파일은 명세이므로 수정하지 마"라고 못박자, 4/4 통과까지 스스로 밀고 갔습니다.

    Pattern 3 — Code Review¶

    /code-review 명령 계열입니다. 머지 전 로컬 게이트로 습관화하세요.

    > /code-review              # 현재 diff 리뷰
> /code-review high         # 노력 수준 지정
> /code-review --fix        # 발견 사항 자동 수정
> /code-review --comment    # PR 인라인 코멘트 게시
> /code-review ultra        # 클라우드 멀티에이전트 심층 리뷰

> /simplify                 # 버그 탐색 없이 정리만
> /security-review          # 보안 관점 읽기 전용 검사

    Pattern 4 — Multi-Agent와 /batch¶

    큰 변경을 병렬 단위로 쪼갭니다.

    # 곁가지 위임
> /fork 이 변경의 문서 업데이트를 맡아줘

# 대규모 분할 실행
> /batch src/ 전체를 Solid에서 React로 마이그레이션

    /batch의 동작: 1. 코드베이스를 조사해 5~30개 독립 단위로 분해 2. 계획 승인 후 단위별 서브에이전트 생성 3. 각자 격리된 git worktree에서 구현과 테스트 4. 단위별 PR 오픈

    > /tasks     # 백그라운드 작업 현황 확인

    단위별로 PR이 나오므로 리뷰 가능한 크기로 산출물이 유지됩니다. (설계 심화는 2주차 Chapter 2)

    Pattern 5 — Visual Workflow¶

    스크린샷이 명세가 되는 흐름입니다.

    > (디자인 시안 이미지 붙여넣기)
  이 시안대로 ProfileCard 컴포넌트를 구현해줘.
  구현 후 스토리북 스크린샷과 시안을 비교해서 다른 부분을 스스로 찾아 고쳐줘.

    프론트엔드 검증 강화: 

    > /chrome 연결 후:
> localhost:3000/profile 열어서 콘솔 에러 확인,
  버튼 클릭했을 때 모달 동작도 검증해줘

    여기서도 원리는 같습니다. 시안이 곧 명세이고, 결과와 시안을 스스로 대조하게 만드는 것이 핵심입니다.

    Pattern 6 — Headless 자동화¶

    -p 플래그로 스크립트에 편입합니다.

    # 기본형
claude -p "package.json에서 outdated 의존성 요약"

# 파이프와 리다이렉트
tail -200 app.log | claude -p "이상 징후 보고"
claude -p "이 저장소 의존성 분석" > deps-report.md

# 도구 제한으로 안전한 무인 실행
claude -p "보안 이슈 스캔" \
  --allowed-tools "Read,Grep,Glob" \
  --permission-mode plan

# 비용 절감
claude -p "간단 분류 작업" --model haiku

    Warning

    무인 실행의 안전선은 --allowed-tools입니다. 사람이 승인할 수 없는 환경이므로, 부작용 있는 도구를 아예 목록에서 빼는 게 정석입니다. Read,Grep,Glob만 허용하면 무엇도 망가뜨릴 수 없습니다.

    Pattern 7 — Pipeline과 JSON 출력¶

    구조화 출력으로 후처리합니다.

    claude -p "현재 디렉토리 스택 분석" \
  --output-format json | jq '.result'

    응답 JSON에는 최종 답변만 들어 있는 게 아닙니다. 후처리에 쓸 메타데이터가 함께 옵니다.

    result가 최종 응답 텍스트이고, modelUsage에 실제로 어떤 모델이 쓰였는지, usage에 토큰 사용량과 비용 근거가 들어옵니다. 그리고 session_id가 있어서 이 세션을 나중에 --resume으로 이어붙일 수 있습니다.

    # 실시간 이벤트 스트림
claude -p "..." --output-format stream-json
# 이벤트 단위 파싱으로 진행 표시 구현

    Tip

    session_id를 받아두면 체인 실행이 가능합니다. 1단계 결과를 보고 2단계를 같은 세션으로 이어붙이는 파이프라인을 짤 수 있습니다.

    Pattern 8 — CI 통합¶

    .github/workflows/claude-review.yml 최소 예시:

    on: [pull_request]
jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: curl -fsSL https://claude.ai/install.sh | bash
      - run: |
          claude -p "이 PR의 diff를 리뷰하고 위험을 보고" \
            --allowed-tools "Read,Grep,Glob,Bash(git diff:*)"
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
    • 공식 액션도 제공됩니다
    • 키는 반드시 시크릿으로 주입
    • CI에서는 읽기 위주 도구로 제한
    • (패턴 심화는 5주차 Chapter 5)

    Pattern 9 — Routines 예약 실행¶

    머신이 꺼져도 도는 자동화입니다.

    > /schedule
# Routine 생성 흐름 시작
# 예: 평일 09:00, 열린 PR 리뷰 상태 요약을 Slack #dev 채널로 보고

    Routines 특성: - Anthropic 관리 인프라에서 실행 - 스케줄 외에 API 호출, GitHub 이벤트 트리거 가능 - 웹과 Desktop 앱에서도 생성·관리

    세션 내 반복은 /loop (내 머신이 켜져 있어야 함): 

    > /loop 10m CI 상태 확인하고 실패하면 원인 요약

    Pattern 10 — /goal 지속 실행¶

    조건이 참이 될 때까지 계속 작업합니다.

    > /goal 전체 테스트 스위트가 통과하고 lint 경고가 0이 될 때

    동작: - Claude가 턴을 넘겨도 목표 달성까지 계속 작업 - 각 턴 종료 시 조건 충족 여부를 스스로 점검

    > /goal            # 현재 목표 확인
> /goal clear      # 목표 조기 해제

    Fable 5와 조합하면 장시간 자율 작업에 최적입니다.

    비용 관리 전략 — 3개의 레버¶

    비용을 줄이려면 먼저 비용이 무엇으로 결정되는지 알아야 합니다. 공식은 이렇습니다.

    비용 = 모델 선택 × 컨텍스트 크기 × 캐시 적중

    세 개가 곱해지므로, 하나만 잡아도 효과가 크고 셋을 다 잡으면 배수로 줄어듭니다.

    flowchart TD
    C["<b>비용</b>"]
    C --- M["<b>① 모델 레버</b><br/>작업 난이도별 배분<br/><br/>일상은 sonnet<br/>난제만 opus<br/>배치는 haiku"]
    C --- X["<b>② 컨텍스트 레버</b><br/>윈도우를 가볍게<br/><br/>/clear · /compact<br/>경로 스코프 rules<br/>MCP 다이어트"]

    모델 레버는 가장 직관적입니다. 모든 작업을 opus로 돌리면 당연히 비쌉니다. 일상 작업은 sonnet, 정말 어려운 것만 opus, 단순 배치는 haiku로 나눕니다.

    컨텍스트 레버는 윈도우에 뭐가 들어있느냐의 문제입니다. 작업 경계마다 /clear하고, 같은 작업이 길어지면 /compact하고, 경로 스코프 rules로 필요할 때만 규칙이 로드되게 합니다. 안 쓰는 MCP 서버를 끄는 것도 여기 해당합니다.

    캐시 레버가 가장 의외이고, 그래서 가장 자주 놓칩니다.

    세션 중간에 모델을 계속 바꾸거나 CLAUDE.md를 수정하면 오히려 비용이 올라갑니다

    프롬프트 캐시가 무효화되기 때문입니다. 캐시가 살아 있으면 매번 보내는 시스템 지침과 프로젝트 문서를 다시 계산하지 않아도 되는데, 앞부분이 하나라도 바뀌면 전체를 다시 계산합니다.

    Part 10의 실측에서 이걸 숫자로 확인했습니다. 실제 입력 토큰은 4개였는데 캐시에서 읽은 토큰이 48,286개였습니다. 입력의 99.99%가 캐시였다는 뜻이고, 뒤집으면 그 48,286 토큰이 통째로 재계산될 수 있다는 뜻이기도 합니다.

    ▲ 교재 슬라이드 164 — 비용 관리: 모델·컨텍스트·캐시 3축

    컨텍스트 관리 전략¶

    비용만의 문제가 아닙니다. 컨텍스트가 지저분해지면 답변 품질이 떨어집니다. 관련 없는 과거 대화가 판단을 흐리기 때문입니다. 그래서 작업 경계마다 정리하는 습관이 긴 세션의 품질을 지킵니다.

    실전 규칙은 다섯 개입니다.

    작업을 전환할 때는 /clear 합니다. 이름을 붙여두면 나중에 /resume으로 찾기 쉽습니다.

    같은 작업이 길어지면 /compact 합니다. 이때 "무엇에 집중해서 요약할지" 초점을 함께 주면 중요한 게 살아남습니다.

    곁가지 질문은 /btw 로 던집니다. 본 작업 컨텍스트를 오염시키지 않습니다.

    탐색성 작업은 서브에이전트로 격리합니다. 파일 50개를 훑는 작업의 출력이 메인 대화에 쌓이면 곧바로 한계에 부딪힙니다. 위임하면 요약만 돌아옵니다.

    주기적으로 /context 로 상태를 봅니다. 무엇이 자리를 많이 먹는지 눈으로 확인하는 습관입니다.

    사라질 것과 남을 것을 구분하기¶

    여기에 더 근본적인 원칙이 하나 있습니다. Part 2에서 본 것처럼 대화 초반의 지시는 compaction 과정에서 소실될 수 있습니다.

    그래서 "이건 세션 내내 지켜져야 한다" 싶은 건 대화에 두면 안 됩니다. 성격에 따라 갈 곳이 다릅니다.

    • 영속 규칙 → CLAUDE.md
    • 경로 한정 지식 → .claude/rules/의 paths: 스코프 규칙
    • 반복되는 다단계 절차 → skill로 승격
    • 요약 시 보존할 지침 → Compact Instructions 섹션

    한 줄로 줄이면 이렇습니다. 대화는 휘발되고, 파일은 남습니다.

    토큰 효율 베스트 프랙티스¶

    같은 결과를 더 적은 토큰으로 얻는 요령이 넷 있습니다. 토큰이 들어가는 쪽과 나오는 쪽 양쪽을 줄이는 게 요점입니다.

    입력을 줄이려면 경로를 지목합니다. "결제 관련 버그 고쳐줘"보다 "src/payments/ 토큰 갱신부터 봐줘"가 훨씬 쌉니다. 저장소 전체를 훑을 필요가 없어지기 때문입니다.

    출력을 줄이려면 형식을 지정합니다. "표로 정리해줘", "다섯 줄로" 같은 지시가 응답 길이를 직접 통제합니다. Part 10의 모델 비교 실측에서 haiku가 "한 문장으로"라는 지시를 덜 지켜 출력 토큰을 2.4배 더 쓴 사례를 확인했습니다.

    MCP를 다이어트합니다. 안 쓰는 서버는 해제하고 /mcp로 서버별 컨텍스트 비용을 점검합니다.

    메모리를 다이어트합니다. CLAUDE.md를 200줄 이하로 유지하고, 특정 경로에서만 필요한 규칙은 rules의 paths: 스코프로 분리합니다.

    자주 마주치는 안티 패턴¶

    마지막으로 자주 보는 비효율 다섯 가지입니다. 각각 신호와 교정이 짝을 이룹니다.

    • 한 세션에 서로 다른 작업을 뒤섞는 것 — 결제 모듈을 고치다가 배포 스크립트로 넘어가고 다시 문서를 고칩니다. 컨텍스트가 뒤엉켜 엉뚱한 판단이 나옵니다. 작업 경계마다 /clear하세요.

    • 거대 파일을 통째로 붙여넣는 것 — Claude는 파일을 직접 읽을 수 있습니다. 붙여넣지 말고 경로를 지목하고, 필요하면 라인 범위를 알려주세요.

    • 검증 기준 없는 막연한 지시 — "잘 고쳐줘"에는 완료 판정 기준이 없습니다. 테스트나 기대 출력을 함께 주세요.

    • 실패한 방향을 수동으로 재타이핑하며 반복하는 것 — 잘못 간 걸 알았으면 그 지점으로 /rewind한 뒤 다시 지시하는 게 빠릅니다. 잘못된 시도가 컨텍스트에 남아 있으면 계속 영향을 줍니다.

    • 모든 작업을 opus로 돌리는 것 — 난이도별로 배분하세요. 단순 분류에 최상위 모델을 쓰는 건 낭비입니다.

    직접 해보기 — 실제 실행 기록¶

    2026-08-02, Claude Code 2.1.220 환경에서 직접 실행. (전체 기록: Part 10 / Lab 5)

    ① Headless 파이프 — 로그 분석이 정말 한 줄로 되는가¶

    5줄짜리 샘플 로그를 파이프로 넣었습니다.

    $ cat /tmp/ccw-sample.log | claude -p "이상 징후가 있으면 원인 후보와 함께 3줄로 보고"

    응답 (발췌):

    1. 징후: 10:01:11부터 /api/pay만 status=500 + 응답시간 3.0초대(정상 경로 12~15ms의 200배)로 급증, 동시에 UnhandledPromiseRejection 발생 후 8초 뒤 DB 풀 고갈(active=20 idle=0).
    2. 원인 후보: (a) 결제 경로의 외부 PG 호출 3초 타임아웃 → 예외가 catch되지 않아 커넥션 release() 누락 = 커넥션 릭, (b) 그로 인한 풀 고갈이 대기·지연을 증폭시키는 연쇄 장애, © 부차적으로 풀 max=20이 결제 트래픽 대비 과소.
    3. 다음 확인: ... 릭이면 재시작으로 잠깐 회복 후 재발하므로 그 패턴으로 (a)와 ©를 구분할 수 있음.

    Tip

    원인 후보를 나열하는 데 그치지 않고 감별 진단 방법까지 제시한 게 인상적이었습니다. 온콜 상황에서 실제로 쓸 수 있는 수준입니다.

    ② JSON 출력 — 문서에 없던 필드가 더 많았다¶

    $ claude -p "..." --allowed-tools "Bash(find:*),Glob" --output-format json > out.json
$ jq -r '.result' out.json
562

    응답 JSON의 최상위 키 전체:

  "total_cost_usd": 0.109508,
  "duration_ms": 3898,

    직접 해보고 알게 된 것 두 가지

    1. total_cost_usd가 응답에 그대로 들어있습니다. 별도 계측 없이 CI에서 비용 상한 가드를 걸 수 있습니다. ttft_ms(첫 토큰까지 시간), num_turns, permission_denials도 문서 표에는 없던 필드입니다.
    2. inputTokens: 4 vs cacheReadInputTokens: 48286 — 입력의 99.99%가 캐시에서 읽혔습니다. 위 "3개의 레버"에서 캐시를 모델·컨텍스트와 나란히 놓은 이유가 숫자로 보입니다. 세션 중 CLAUDE.md를 고치면 이 48,286 토큰이 통째로 캐시 미스가 됩니다.

    ③ 모델 레버 검증 — 완전히 같은 프롬프트, 모델만 교체¶

    $ for M in haiku sonnet; do
    claude -p "src/checkout.js가 무슨 일을 하는지 한 문장으로" \
      --model $M --allowed-tools "Read" --output-format json
  done
    모델 비용 입력 토큰 출력 토큰 소요
    haiku $0.0264 18 407 7,402ms
    sonnet $0.1011 4 168 5,890ms

    약 3.8배 차이가 났지만, 단순히 '싼 모델이 이득'은 아니었습니다

    haiku가 출력 토큰을 2.4배 더 많이 썼고 시간도 1.3배 더 걸렸습니다. "한 문장으로"라고 했는데 더 장황하게 답한 것입니다. 즉 위에서 "난이도별 배분"이라고 쓴 표현이 정확합니다. 작업이 단순할수록 이득이 커지고, 지시 준수가 중요한 작업에서는 오히려 손해일 수 있습니다.

    ④ 무인 실행 안전선 — 화이트리스트가 실제로 막는지¶

    --allowed-tools "Read,Grep,Glob" 상태로 파일 수정을 시켰더니 Edit가 차단됐고 git status는 깨끗했습니다. permission_denials에 시도하려던 tool_input이 통째로 기록됩니다 → 그대로 감사 로그로 활용 가능. (상세: Part 6)

    정리¶

    • 기본 리듬은 Explore → Plan → Code. 큰 변경일수록 단계 분리 효과가 큽니다.
    • 품질은 TDD와 /code-review 계열로 확보합니다.
    • 확장은 /fork, /batch, Routines, /goal 로 합니다.
    • 규율은 /usage, /clear, /compact 로 유지합니다.
    • 모든 패턴의 공통점은 "명세 동봉" 입니다 — 무엇이 완료인지 스스로 확인할 수 있게 만드세요.
    • 무인 실행(headless/CI)의 안전선은 --allowed-tools 화이트리스트입니다.
