    Part 7 — Commands와 Skills¶

    한 줄 요약¶

    Command는 반복되는 정형 프롬프트를 Markdown 한 장으로 굳힌 것이고 공식문서 기준으로 Skill은 별개 시스템이 아니라 같은 메커니즘을 폴더 단위로 확장한 형태입니다.

    왜 알아야 하나¶

    지금까지 CLAUDE.md(1주차), Subagent(2주차), Hook(Part 3·4), MCP(Part 5·6)를 다뤘습니다. 이 파트가 다루는 Command와 Skill까지 더하면 "반복 작업을 어떤 수단으로 굳힐까"의 선택지가 여섯 가지가 됩니다. 이 파트의 목적은 각 수단의 한 줄 판별법을 잡아 새 요구가 생겼을 때 바로 답할 수 있게 하는 것입니다.

    1. 커스텀 명령 기본 — Markdown 한 장이 슬래시 명령¶

    .claude/commands/summarize.md 같은 파일 하나가 그대로 /summarize 명령이 됩니다. 파일명이 곧 명령 이름이고 하위 폴더는 네임스페이스로 쓰여 /dir:name 형태로 호출됩니다. 저장 위치는 두 곳입니다. 프로젝트 전체가 공유하는 .claude/commands/와 나만 쓰는 ~/.claude/commands/. Part 1의 라이브 리로드 덕에 파일을 저장하면 바로 반영됩니다.

    2. 핵심 발견 — Command와 Skill은 사실 같은 메커니즘¶

    공식문서(code.claude.com/docs/en/skills)는 이렇게 명시합니다: "Custom commands have been merged into skills." .claude/commands/deploy.md 파일과 .claude/skills/deploy/SKILL.md 파일은 둘 다 /deploy를 만들고 동일하게 동작합니다. Command가 Skill과 별개의 시스템이 아니라 폴더 없이 파일 하나로만 존재하는 더 단순한 형태의 Skill에 가깝다는 뜻입니다.

    실제로 Lab 4에서 standup Command를 Skill로 옮겨봤을 때 정확히 이걸 확인했습니다.

    Command 버전 (파일 하나):
.claude/commands/standup.md

Skill 버전 (폴더 + 파일 여러 개):
.claude/skills/standup/
  SKILL.md         # 지시문(Command 파일과 거의 같은 내용)
  checklist.md     # 새로 추가한 동봉 파일

    SKILL.md에 "checklist.md도 같이 확인해라"라고 써두자 Claude가 SKILL.md뿐 아니라 같은 폴더의 checklist.md까지 읽어서 실제 응답에 그 내용을 반영했습니다(아래 직접 해보기에 로그가 있습니다). Skill이 Command에 실질적으로 더하는 건 폴더 단위로 체크리스트·스크립트 같은 자산을 동봉할 수 있다는 것, 그리고 파일 하나로는 표현하기 번거로운 고급 옵션(context: fork 등)을 붙일 수 있다는 것입니다. 기존 .claude/commands/ 파일은 그대로 계속 작동하고 name·paths를 제외한 동일한 frontmatter를 지원합니다.

    Warning

    라이브 리로드에 예외가 하나 있습니다. 이미 감시 중인 .claude/skills/ 안에서 파일을 추가·수정하는 건 즉시 반영되지만 프로젝트에 .claude/skills/ 디렉터리 자체를 처음 만드는 경우는 세션이 그 디렉터리를 아직 감시하지 않아 한 번 재시작해야 인식됩니다.

    3. 여섯 가지 확장 수단 — 이제 비교할 수 있습니다¶

    Command/Skill의 관계를 알았으니 이제 지금까지 배운 확장 수단 전체를 한 줄씩 비교할 수 있습니다.

    • CLAUDE.md — 항상 알아야 할 프로젝트 지식. 상시 컨텍스트로 살아 있습니다(1주차).
    • Command/Skill — 반복 작업의 정형 절차. 같은 메커니즘을 파일 하나로 쓸지 폴더+자산으로 쓸지의 선택입니다(방금 배운 것).
    • Subagent — 컨텍스트가 격리된 전담 워커에게 위임 실행시킵니다(2주차).
    • Hook — 수명주기 이벤트에 자동으로 반응합니다(Part 3·4).
    • MCP — 외부 시스템 연결로 도구를 확장합니다(Part 5·6).
    • Plugin — 위 전부를 묶어 배포하는 유통 단위입니다.

    2주차와 다른 관점의 트리라는 점에 유의

    2주차 part-03도 "여러 수단 중 하나를 고른다"는 트리를 다뤘지만 그건 "작업을 어떻게 병렬화할까"(서브에이전트 vs 직접 처리)라는 관점이었습니다. 이 파트의 트리는 "반복 절차를 어떤 형태로 굳힐까"라는 다른 질문에 답합니다.

    4. 인자 받기 — $ARGUMENTS와 위치 인자¶

    명령 본문에서 $ARGUMENTS는 호출 시 넘긴 전체 문자열을 가리킵니다. 개별 인자는 $ARGUMENTS[N](0부터 시작하는 인덱스)으로 꺼내거나 그 축약형인 $N을 씁니다. 즉 $0이 첫 번째 인자, $1이 두 번째 인자입니다.

    ---
description: 이슈 번호로 수정 착수
argument-hint: "<이슈번호> [우선순위]"
---
이슈 #$0 을 조사해 수정하라.
우선순위는 $1, 전체 지시: $ARGUMENTS

    직접 해보고 알게 된 것 — 실측에서는 옛 1-based 관례가 나왔다

    Lab 4에서는 .claude/commands/standup.md(기존 방식 Command 파일)에 $1을 써서 /standup Jade를 호출했는데, 인자 하나(Jade)뿐이었는데도 $1에 정확히 채워졌습니다. 이건 공식문서가 설명하는 0-based 규칙($1은 원래 두 번째 인자여야 함)과 안 맞습니다. 정확한 원인까지는 확인하지 못했는데, 레거시 .claude/commands/ 파일에 남아있는 예전 1-based 호환 동작일 가능성이 있습니다. 새로 Skill을 작성한다면 공식문서 기준인 $0/$ARGUMENTS[0]을 쓰고 기존 Command 파일의 $1 동작은 직접 한 번 테스트해서 확인하는 걸 권합니다.

    5. frontmatter 옵션 — 세 그룹으로 묶어서¶

    명령 하나에 붙일 수 있는 메타데이터는 세 그룹으로 나눠보면 쉽습니다.

    • 입력 관련 — argument-hint(자동완성 힌트), description(명령 목록과 모델의 자동 호출 판단에 쓰임, 항상 채우는 습관 필요)
    • 권한 관련 — allowed-tools(이 명령 실행 중 쓸 수 있는 도구를 최소 권한 원칙으로 제한), disable-model-invocation(모델이 자동으로 못 부르게 막아 사용자가 명시적으로 호출할 때만 실행)
    • 실행 관련 — model(전용 모델 지정, 무거운 분석엔 opus), hooks(활성화된 동안만 유효한 훅, once 옵션으로 세션당 1회 제한 가능)

    6. 컨텍스트 수집 — !실행과 @참조¶

    명령 본문 안에 !`백틱`으로 감싼 셸 명령을 넣으면 실행 시점에 평가되어 그 결과가 그대로 삽입되고 @경로는 파일을 컨텍스트에 첨부합니다.

    ---
description: PR 컨텍스트를 모아 리뷰 준비
allowed-tools: Bash(git *), Read
---
## 현재 상태
- 브랜치: !`git branch --show-current`
- 변경: !`git diff --stat main...HEAD`

## 기준 문서
@docs/review-checklist.md

위를 바탕으로 리뷰 관점 5가지를 제시하라.

    두 방식 다 "항상 최신 상태"를 보장하는 게 핵심입니다. 명령을 저장해둔 시점의 값이 아니라 호출하는 순간의 브랜치·diff·파일 내용을 가져옵니다. 실제로 Lab 4에서 !git log --oneline -5` 를 넣었을 때 호출 시점의 실제 커밋 목록이 정확히 반영됐습니다. 조직은disableSkillShellExecution` 같은 키로 이 인라인 실행 자체를 차단할 수 있습니다.

    7. 스킬 고급 옵션 (필요할 때 참고)¶

    context: fork를 Skill에 걸면 무거운 절차를 별도의 격리된 컨텍스트에서 실행한 뒤 요약만 본 세션으로 가져옵니다. 본 세션의 대화 기록은 안 가져가고 끝나면 요약만 돌아오는 구조라 무거운 절차 때문에 본진 컨텍스트가 오염되는 걸 막고 싶을 때 씁니다. 이 밖에 allowed-tools(명령과 마찬가지로 활성화된 동안 도구 제한), disable-model-invocation(위험한 절차를 명시적 호출 전용으로), 기본 동봉된 번들 스킬을 끄는 disableBundledSkills 정도만 알아두면 됩니다. 스킬을 플러그인으로 묶으면 마켓이나 팀 배포 경로를 탈 수 있습니다.

    9. 실전 명령과 성장 경로 (요약)¶

    교재는 두 가지 실전 예시를 듭니다. PR 리뷰 명령은 !git diff`로 변경사항을 수집하고 2주차 서브에이전트(code-reviewer)에게 판정을 위임한 뒤 머지 가능 여부를 마지막 줄에 출력하도록 압축한 예시입니다. **배포 점검 명령**은disable-model-invocation: true의 전형적인 용례입니다. 배포처럼 되돌리기 어려운 작업은 모델이 스스로 판단해 실행하면 안 되니 사용자가/deploy`로 명시 호출했을 때만, 체크리스트를 통과한 경우에 한해 배포 명령을 제시(직접 실행이 아니라)하도록 설계돼 있습니다.

    명령 자산의 성장 경로도 코드와 비슷합니다. 개인(~/.claude/commands)에서 검증을 거쳐 → 프로젝트(커밋해서 공유)로 승격하고 → 여러 저장소에서 공통으로 쓰게 되면 플러그인으로 묶어 배포합니다.

    직접 해보기 — Lab 4: 커스텀 명령을 헤드리스에서 호출¶

    교재가 명령·인자·인라인 컨텍스트 수집을 설명하지만, 이게 대화형 세션 전용 UI 기능인지 -p 헤드리스에서도 그대로 작동하는지는 명시하지 않습니다. 직접 확인했습니다.

    <!-- .claude/commands/standup.md -->
---
description: 최근 커밋을 바탕으로 스탠드업 요약 작성
argument-hint: "<이름>"
---
git log --oneline -5 결과를 바탕으로 $1 의 스탠드업 보고를 세 줄로 작성하라.

최근 커밋:
!`git log --oneline -5`

    $ claude -p "/standup Jade" --output-format json
{..., "result":"Jade의 스탠드업 보고:\n\n- 프로젝트 초기 설정(init) 완료\n
- lab4 관련 초기 세팅 작업 진행\n- 다음 작업 항목은 커밋 로그에 아직 반영되지 않음"}

    $1이 "Jade"로 정확히 치환됐고 결과에 언급된 "init"과 "lab4 관련 초기 세팅"은 실제 스크래치 저장소의 커밋 두 개(init, lab4 setup)와 정확히 일치합니다. !git log --oneline -5`` 인라인 실행이 호출 시점에 평가되어 컨텍스트에 들어간 것도 함께 확인된 셈입니다.

    직접 해보고 알게 된 것 — 명령·인자·인라인 실행 전부 헤드리스와 무관하게 작동한다

    Part 3의 Lab 2(훅)에서 확인한 패턴과 정확히 같은 결론입니다. -p가 건너뛰는 건 "사람에게 물어보는" 절차뿐이고, 명령 파일을 슬래시로 호출하고 인자를 치환하고 인라인 셸 결과를 끼워 넣는 메커니즘 자체는 대화형 세션과 동일하게 동작합니다.

    이어서 이 명령을 실제로 Skill로 승격시켜봤습니다. .claude/commands/standup.md를 지우고 .claude/skills/standup/SKILL.md + checklist.md(어제 완료·오늘 할 일·블로커 세 항목)로 옮긴 뒤 똑같이 헤드리스로 호출했습니다.

    $ claude -p "/standup Jade" --output-format json
{..., "result":"Jade의 스탠드업 보고 (2026-08-23):\n\n
- 어제: `a87f415 lab4 setup`, `e7c58ad init` 커밋으로 lab4 초기 설정과 프로젝트 초기화를 완료함.\n
- 오늘: lab4 설정 위에서 다음 작업 항목을 구체화하고 진행할 예정.\n
- 블로커: 현재 없음."}

    Command 시절과 똑같이 $1·!실행`이 그대로 작동했습니다. 결과의 "블로커" 항목은 명령 본문이 아니라 새로 추가한checklist.md에만 있던 문구라, 이 파일이 실제로 읽혀 반영됐다는 것도 확인됩니다..claude/skills/디렉터리를 이 프로젝트에 처음 만들었는데도 재시작 없이 바로 작동했습니다. 이건 공식문서가 말하는 "이미 떠 있는 세션 도중에 새 스킬 디렉터리를 만들면 재시작이 필요하다"는 경고와 모순되지 않습니다.-p` 헤드리스는 호출마다 새 프로세스로 시작하므로 디렉터리는 그 세션이 뜨기 전에 이미 존재했던 셈입니다.

    흔한 오해 바로잡기¶

    "슬래시 명령은 대화형 세션에서만 쓸 수 있다" — 아닙니다. claude -p "/명령이름 인자" 형태로 헤드리스에서도 그대로 호출되고 $1/$ARGUMENTS 치환과 !실행`/@참조`도 동일하게 작동합니다.

    "Command와 Skill은 서로 다른 두 시스템이다" — 공식문서 기준으로는 같은 메커니즘입니다. Skill이 폴더와 고급 옵션을 추가로 지원하는 확장판에 가깝습니다.

    정리¶

    Command는 짧은 정형 프롬프트를 파일명 하나로 굳힌 것이고 공식문서 기준으로 Skill은 별개 시스템이 아니라 같은 메커니즘에 동봉 자산과 고급 옵션을 더한 확장판입니다. 둘 다 $ARGUMENTS/$1 인자와 !실행/@참조컨텍스트 수집을 공유하고disable-model-invocation`으로 위험한 절차의 자동 발동을 막을 수 있습니다. Lab 4로 확인했듯 이 모든 메커니즘은 헤드리스 자동화에도 그대로 적용되므로 팀 명령 라이브러리를 CI 파이프라인에 재사용하는 데 별다른 제약이 없습니다. 다음 파트는 이 챕터 전체(설정·권한·훅·MCP·명령)가 한 프로젝트 안에서 어떻게 맞물리는지 통합 예시로 정리하고 진단 도구와 실습 전체 기록을 마무리합니다.
