    Part 1 — Settings 체계¶

    한 줄 요약¶

    Claude Code의 설정은 한 파일이 아니라 스코프가 다른 여러 파일이 계층적으로 겹쳐 적용되는 구조이고 값이 하나뿐인 키와 목록으로 된 키(특히 권한 규칙)는 충돌 시 처리 방식이 다릅니다.

    왜 알아야 하나¶

    2주차에서 서브에이전트의 도구 권한이 어디서 오는지, 3주차에서 조직이 managed settings로 무엇을 강제할 수 있는지를 다뤘습니다. 이번 주는 그 사이, 개인 개발자가 실제로 손대는 설정 파일들이 몇 개나 있고, 같은 값을 두 파일에 다르게 써 넣으면 무슨 일이 일어나는가를 다룹니다. 이 질문에 정확히 답하지 못하면 "왜 팀 표준으로 막아뒀는데 내 로컬에서는 다르게 동작하지", "분명 두 파일 다 손댔는데 왜 하나만 반영됐지" 같은 상황에서 원인을 못 찾고 헤매게 됩니다.

    1. 설정 파일은 다섯 곳에 있다¶

    Claude Code가 읽는 설정 파일은 실제로 다섯 군데입니다. 3주차에서 다룬 조직 관리형(managed) 계층이 맨 위에 있고 그 아래로 개인 개발자가 직접 만지는 네 곳이 이어집니다.

    • Managed — 서버 관리형 배포, macOS의 plist나 Windows 레지스트리, 또는 시스템 설정 파일. 조직 전체에 적용되며 3주차에서 이미 다뤘습니다.
    • User — ~/.claude/settings.json. 내 모든 프로젝트에 공통으로 적용되고 다른 사람과 공유되지 않습니다. 개인 취향(테마, 알림 방식 등)을 넣기 적합합니다.
    • Project — .claude/settings.json. 저장소에 커밋되어 협업자 전원에게 공유됩니다. 팀 표준을 넣는 곳입니다.
    • Local — .claude/settings.local.json. 같은 저장소 안에서 나만 쓰는 설정이고 관례상 .gitignore에 넣어 커밋하지 않습니다. 실험이나 개인 예외를 여기 둡니다.

    이 네 계층에 CLI 인자(claude --settings로 넘긴 값이나 개별 플래그)까지 더하면 실제 우선순위는 5단입니다: Managed → CLI 인자 → Local → Project → User 순으로 앞쪽이 이깁니다. 공식문서(code.claude.com/docs/en/settings)의 스코프 우선순위 설명도 정확히 이 순서를 명시해 교재와 공식문서가 일치합니다.

    2. 함정 하나 — 이 우선순위가 안 통하는 키가 있다¶

    앞의 우선순위는 defaultMode처럼 값이 하나뿐인 키에는 그대로 맞습니다. 근데 permissions.allow나 deny처럼 목록(배열)으로 된 키는 다르게 동작합니다. 예시로 확인해보겠습니다.

    User 설정 파일:     { "permissions": { "allow": ["mkdir"] } }
Project 설정 파일:  { "permissions": { "allow": ["touch"] } }

    Project 파일엔 mkdir 얘기가 아예 없습니다. 그럼 mkdir 폴더명을 시켰을 때 Project가 이겨서 막힐까요? 아닙니다. 그냥 실행됩니다. 두 목록이 이어붙어서 최종적으로 ["mkdir", "touch"]가 되고 Claude Code는 이 합쳐진 목록 하나만 보고 판단하기 때문입니다.

    보통 설정값은 "위 스코프가 있으면 아래 값은 무시"가 맞는데(값을 하나만 담는 키가 이렇게 동작합니다), 권한 규칙 같은 목록 키만 예외적으로 "모든 스코프의 값이 다 합쳐진다"는 게 이 파트의 핵심입니다. 공식문서는 이를 "Lists merge instead of overriding"이라는 절로 명시하고 교재 슬라이드도 우선순위 5단 표에 "권한은 병합"이라고 별도로 각주를 달아 이 예외를 명시합니다.

    왜 이렇게 만들었을까요? defaultMode 같은 건 "한 가지 답만 있어야 하는 결정"이라 위가 이기는 게 자연스럽습니다. 근데 권한 규칙은 여러 사람이 각자 다른 이유로 하나씩 추가하는 것에 가깝습니다. 내(User)가 내 모든 프로젝트에서 mkdir을 믿고 허용해뒀는데, 이 프로젝트(Project)에 들어올 때마다 그게 통째로 무시된다면 매번 새로 허용해줘야 해서 번거롭습니다.

    더 심각한 경우도 있습니다. 회사가 managed 설정으로 위험한 명령을 deny 해뒀는데, 어떤 프로젝트 설정 파일이 그 규칙을 언급조차 안 했다는 이유로 덮어써져 사라진다면, 프로젝트 파일 하나 만들었을 뿐인데 회사의 안전장치가 조용히 없어지는 셈입니다. 그래서 권한 규칙만큼은 "누가 이기냐"가 아니라 각 단계가 추가한 규칙이 전부 쌓인다는 방식으로 설계되어 있습니다.

    Note

    여기서 자연스럽게 드는 의문 하나: 그럼 allow에 위험한 명령을 넣고 deny에도 같은 걸 넣으면 어떻게 될까요? deny가 무조건 이깁니다. 목록이 합쳐지는 것과는 별개로, "deny에 걸리면 allow가 뭐라고 하든 막는다"는 규칙이 항상 우선합니다. 이 평가 순서 자체는 Part 2에서 자세히 다룹니다.

    이 병합 규칙, 말로만 설명하고 끝내지 않고 실제로 확인해봤습니다 — 아래 직접 해보기에 실험 로그를 남겼습니다.

    3. 이 문서에 없는 것들 — 설정만 이 규칙을 따르는 건 아니다¶

    스코프 4계층·우선순위 5단은 Settings 자체(~/.claude/settings.json, .claude/settings(.local).json)에 적용되는 이야기이고 Claude Code가 관리하는 다른 구성 요소들은 저장 위치가 다릅니다. 깊게 다루지 않고 지도만 남겨둡니다.

    • MCP 서버 — User/Local 스코프는 ~/.claude.json에, Project 스코프는 저장소 루트의 .mcp.json에 따로 저장됩니다(Part 5에서 다룸).
    • Subagents — ~/.claude/agents/와 .claude/agents/에 저장되며, 2주차에서 이미 다룬 내용입니다.
    • CLAUDE.md — ~/.claude/, 프로젝트 루트, CLAUDE.local.md 세 곳에 나뉘어 있고 1주차에서 다뤘습니다.
    • ~/.claude.json — OAuth 세션·프로젝트별 상태·캐시가 들어 있는 파일로, 직접 편집은 권장되지 않습니다. Lab 1에서 워크스페이스 신뢰(trust) 상태를 확인하려고 이 파일을 들여다봤는데, 실제로 각 프로젝트 경로별 hasTrustDialogAccepted 값이 여기 저장돼 있었습니다.
    • 백업 — 설정 파일은 최근 5개까지 자동 백업되어 복구 안전망 역할을 합니다.

    ▲ 교재 슬라이드 6 — 기능별 파일 지도

    4. 설정을 고치면 언제 반영되는가¶

    settings.json 하나에는 $schema(에디터 자동완성용), permissions(Part 2 주제), env(환경변수 배포), companyAnnouncements(시작 배너) 등 여러 성격의 키가 함께 들어갑니다. 답부터 말하면, 대부분은 저장하는 순간 바로 반영되고 세션을 껐다 켤 필요가 없습니다. 설정 파일은 파일 시스템 워처로 감시되고 있어서 저장하면 곧바로 세션에 반영되고 ConfigChange 훅(Part 3)이 발화합니다.

    예외는 딱 셋입니다: model, effortLevel, outputStyle. 이 셋은 세션이 시작할 때 딱 한 번만 읽고 중간에 파일을 고쳐도 반영되지 않습니다. model은 /model 명령으로, effortLevel은 /effort 명령으로 바꿀 수 있지만 outputStyle은 이런 명령이 없어 /clear나 세션 재시작을 해야 다시 구성됩니다.

    ▲ 교재 슬라이드 12 — 라이브 리로드

    왜 이 세 개만 예외인가

    permissions, hooks, 환경변수 같은 건 "도구를 호출하는 바로 그 순간에 확인하면 되는 규칙"이라 매번 새로 읽어도 문제가 없습니다. 근데 model은 세션이 시작되자마자 이미 그 모델 기준으로 대화가 쌓이기 시작하고 outputStyle은 시작할 때 시스템 프롬프트 안에 이미 박혀 들어갑니다. 중간에 파일만 슬쩍 바꿔버리면 지금까지 쌓인 맥락과 어긋나는 이상한 상황이 되기 때문에, 이 셋은 "저장하면 바로 반영"이 아니라 명시적으로 전환하는 명령을 거치게 만들어둔 겁니다. 설정을 고치고 "왜 안 먹지" 싶을 때는 먼저 이 세 키에 해당하는지부터 의심하는 게 빠릅니다.

    5. 키 카탈로그 — 전체가 아니라 감을 잡는 정도로¶

    교재는 키를 성격별로 묶어 "모델과 사고"(alwaysThinkingEnabled, availableModels, model 등), "운영"(autoUpdatesChannel, autoCompactEnabled, cleanupPeriodDays 등), "끄기 스위치"(disableAllHooks, disableAutoMode, disableSideloadFlags 등 disable 패밀리) 세 그룹으로 소개합니다. 전체 키 개수는 100개를 훌쩍 넘기 때문에 이 문서에서 전수를 나열하는 대신, 공식 레퍼런스(code.claude.com/docs/en/settings-reference)에서 필요할 때 찾아 쓰는 습관을 들이는 편이 실용적입니다.

    6. managed-settings.d 드롭인 — 회사 정책을 조각내는 법¶

    3주차에서 managed settings가 조직 전체를 강제하는 최상위 계층이라는 건 다뤘습니다. 이번엔 그 계층 내부의 운영 디테일을 하나 더 봅니다.

    회사 정책 파일(managed-settings.json)을 관측팀·보안팀·플랫폼팀이 전부 하나로만 관리하면, 다들 같은 파일을 동시에 고쳐야 해서 충돌이 납니다. 그래서 파일을 여러 조각으로 쪼갤 수 있게 해주는 게 managed-settings.d/ 디렉터리입니다.

    managed-settings.json          # 기본판
managed-settings.d/
  10-telemetry.json             # 관측팀 조각
  20-security.json              # 보안팀 조각

    숫자 접두(10-, 20-) 순서대로 병합하는데, 값의 종류에 따라 합치는 방식이 다릅니다. 값이 하나뿐인 키는 이렇게 동작합니다.

    10-telemetry.json:  { "logLevel": "info" }
20-security.json:   { "logLevel": "debug" }
→ 최종 결과: "logLevel": "debug"   (숫자가 늦은 파일이 앞선 파일을 덮음)

    목록(배열) 키는 다릅니다.

    10-telemetry.json:  { "allowedHosts": ["metrics.corp.com"] }
20-security.json:   { "allowedHosts": ["audit.corp.com"] }
→ 최종 결과: "allowedHosts": ["metrics.corp.com", "audit.corp.com"]   (이어붙임)

    객체(중첩된 { })는 안쪽까지 파고들어 같은 규칙을 재귀적으로 적용합니다(깊은 병합). 이 세 규칙(단일 값 덮어쓰기·배열 이어붙이기·객체 깊은 병합)은 systemd의 드롭인 관례와 동일합니다.

    2절의 병합과 헷갈리지 마세요

    방금 본 규칙은 managed 계층 내부에서 조각 파일들끼리 합치는 규칙이고 2절에서 본 "User/Project/Local 사이의 배열 병합"은 서로 다른 스코프 사이의 규칙입니다. 이름은 비슷해 보여도 완전히 별개의 메커니즘입니다.

    managed 설정은 오타 하나가 조직 전체 정책을 무력화하면 안 되기 때문에 관용적으로 파싱됩니다. 무효 항목만 조용히 제거하고 나머지는 강제 유지하며 보안 관련 키는 실패 시 안전한 쪽(예: 무효 allowlist는 빈 목록)으로 fail-closed 됩니다. 반면 User/Project/Local 설정은 엄격하게 파싱되어 검증에 실패하면 그 파일 전체가 거부되고 시작 시 오류로 보고됩니다. 개인 설정 파일 맨 위에 $schema를 넣어두면 에디터가 저장 전에 오타를 미리 잡아주므로, 이 엄격한 파싱의 예방책으로 유용합니다.

    인프라 관점

    이 단일 값/배열/객체 병합 규칙은 Ansible의 group_vars/host_vars 계층이나 Kustomize의 overlay 병합과 정확히 같은 고민을 풉니다. 여러 팀이 같은 정책 파일을 동시에 건드리지 못하게 조각내면서도 합쳤을 때 예측 가능한 결과를 보장해야 하는 문제입니다. GPO(그룹 정책 개체)를 여러 OU에 나눠 적용해본 경험이 있다면 "나중 파일이 값을 덮는다"는 규칙이 낯설지 않을 것입니다.

    7. /config — 설정의 대화형 창구¶

    파일을 직접 여는 대신 /config로 탭 형태의 설정 UI를 열 수 있고 /config verbose=true처럼 키=값 형태로 붙이면 UI 없이 즉시 단일 키를 바꿀 수 있습니다(v2.1.181 이상). 자주 만지는 항목은 auto-compact, session recap, push 알림, thinking 기본값, 테마 정도입니다. 어느 스코프 파일에 저장되는지도 함께 표시되므로 "이 값이 지금 어느 파일에서 온 건지" 확인하는 용도로도 쓸 수 있습니다.

    직접 해보기 — Lab 1: 스코프 우선순위·병합 실측¶

    2절에서 개념으로 짚은 병합 규칙과 우선순위를 실제로도 확인했습니다. 격리된 스크래치 프로젝트(실제 계정의 ~/.claude/settings.json은 건드리지 않음)에서 세 가지를 확인했습니다.

    실험 1 — Project 공유 설정 vs Project Local 설정, 값 하나만 담는 키의 우선순위 .claude/settings.json에 defaultMode: "plan", .claude/settings.local.json에 defaultMode: "acceptEdits"를 넣고 claude -p로 파일 생성을 시켰습니다.

    $ claude -p "test1.txt 파일을 만들고 내용은 hello로 채워줘." --output-format json
{"is_error":false, ..., "permission_denials":[], "result":"test1.txt 생성 완료."}

    파일이 프롬프트 없이 바로 생성됐습니다. Local(acceptEdits)이 Project 공유 설정(plan)을 이긴 것으로, 우선순위 5단(Local > Project)과 정확히 일치합니다. settings.local.json을 지우고 Project 설정(plan)만 남긴 채 같은 프롬프트를 다시 실행하자 결과가 완전히 달라졌습니다.

    $ claude -p "test2.txt 파일을 만들고..." --output-format json
{..., "result":"Plan mode is active, but the `ExitPlanMode` tool is disabled for this session,
so I can't request approval to execute through it. ... I've saved it to
/Users/jade/.claude/plans/test2-txt-vectorized-parrot.md. ...
please switch out of plan mode yourself ... and ask me to proceed"}

    직접 해보고 알게 된 것 — plan 모드와 헤드리스는 근본적으로 안 맞는다

    파일이 안 만들어진 것 자체는 예상대로였지만 왜 안 만들어졌는지는 예상 밖이었습니다. Plan 모드는 원래 "계획을 세우고 사람이 승인하면 실행"하는 구조인데, 헤드리스(-p)에는 계획을 승인해줄 사람이 없습니다. v2.1.239의 이 실험에서 Claude는 이걸 스스로 인지하고 ExitPlanMode 도구를 호출할 수 없다고 밝힌 뒤, 계획만 파일로 저장하고 멈췄습니다. 이 메커니즘(승인할 대상이 없음)을 그대로 따르면, plan 모드를 헤드리스 자동화 파이프라인에 기본값으로 깔아둔 경우 "계획만 세우고 아무것도 안 하는" 상태로 멈출 가능성이 커 보입니다. 다만 이번에 검증한 건 이 한 번의 실험이고, 모든 버전·구성에서 동일하게 동작하는지까지 확인하지는 못했습니다.

    실험 2 — CLI 플래그가 설정 파일보다 우선 Project 공유 설정이 plan으로 막고 있어도 --permission-mode acceptEdits를 붙이면 그대로 뚫립니다.

    $ claude -p "test3.txt 파일을 만들고..." --permission-mode acceptEdits --output-format json
{..., "permission_denials":[], "result":"생성 완료."}

    우선순위 5단의 두 번째 자리(CLI 인자 > Local)를 그대로 확인한 결과입니다.

    실험 3 — deny는 무조건 이긴다, 단 도구 이름을 정확히 써야 한다 acceptEdits 모드(파일 쓰기 자동 승인)에 allow: ["Write(*)"], deny: ["Write(secret.txt)"]를 같이 넣고 secret.txt를 만들어봤는데, 파일이 만들어졌습니다. deny가 무시된 것처럼 보였지만 원인은 규칙 문법에 있었습니다. 공식문서(code.claude.com/docs/en/permissions)를 대조해보니 Claude Code는 Write 도구의 경로 지정자를 아예 참조하지 않습니다. 파일 경로 기반 규칙은 Edit(path)와 Read(path)만 유효하고, Write(path)/NotebookEdit(path)/Glob(path)/MultiEdit(path)는 "규칙을 받아들이지만 절대 참조하지 않는다"고 명시돼 있습니다. 규칙을 Edit(secret2.txt)로 바꾸자 예상대로 막혔습니다.

    $ claude -p "secret2.txt 파일을 만들고..." --output-format json
{..., "permission_denials":[], "result":"权限设置阻止了在该目录创建文件，无法完成此操作。"}
$ ls secret2.txt
ls: secret2.txt: No such file or directory

    직접 해보고 알게 된 것 — Write(path) 규칙은 조용히 무시된다

    파일 쓰기를 막고 싶을 때 직관적으로 Write(파일명)을 쓰기 쉬운데, 실제로 참조되는 건 Edit(파일명)입니다. 공식문서는 v2.1.210부터 이런 잘못된 규칙에 시작 시 경고를 띄운다고 설명하지만 이번 -p --output-format json 실행에서는 그 경고가 JSON 결과에도, 표준 출력에도 보이지 않았습니다. 경고가 대화형 배너 전용이거나 이 버전(v2.1.239)의 헤드리스 경로에서 억제되는 것으로 보이는데, 정확한 원인까지는 이번 실습으로 확정하지 못했습니다. 경고를 안 보이니 규칙이 맞다고 믿지 말고, /permissions나 문서로 도구별 지정자 의미를 직접 확인하는 습관이 필요합니다.

    덧붙여, 위 결과의 permission_denials 필드가 두 경우 모두 빈 배열이었다는 점도 눈여겨볼 만합니다. Edit(secret2.txt) deny로 실제로 차단됐는데도 permission_denials에는 안 잡혔습니다. 반면 뒤이어 "default 모드에서 승인 대기 없이 rm류 명령을 시도"하는 시나리오에서는 permission_denials에 정확히 기록됐습니다(Part 2에서 다룸). 이 시점에서 잠정적으로 낸 결론은 "정적 deny 규칙에 의한 차단은 이 실험에서 기록되지 않았고, 프롬프트가 필요한데 헤드리스라 못 띄운 경우는 기록됐다"는 것입니다. 다만 이 결론은 잠정적이고, Part 3의 Lab 2에서 훅의 deny 결정까지 확인해보면 한 번 더 정정됩니다. 이 프로젝트가 1주차부터 써온 "-p + permission_denials로 검증" 기법도 이런 한계를 염두에 두고 읽어야 합니다.

    흔한 오해 바로잡기¶

    "우선순위가 높은 파일이 낮은 파일의 설정을 완전히 덮어쓴다" — 값을 하나만 담는 키(defaultMode 등)에는 맞지만, permissions.allow/ask/deny 같은 배열 키에는 틀린 설명입니다. 배열은 모든 스코프에서 합쳐지며 낮은 스코프의 항목도 높은 스코프가 명시적으로 언급하지 않는 한 그대로 살아남습니다.

    "설정을 고쳤는데 반영이 안 된다 = 버그" — 대부분의 키는 저장 즉시 반영되지만 model·effortLevel·outputStyle처럼 세션 시작 시 한 번만 읽는 키는 의도적인 예외입니다. 반영이 안 되는 것처럼 보이면 이 키들부터 의심하는 게 먼저입니다.

    정리¶

    Claude Code의 설정은 Managed·User·Project·Local 네 파일과 CLI 인자를 합쳐 5단 우선순위로 겹쳐 적용됩니다. 값을 하나만 담는 키는 높은 스코프가 완전히 이기지만 권한 규칙 같은 배열 키는 모든 스코프에서 합쳐진다는 게 이 챕터 전체를 관통하는 핵심 예외입니다. 이 예외를 모르면 "분명 프로젝트에서 막았는데 왜 뚫리지"라는 질문의 답을 영영 못 찾습니다. 대부분의 설정은 저장 즉시 반영되고, managed 계층은 조직 정책이 오타 하나로 무너지지 않도록 관용적으로 파싱되는 반면 개인 설정은 실수를 조기에 잡아주려고 엄격하게 파싱됩니다. 다음 파트는 이 스코프 체계 위에서 실제로 어떤 도구 호출이 허용·거부되는지를 결정하는 permissions 자체를 다룹니다.
