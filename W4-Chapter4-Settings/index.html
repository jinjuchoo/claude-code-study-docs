    4주차 — Chapter 4: Settings¶

    여러 스코프(조직·사용자·프로젝트·로컬)의 설정이 겹칠 때 "어느 게 이기는가"라는 질문에, 값 하나짜리 키와 권한 규칙 같은 목록형 키는 서로 다르게 답합니다 — 전자는 상위가 완전히 덮어쓰고 후자는 전부 합쳐집니다. 이 챕터는 이 구분에서 출발해 권한·훅·MCP·Command/Skill이라는 네 확장 수단이 그 위에서 어떻게 조합되는지, 그리고 이 전부가 사람이 지켜보지 않는 헤드리스 자동화에서도 그대로 작동하는지를 다룹니다.

    원본: Claude Code Deep Dive Workshop / Chapter 4 — Settings (9파트, 약 93 슬라이드 — 문서는 8개 파일로 병합) 기준 버전: Claude Code v2.1.239 / 2026년 7월 교재 판 · 공식 문서 code.claude.com/docs 2026-08-22 대조 반영

    회고¶

    이번 챕터는 "설정 우선순위"라는 말을 너무 쉽게 써왔다는 걸 깨닫게 해줬습니다. defaultMode처럼 값 하나만 갖는 키는 상위 스코프가 하위를 완전히 덮는데, permissions.allow나 deny 같은 목록은 모든 스코프의 값이 그냥 합쳐집니다. 둘을 뭉뚱그려서 "위에 있는 파일이 이긴다"로 외우고 있었습니다. 스크래치 프로젝트에서 실험해보니 User 스코프에만 있던 허용 규칙이 Project 설정을 무시하고 그대로 살아 있더군요. 이 하나를 다시 잡는 데 생각보다 오래 걸렸습니다.

    plan 모드를 헤드리스(-p)로 걸어본 실험은 좀 재밌었습니다. Claude가 파일을 안 만들길래 "역시 안 되는구나" 하고 넘어가려는데, 결과 메시지를 자세히 보니 Claude 스스로 "ExitPlanMode를 호출할 수 없어서 승인을 못 받는다"고 밝히고 있었습니다. 생각해보면 당연합니다. plan 모드는 사람이 계획을 보고 승인해야 다음 단계로 가는 구조인데, 헤드리스에는 그 사람이 없으니까요. 자동화 파이프라인에 plan을 기본값으로 깔아두면 안 되는 이유를 이렇게 직접 눈으로 보게 될 줄은 몰랐습니다.

    deny 규칙 하나도 발목을 잡았습니다. secret.txt를 못 만들게 막으려고 deny: ["Write(secret.txt)"]를 걸었는데 그대로 뚫렸습니다. 한참 뒤에야 원인을 찾았는데, Claude Code가 Write 도구의 경로 지정자 자체를 참조하지 않는다는 걸 몰랐던 겁니다. 파일 경로 기반 규칙은 Edit(path)로 써야 먹힙니다. 이 차단이 permission_denials 필드에 안 잡힌다는 것도 같이 알게 됐습니다. 그 뒤 훅으로 똑같은 걸 막아보니 이번엔 그 필드에 정확히 기록되더군요. 같은 "거부"라도 누가 막았느냐에 따라 검증 로그에 남는 흔적이 다르다는 걸 실습으로 확인한 셈입니다.

    1주차부터 미뤄뒀던 숙제, 권한 모드가 몇 종인지도 이번에 정리했습니다. 공식문서 원문을 직접 펼쳐보니 6종이 맞았습니다. 이 챕터 교재 슬라이드도 정확히 6종을 나열하고 있어서 1주차에 이미 내려둔 판정과 그대로 맞아떨어졌습니다.

    disableAllHooks: true를 켜보니 로그 파일 자체가 안 생길 만큼 훅이 완전히 꺼졌고, 명령을 스킬로 승격해도 그대로 잘 작동했습니다. /hooks 메뉴만 헤드리스에서 "/hooks isn't available in this environment."라는 응답이 돌아와서 대화형 전용 기능이라는 게 확인됐습니다.

    GitHub MCP 서버 연결에서는 처음에 OAuth 자체가 안 먹혔습니다. "does not support dynamic client registration"이라는 오류가 났는데, 공식문서를 다시 찾아보니 이 서버는 원래 OAuth가 아니라 개인 액세스 토큰(PAT)을 헤더로 넘기는 방식이더군요. 교재는 이걸 OAuth처럼 보여주고 있어서, 이 챕터에서 실제로 걸려보지 않았다면 계속 몰랐을 뻔했습니다. 짧은 만료의 읽기 전용 토큰을 발급해서 헤더에 붙였더니 바로 연결됐고, 실제로 공개 저장소 정보를 정확히 가져오는 것까지 확인했습니다.

    30초 요약¶

    Claude Code의 설정은 스코프 4계층(Managed/User/Project/Local) + CLI 인자가 5단으로 겹쳐 적용되는데, defaultMode처럼 값을 하나만 담는 키는 상위 스코프가 완전히 이기지만, 권한 규칙처럼 여러 값을 담는 목록형 키는 모든 스코프의 값이 합쳐진다는 게 이 챕터 전체를 관통하는 핵심 예외입니다.

    이 위에서 권한 규칙(Tool(specifier), deny 우선), 훅(30 이벤트·5핸들러·침묵은 무결정), MCP(3프리미티브·4전송·3스코프), Command/Skill(Markdown 한 장이 곧 /명령)이 각각 다른 층위의 확장 수단으로 자리 잡습니다. 실습으로 확인한 가장 값진 결론은 이 메커니즘들이 대화형 세션과 헤드리스(-p) 자동화에서 동일하게 작동한다는 것입니다 — -p가 건너뛰는 건 사람에게 묻는 절차뿐입니다.

    시작하기 전에 확인할 것¶

    가장 먼저 오해하기 쉬운 것부터 짚으면 — "설정 우선순위"라는 말을 하나의 규칙으로 뭉뚱그리지 마세요. defaultMode처럼 값 하나만 갖는 키는 상위 스코프가 하위를 완전히 덮지만 permissions.allow/deny처럼 목록으로 된 키는 모든 스코프의 값이 합쳐집니다. 이 구분을 Part 1에서 먼저 잡고 가야 이후 파트들이 자연스럽게 이어집니다.

    이 챕터는 앞선 세 챕터와 여러 지점에서 맞물립니다. 권한 모드 자체는 1주차 "개념 7"에서, 서브에이전트의 permissionMode 상속·frontmatter는 2주차에서, managed settings의 배포 계층은 3주차에서 이미 다뤘습니다. 이번 주는 그 설정값들이 실제로 어디서, 어떤 우선순위로 적용되는지가 초점이라 앞선 개념을 다시 설명하지 않고 필요할 때마다 해당 챕터를 참조로 연결합니다. 참고로 권한 모드 개수는 교재 챕터마다 다르게 말하는데(1주차는 4종, 이 챕터는 6종, 6주차는 5종), 공식문서 기준 현행은 6종이고 이 챕터·1주차 서술 모두 이와 일치합니다 — Part 2에서 그 근거를 자세히 다룹니다.

    실습 기록¶

    이 정리의 실습 부분은 읽고 옮긴 게 아니라 2026-08-22에 직접 실행한 결과입니다. 실행 환경: macOS / Claude Code v2.1.239, 격리된 스크래치 프로젝트(실제 계정의 ~/.claude/settings.json은 건드리지 않음).

    Lab 상태 핵심 발견
    Lab 1 — Settings/Permissions 우선순위·deny 실측 ✅ 완료 Local > Project 확인, plan+헤드리스는 ExitPlanMode 불가로 멈춤, Write(path) 규칙 무시됨(Edit(path)만 유효)
    Lab 2 — Hooks 발화 확인(-p에서도 도는지) ✅ 완료 Pre/PostToolUse가 헤드리스에서도 동일 JSON으로 발화, JSON deny가 실제 차단하고 permission_denials에 기록됨, disableAllHooks로 전체 훅 정지도 확인
    Lab 3 — MCP 서버 연결(claude mcp add + /context 전후 비교) ✅ 완료 23개 도구 연결에도 총 컨텍스트 불변(온디맨드 로딩 확인), GitHub 원격 서버는 OAuth 대신 PAT 헤더 방식이 필요하다는 것도 확인
    Lab 4 — 커스텀 명령 작성 + 헤드리스 호출 ✅ 완료 $1 인자·!실행`` 인라인 컨텍스트가 헤드리스에서도 그대로 반영됨, 스킬로 승격 후에도 동일하게 작동
