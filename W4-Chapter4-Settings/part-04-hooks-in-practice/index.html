    Part 4 — Hooks 실전¶

    한 줄 요약¶

    command 외 네 핸들러(http·mcp_tool·prompt·agent)는 각각 "중앙화", "무스크립트 연동", "의미 기반 판정"이라는 다른 용도가 있고 실무에서는 포맷터·가드·알림 세 가지가 가장 먼저 손이 가는 기본기입니다.

    왜 알아야 하나¶

    Part 3이 훅의 뼈대(이벤트·매처·결정 출력)를 다뤘다면, 이 파트는 "그래서 실제로 뭘 만들 수 있는가"를 다룹니다.

    1. 실무에서 가장 먼저 손이 가는 세 가지¶

    command 핸들러 하나만 알아도 웬만한 자동화는 됩니다. 실무에서 가장 자주 쓰는 세 가지부터 봅니다.

    • 포맷터: PostToolUse에서 Edit|Write 매처로 걸어 파일 수정 직후 자동으로 prettier/ruff 같은 포맷터를 돌립니다. 파일 확장자로 분기하면 다언어 프로젝트에도 대응할 수 있고 프로젝트 설정에 커밋하면 팀 표준 훅이 됩니다.
    • 보호 가드: PreToolUse + if: "Bash(rm *)"로 걸어서 실제로 rm -rf 패턴이 보이면 permissionDecision: "deny" JSON을 반환하고 그 외엔 exit 0(무결정)으로 정상 권한 흐름에 맡깁니다. 이건 Part 3 Lab 2에서 이미 직접 검증한 것과 정확히 같은 패턴입니다. 실습에서는 항상 deny하는 단순화된 버전을 썼지만 실전에서는 이렇게 조건부로 판단합니다.
    • 알림: Notification 이벤트로 확인이 필요할 때 로컬 알림을 띄우거나, Stop(턴이 끝났을 때, 즉 내가 메시지를 보내고 Claude가 응답을 마칠 때까지의 한 사이클이 끝났을 때)에 슬랙 웹훅을 걸어 알립니다. 장기 실행 작업에서 체감 효용이 가장 큽니다.

    ▲ 교재 슬라이드 48 — Recipe 2 / 보호 가드

    인프라 관점

    보호 가드는 Kubernetes의 admission webhook과 판단 구조가 거의 같습니다. validating webhook이 "이 리소스를 만들어도 되는가"를 판정하듯 PreToolUse 훅이 "이 도구 호출을 실행해도 되는가"를 판정하고 둘 다 명시적으로 거부하지 않으면 요청을 통과시키는 fail-open 기본값을 공유합니다. 다만 admission webhook은 클러스터 API 서버 앞에서 항상 거치는 강제 관문인 반면, PreToolUse 훅은 어디까지나 권한 시스템의 보조 계층이라는 차이를 혼동하면 안 됩니다.

    2. HTTP 훅 — 중앙 서비스로 이벤트를 쏜다¶

    command 대신 팀 전체가 공유하는 중앙 훅 서버로 이벤트를 보내고 싶을 때 씁니다.

    { "hooks": { "PreToolUse": [
  { "matcher": "Bash",
    "hooks": [{ "type": "http",
      "url": "https://hooks.corp.example/pre-tool",
      "headers": { "Authorization": "Bearer $HOOK_TOKEN" },
      "allowedEnvVars": ["HOOK_TOKEN"] }] } ] } }

    핵심 동작은 이 둘뿐입니다. 서버가 2xx(200번대, "성공"을 뜻하는 HTTP 상태 코드) 응답을 주면서 "막아"(permissionDecision: "deny")라고 답하면 차단되고 그 외 전부(에러 응답, 타임아웃) 그냥 통과시킵니다.

    이 방식을 fail-open(애매하면 막지 않고 통과)이라고 부릅니다. 만약 반대로(응답이 안 오면 차단) 설계했다면, 중앙 훅 서버 하나가 잠깐 다운되는 순간 그 훅을 쓰는 모든 사람의 작업이 멈춰버립니다. 서버 장애 하나로 회사 전체가 마비되는 걸 피하려고 "애매하면 통과"를 기본값으로 삼은 겁니다. 물론 Part 2의 진짜 권한 규칙(allow/ask/deny)은 이 훅과 별개로 계속 작동하니 HTTP 훅은 추가 방어선이지 유일한 방어선이 아니라는 전제가 깔려 있습니다.

    세부 설정 두 가지만 더 알아두면 됩니다. allowedEnvVars로 헤더에 보간할 환경변수를 명시적으로 허용해야 하고 조직 차원에서는 allowedHttpHookUrls로 훅이 쏠 수 있는 목적지 자체를 통제할 수 있습니다.

    3. mcp_tool·prompt·agent — 상황별로 고르기¶

    나머지 세 핸들러는 이렇게 나눠보면 헷갈리지 않습니다.

    • 파일명 규칙 체크처럼 딱 정해진 로직 → command (이미 봄)
    • 이미 연결된 MCP 서버의 도구를 그대로 쓰고 싶음 → mcp_tool
    • "이 커밋 메시지가 적절한가?"처럼 의미를 판단해야 함 → prompt
    • 여러 파일을 실제로 열어보고 조사해야 함 → agent
    { "hooks": { "PostToolUse": [
  { "matcher": "Write|Edit",
    "hooks": [{ "type": "mcp_tool",
      "server": "security", "tool": "security_scan",
      "input": { "file_path": "${tool_input.file_path}" } }] }
] } }

    mcp_tool은 ${tool_input.file_path}처럼 이벤트 필드를 입력에 치환해 넣을 수 있고 별도 스크립트 없이 이미 연결된 MCP 서버의 도구를 그대로 재사용합니다. 단 서버가 이미 연결된 상태여야 하고, 이 훅 자체는 새로운 OAuth 인증을 유발하지 않습니다. 그래서 SessionStart나 Setup처럼 아직 MCP 연결이 끝나지 않은 시점의 이벤트에 걸면 첫 실행에서 실패할 수 있습니다.

    { "type": "prompt",
  "prompt": "이 도구 호출이 마이그레이션 파일을 건드리면 deny하라. 입력: $ARGUMENTS",
  "model": "haiku" }

    prompt 훅은 정규식이나 권한 규칙으로는 표현 못 하는 의미적 판단을 모델 호출 한 번으로 위임합니다. 기본으로 빠른 모델(예: haiku)을 쓰며 타임아웃도 30초로 짧게 잡혀 있어 지연·비용을 통제합니다. agent 훅은 한 걸음 더 나아가 Read, Grep 같은 도구로 실제 diff를 읽고 스키마 파괴 여부까지 확인한 뒤 판정합니다. 교재는 이를 "실험적" 기능으로 표시하고 있어 변경 가능성을 염두에 둬야 합니다.

    4. 그 외 레시피 (필요할 때 참고)¶

    • 반응형 환경: FileChanged에 .envrc|.env 매처를 걸고 async: true로 direnv allow를 자동 실행하거나, CwdChanged로 디렉터리 이동 시마다 환경을 재정렬합니다.
    • Setup과 컨텍스트 주입: claude --init-only로 CI 환경을 1회 준비하고 UserPromptSubmit의 stdout을 컨텍스트에 주입해(git status --short 등) 매 턴 최신 상태를 자동으로 알려줍니다.

    5. /hooks 메뉴와 디버깅¶

    /hooks는 구성된 모든 훅을 읽기 전용으로 보여주는 브라우저입니다. 어느 파일(User/Project/Local/Plugin/Session/Built-in)에서 왔는지도 보여줍니다. 훅이 원인으로 의심되는 문제가 생기면 disableAllHooks를 켜서 훅 자체가 원인인지부터 확인하는 게 정석 디버깅 순서입니다.

    직접 해보기¶

    보호 가드의 핵심 메커니즘은 Part 3의 Lab 2에서 이미 직접 실행하며 검증했습니다. PreToolUse + JSON deny 결정이 실제로 도구 호출을 차단하고, 차단된 호출은 PostToolUse까지 도달하지 않으며 이 차단은 permission_denials에 기록된다는 것까지 확인했습니다. 나머지 레시피(HTTP·mcp_tool·알림·반응형 환경)는 외부 서비스(슬랙 웹훅, MCP 서버, direnv)가 있어야 해서 이번 실습에서는 재현하지 않았습니다.

    disableAllHooks 디버깅 순서도 실제로 검증했습니다. PreToolUse 훅이 로그 파일에 기록을 남기는 상태에서 파일을 하나 만들면 로그가 정상적으로 남지만 disableAllHooks: true를 켠 채 같은 요청을 하면 파일은 그대로 생성되면서도 로그 파일 자체가 생기지 않습니다. 훅이 완전히 꺼졌다는 뜻입니다. /hooks 메뉴는 대화형 전용 UI라 헤드리스(-p)에서는 "/hooks isn't available in this environment."라는 메시지만 돌아오고 소스 라벨(User/Project/Local/Plugin/Session/Built-in) 확인은 대화형 세션에서만 가능하다는 점도 함께 확인했습니다.

    흔한 오해 바로잡기¶

    "HTTP 훅이 응답을 못 받으면 안전하게 차단된다" — 정반대입니다. 비2xx나 타임아웃은 비차단 오류로 처리되어 그냥 진행됩니다. 중앙 훅 서비스의 가용성에 보안을 의존하고 있다면 이 fail-open 기본값을 반드시 감안해야 합니다.

    정리¶

    command를 넘어서는 네 핸들러는 각각 뚜렷한 용도가 있습니다. HTTP는 팀 전체 훅을 한 곳에서 관리하고 싶을 때, mcp_tool은 이미 연결된 도구를 스크립트 없이 재사용하고 싶을 때, prompt·agent는 정규식으로 표현 못 하는 의미 판단이 필요할 때 씁니다. 실무에서 가장 먼저 손이 가는 건 포맷터·보호 가드·알림 세 레시피이고 이 중 보호 가드는 Part 3의 Lab 2로 이미 실제 동작을 확인했습니다. /hooks로 출처를 추적하고 문제가 생기면 disableAllHooks로 훅 자체를 먼저 의심하는 게 정석 디버깅 순서입니다. 다음 파트부터는 Claude Code를 외부 시스템과 연결하는 MCP를 다룹니다.
