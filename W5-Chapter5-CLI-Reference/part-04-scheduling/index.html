    Part 4 — 스케줄과 자동 실행¶

    한 줄 요약¶

    자동화에서 먼저 정할 것은 명령이 아니라 무엇이 이 작업을 깨우고, 어디서 돌고, 어떻게 들여다보고 멈추는가입니다. 이 셋이 정해지면 /loop·/goal·cron·Routines·CI·--bg 중 무엇을 쓸지는 저절로 좁혀집니다.

    왜 알아야 하나¶

    매일 아침 9시에 어제 머지된 PR을 요약해 주는 작업을 만든다고 해 봅시다. 손에 가장 익은 도구는 cron입니다. 노트북 crontab에 0 9 * * * 한 줄을 걸면 끝날 것 같습니다.

    그런데 실제로 걸어 두면 이런 일이 순서대로 일어납니다. 첫날 9시에는 노트북 뚜껑이 닫힌 채 잠들어 있어서 아무것도 안 돌았습니다. 다음 날에는 이전 실행이 아직 안 끝났는데 새 실행이 겹쳐 들어가 같은 요약이 두 번 올라왔습니다. 출장을 가서 시스템 시간대가 바뀌자 이번엔 새벽 3시에 돌았습니다. 그리고 한 달쯤 지나 인증이 만료되자 아무 알림 없이 조용히 실패하기 시작했습니다.

    이 넷은 전부 cron 문법을 몰라서 생긴 문제가 아닙니다. "이 작업을 누가 깨워야 하는가"를 정하지 않은 채 손에 익은 도구부터 집었기 때문에 생긴 문제입니다. 자동화 표면은 같은 명령을 부르는 여러 별칭이 아니라, 서로 다른 운영 책임을 지는 선택지입니다. 무엇을 고르느냐에 따라 "노트북이 꺼져 있으면 어떻게 되나", "겹치면 어떻게 되나", "실패를 누가 알아채나"의 답이 통째로 달라집니다.

    1. 먼저 실행 주체를 고른다¶

    그래서 명령을 고르기 전에 답해야 할 질문은 하나입니다. 무엇이 이 작업을 깨우는가? 답에 따라 쓸 수 있는 표면이 다섯 갈래로 갈립니다. 하나씩 봅시다.

    • 내가 지금 이 대화에서 깨운다 → /loop, /goal — 터미널 앞에 앉아 있는 동안, "될 때까지 계속" 또는 "이 조건을 만족할 때까지"를 걸어 두는 방식입니다. 세션이 살아 있는 동안만 유효하므로 엄밀히는 스케줄이 아니라 지금 이 대화를 목표까지 밀어붙이는 장치에 가깝습니다. 둘의 차이는 뒤의 실습에서 직접 확인했습니다.
    • 내 머신의 시계가 깨운다 → cron — 운영체제 스케줄러에 맡기는 가장 익숙한 방법입니다. 대신 위에서 본 네 가지 문제(꺼진 머신, 겹침, 시간대, 조용한 실패)를 전부 내가 직접 막아야 합니다.
    • 클라우드의 시계가 깨운다 → Routines — 여기서 말하는 Routines는 내 컴퓨터가 아니라 Anthropic이 관리하는 클라우드 쪽에서 정해진 일정에 따라 실행되는 방식입니다. 노트북이 꺼져 있든 뚜껑이 닫혀 있든 일정은 지켜지므로 cron이 안고 있던 "내 머신이 깨어 있어야 한다"는 전제 자체가 사라집니다.
    • 코드 변경이나 PR 같은 사건이 깨운다 → CI — 진짜 조건이 "매일"이 아니라 "푸시될 때마다"라면 시계가 아니라 사건이 트리거여야 합니다. 시계로 흉내 내면 늦게 돌거나 헛돌게 됩니다.
    • 내가 지금 시작하되 터미널을 붙잡지 않는다 → --bg — 실측 도움말의 --bg는 세션을 background로 시작하고 ID를 즉시 출력하며 attach, logs, stop, rm이 그 ID를 받는다고 설명합니다. 깨우는 주체는 여전히 나이므로 이건 스케줄러가 아니라 실행 위치를 옮기는 선택입니다.

    2. background는 관측 가능해야 한다¶

    셸에서 명령 뒤에 &를 붙여 본 적이 있다면 그 뒤의 답답함도 압니다. 프로세스는 떨어져 나가지만 그게 지금 뭘 하고 있는지 물어볼 창구가 없습니다. 잘 됐는지 확인하려면 결국 출력 파일을 뒤지거나 ps로 살아 있는지만 확인하게 됩니다.

    --bg가 다른 지점이 바로 여기입니다. --bg는 "비동기로 던져 놓는" 선택이 아니라, 나중에 다시 말을 걸 수 있는 작업 ID를 만드는 선택입니다. ID가 있으면 왕복이 성립합니다. claude agents가 지금 살아 있는 작업 목록을 보여 주고, claude logs <id>가 그 작업의 출력을, claude attach <id>가 그 작업과의 대화를, claude stop <id>가 중지를 맡습니다. 아래 실습에서 이 왕복을 띄우기부터 멈추기까지 끝까지 돌려 봤습니다.

    교재도 이 대목에서 Routines와 --bg를 나란히 놓고 설명합니다. 하나는 내 컴퓨터 없이 도는 것, 다른 하나는 내 컴퓨터에서 돌되 터미널을 붙잡지 않는 것이라 짝으로 놓고 보면 차이가 선명해집니다.

    현장 메모

    cron에는 겹침 방지 락, 절대 경로, 고정된 PATH, UTC 또는 명시한 시간대, 실패 알림이 필요합니다. “매일 7시”만 적으면 운영 계약이 아닙니다.

    직접 해보기¶

    실행 환경: macOS 26.6.2 / Claude Code 2.1.251 / 2026-08-29. 격리한 스크래치 저장소에서 --safe-mode로 실행했습니다.

    --bg로 띄우고, 목록에서 찾고, 멈추기¶

    먼저 습관대로 -p를 붙였다가 거절당했습니다.

    $ claude --bg -p 'src/pay.js 개선점 세 가지' --safe-mode
--bg and --print conflict: --print never starts the interactive session that `claude agents` attaches to, so the job would be unattachable. The prompt is the positional — drop --print: `claude --bg '<task>'`.

    거절 메시지 자체가 앞 절의 이야기를 그대로 반복합니다. -p는 답만 출력하고 끝나므로 나중에 붙을 세션이 애초에 남지 않습니다. 그러면 --bg가 ID를 줘 봐야 쓸 데가 없습니다. 프롬프트를 위치 인자로 옮기니 곧바로 ID와 후속 명령 네 줄을 돌려줬습니다.

    $ claude --bg 'src/pay.js를 읽고 개선점 세 가지를 번호 매겨 정리해줘' --safe-mode
backgrounded · cd44ce18
  claude agents             list sessions
  claude attach cd44ce18    open in this terminal
  claude logs cd44ce18      show recent output
  claude stop cd44ce18      stop this session

    다음은 이 작업을 목록에서 찾는 차례입니다. claude agents를 그냥 치면 TTY, 즉 사람이 보고 있는 대화형 터미널을 요구합니다. 스크립트에서 쓰려면 --json을 붙여야 하고 --cwd를 함께 주면 특정 경로에서 시작한 작업만 추릴 수 있습니다.

    스크립트를 짤 때 실제로 봐야 하는 필드는 사실 두 개뿐입니다. 후속 명령에 넘길 id, 그리고 작업이 끝났는지 알려 주는 state. 아래는 그 둘을 포함해 식별에 쓰는 필드만 추린 것입니다.

    $ claude agents --json --cwd "$PWD" | jq '[.[] | select(.kind=="background") | {id, name, status, state, sessionId}]'
[
  {
    "id": "cd44ce18",
    "name": "analyze pay.js improvements",
    "status": "idle",
    "state": "done",
    "sessionId": "cd44ce18-93d2-4913-b5e3-6c48812d1ddc"
  }
]

    여기서 한 번쯤 헷갈리는 게 id와 sessionId가 따로 있다는 점입니다. id는 cd44ce18 같은 짧은 형태이고 sessionId는 같은 작업의 전체 UUID인데 attach·logs·stop이 받는 것은 짧은 id 쪽입니다. jq 안에 붙은 select(.kind=="background")도 장식이 아니라 꼭 필요한 조건인데 그 이유는 조금 뒤 메모에 적었습니다.

    참고 — 나머지 필드

    항목에는 이 밖에도 name, pid, cwd, startedAt이 함께 실려 옵니다. name은 지시하지 않았는데도 CLI가 프롬프트를 요약해 붙여 준 것이고 나머지는 프로세스나 시작 시점을 추적할 때 씁니다. 처음 스크립트를 짤 때는 몰라도 되는 값들입니다.

    출력을 확인하려고 claude logs를 붙였는데, 여기서 예상이 어긋났습니다. 사람이 읽을 문장이 아니라 터미널 화면 자체가 이스케이프 시퀀스째로 쏟아졌습니다.

    $ claude logs cd44ce18 > logs.txt
$ wc -c < logs.txt
    9890
$ wc -l < logs.txt
       0
$ tr -cd '\033' < logs.txt | wc -c
     777

    9,890바이트 안에 줄바꿈은 한 번도 없고 ESC 문자만 777개입니다. 화면을 지우고 커서를 옮겨 가며 그린 TUI 프레임을 그대로 받아 적은 결과입니다.

    작업이 끝난 뒤 중지하면 목록이 비워집니다. 띄우기 → 조회 → 출력 확인 → 중지까지 왕복이 닫힙니다.

    $ claude stop cd44ce18
stopped cd44ce18
$ claude agents --json --cwd "$PWD"
[]

    직접 해보고 알게 된 것

    claude logs <id>가 돌려주는 것은 “로그 파일”이 아니라 터미널 화면을 그대로 뜬 덤프였습니다. ANSI를 벗겨 내도 커서 위치 지정 때문에 글자 순서가 뒤엉켜 문장으로 복원되지 않습니다. 그러니 logs와 attach는 사람이 눈으로 확인할 때 쓰고, 기계가 읽을 결과가 필요하면 애초에 -p --output-format json으로 돌리는 쪽을 골라야 합니다. 이름이 logs라서 grep에 넘길 만한 무언가를 기대했다가 방향을 바꾼 지점입니다.

    직접 해보고 알게 된 것

    claude agents --json이 배열로 돌려주는 항목에는 background 작업뿐 아니라 지금 이 터미널에서 돌고 있는 대화형 세션("kind": "interactive")도 섞여 나옵니다. 스크립트에서 “내가 띄운 백그라운드 작업”만 세려면 jq '[.[] | select(.kind=="background")]'처럼 걸러야 하고 그러지 않으면 자기 자신을 세어 버립니다.

    /loop와 /goal — 나란히 놓고 보니 역할이 달랐다¶

    교재는 /loop와 /goal을 나란히 소개합니다. 이름만 보면 "반복"과 "목표"라서 같은 기능의 다른 표현처럼 읽히는데, 정말 그런지 확인하고 싶었습니다.

    /loop는 세션이 열려 있는 동안 같은 프롬프트를 일정한 간격(직접 정한 시간이든 Claude가 알아서 고르는 시간이든)으로 다시 실행하는 쪽입니다. 세션이 계속 떠 있어야 다음 차례가 돌아오는 구조라 -p처럼 한 번 답하고 끝나는 실행에는 애초에 안 맞습니다. 그래서 이번엔 tmux로 진짜 대화형 세션을 하나 열고 그 안에 직접 쳐서 확인했습니다. 대상은 eslint 경고 두 개(no-unused-vars, eqeqeq)가 남아 있는 app.js입니다.

    한 번 만에 목표를 채우고 스스로 멈췄습니다. /loop는 원래 정해 둔 간격마다 프롬프트를 다시 실행하며 도는 구조인데, 첫 실행에서 바로 고쳐졌기 때문에 다음 간격까지 기다릴 필요가 없어져 Claude 스스로 다음 예약을 걸지 않고 끝낸 것입니다. 그래서 "언제 다음 차례가 도나"를 지켜볼 기회는 이번엔 없었습니다.

    같은 파일에 /goal도 걸어 봤습니다. 슬래시 자동완성에 Set a goal Claude checks before stopping이라는 설명으로 따로 등록되어 있는 것부터가 힌트였습니다.

    ❯ /goal npx eslint@8.57.0 app.js 경고 0개
  ⎿  Goal set: npx eslint@8.57.0 app.js 경고 0개

⏺ Goal acknowledged: npx eslint@8.57.0 app.js warnings at 0. Already
  verified — exits clean with no output, condition is met.

✔ Goal achieved (8s · 1 turn · 288 tokens)

    /goal을 걸면 매 턴이 끝날 때마다 별도의 작고 빠른 모델이 조건 충족 여부를 판정하고, 안 됐으면 새 턴을 또 시작합니다 — "충족될 때까지 스스로 턴을 반복하는" 쪽은 오히려 /goal이었습니다. 그리고 -p와도 아예 무관한 게 아니었습니다. 공식 문서가 claude -p "/goal ..." 예시를 직접 들고 있길래 같은 조건으로 재현해 봤습니다.

    $ claude -p "/goal npx eslint@8.57.0 app.js 경고 0개" --safe-mode --output-format json \
    | jq '{result,num_turns,total_cost_usd}'
{
  "result": "ESLint already reports 0 warnings on `app.js` — no changes needed. Goal met.",
  "num_turns": 4,
  "total_cost_usd": 0.0457716
}

    정말로 됐습니다. -p 한 번으로 목표 판정까지 끝까지 돌아갔고, 비용 집계(modelUsage)에는 실제 작업을 한 claude-sonnet-5와 별도로 조건을 판정한 claude-haiku-4-5가 함께 찍혀 있었습니다 — 조건 판정이 진짜로 별도 모델이 맡는 일이라는 뜻입니다.

    직접 해보고 알게 된 것

    처음엔 "/loop가 능동적으로 반복하는 쪽, /goal은 한 번 확인만 하는 쪽"이라고 짐작했는데 반대에 가까웠습니다. 턴을 계속 새로 시작해 가며 조건을 채우는 건 /goal이고, /loop는 세션이 열려 있는 동안 같은 프롬프트를 시간 간격으로 재실행하는 스케줄러입니다. 그리고 세션이 계속 떠 있어야 하는 /loop와 달리 /goal은 -p 한 번으로 조건 판정까지 끝까지 돌아갑니다 — 그래서 이번 실습에서 /loop는 tmux가 꼭 필요했지만, /goal은 사실 tmux 없이 -p만으로도 확인할 수 있었습니다.

    이번엔 터미널이 아니라 웹에서 이어가 보려다 막혔다 — Remote Control¶

    여기까지는 전부 터미널 안에서 끝나는 이야기였습니다. 방향을 반대로 돌려서 터미널에서 시작한 세션을 자리를 뜬 뒤 브라우저에서 이어 받는 것도 해 보고 싶었습니다. 그게 Remote Control입니다.

    이름 그대로 상대(웹·모바일 쪽 화면)가 있어야 성립하는 기능이라, 처음엔 한쪽인 터미널만으로 재현해 보려다 막혔습니다. claude --remote-control을 켰는데 이어 받을 때 필요한 페어링 코드가 아무것도 뜨지 않았습니다.

    $ claude --remote-control w5-doc-test
# 트러스트 확인 → 정상 진행되지만, 세션이 떠도 페어링 URL/QR이 전혀 안 보인다

    세션은 정상으로 떴는데 페어링만 안 되니 처음엔 "붙을 상대가 없어서 그런가" 싶었습니다. 원인은 다른 데 있었습니다. 이 환경은 CLAUDE_CODE_OAUTH_TOKEN_FILE(= claude setup-token으로 받은 장기 토큰)로 로그인돼 있었는데, 공식 문서는 이 경우를 정확히 짚습니다.

    "Remote Control requires a full-scope login token" — claude setup-token이나 CLAUDE_CODE_OAUTH_TOKEN으로 인증된 세션은 모델 호출 전용 토큰이라 Remote Control 세션 자체를 만들 수 없습니다.

    unset CLAUDE_CODE_OAUTH_TOKEN_FILE 후 /login으로 계정에 다시 로그인하고 나서야 세션이 정상적으로 페어링 URL을 냈습니다.

    $ unset CLAUDE_CODE_OAUTH_TOKEN_FILE CLAUDE_CODE_OAUTH_TOKEN
$ claude --remote-control
/remote-control is active · Continue here, on your phone, or at
https://claude.ai/code/session_01XHhhRDNgjELZnsnqkBMY1k

    이 URL을 다른 브라우저에서 열어 "지금 몇 시야?"라고 보내자, 로컬 머신이 실제로 도구를 호출(Got current system time)해 응답했고 세션 이름도 대화 내용에 맞춰 자동으로 바뀌었습니다(공식 문서가 말하는 "명시적 이름이 없으면 첫 프롬프트로 제목을 갱신한다"는 규칙 그대로).

    직접 해보고 알게 된 것

    Remote Control이 안 되는 것과 "연결 상대가 없어서 안 되는 것"은 다른 문제였습니다. 이번 실패의 진짜 원인은 상대가 아니라 이 환경의 인증 방식 자체였습니다 — CI·자동화용으로 흔히 쓰는 setup-token/CLAUDE_CODE_OAUTH_TOKEN 인증이 Remote Control과는 애초에 호환되지 않습니다. 자동화 스크립트와 사람이 직접 켜는 대화형 세션은 같은 CLI라도 쓸 수 있는 기능의 경계가 다르다는 걸 이번에 명확히 알게 됐습니다.

    페어링이 한 번 성립하고 나면 반대 방향도 자연스럽게 따라옵니다. --teleport는 이렇게 페어링된 세션을 로컬로 다시 불러오는 동작이라 같은 메커니즘의 반대편으로 이해하면 됩니다.

    흔한 오해 바로잡기¶

    "background면 스케줄러가 필요 없다" — 아닙니다. background는 지금 시작한 작업을 떼어 놓는 방식이고 언제 다시 시작할지는 cron·Routine·CI 같은 스케줄/이벤트 주체가 결정합니다.

    "/loop와 /goal은 이름만 다른 같은 기능이다" — 위 실습에서 갈렸습니다. /goal은 조건이 채워질 때까지 턴을 새로 시작해 가며 스스로 반복하고 -p로도 그대로 돌아갑니다. /loop는 세션이 떠 있는 동안 같은 프롬프트를 시간 간격으로 다시 실행하는 스케줄러라 -p와는 맞지 않습니다.

    정리¶

    맨 앞의 cron 실패 네 가지는 전부 같은 곳에서 출발했습니다. "언제 돌릴까"를 먼저 정하고 "누가 깨우는가"를 나중에 생각한 것입니다. 순서를 뒤집으면 답이 훨씬 빨리 나옵니다. 누가 깨우고(내 대화인지, 내 머신의 시계인지, 클라우드의 시계인지, 코드 이벤트인지), 어디서 돌며(내 노트북인지 클라우드인지), 어떻게 관측하고 멈출 것인가(ID가 있는지, 실패를 누가 알아채는지). 이 셋에 답하고 나면 /loop든 cron이든 Routines든 CI든 --bg든, 명령은 뒤따라옵니다.
