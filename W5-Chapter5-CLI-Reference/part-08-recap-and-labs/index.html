    Part 8 — Recap과 Labs¶

    한 줄 요약¶

    이 챕터의 실무 순서는 도움말 실측 → 작은 JSON 호출 → 세션·비용·정책 게이트 → CI와 운영 자동화입니다.

    왜 알아야 하나¶

    CLI를 한 번 실행해 본 것과 운영 가능한 자동화를 만든 것은 다릅니다. 한 번 성공한 명령은 성공한 그 한 번만 증명합니다. 그래서 이 마지막 파트는 성공한 결과만 모으지 않고 랩을 돌리는 동안 실제로 손이 멈췄던 지점과 거기서 무엇을 고쳤는지를 같이 남깁니다. 뒤에서 같은 자동화를 만들 사람이 다시 막히는 데 시간을 쓰지 않게 하는 게 이 기록의 목적입니다.

    1. 챕터 전체를 자동화 하나로 되짚기¶

    이 챕터가 다룬 것을 한 번에 떠올리는 가장 빠른 방법은, PR마다 자동 리뷰를 붙이려다 네 번 막히는 장면을 순서대로 따라가 보는 것입니다.

    처음 막히는 곳은 실행 그 자체입니다. 교재에서 본 플래그 조합을 스크립트에 그대로 옮겨 적었는데 실행이 거부됩니다. 이때 기준이 되는 건 교재가 아니라 지금 이 머신의 claude --help입니다. 플래그는 문서보다 빠르게 추가되고 폐기되므로, 자동화가 의존해야 할 계약은 언제나 실측 도움말 쪽에 있습니다.

    두 번째는 결과를 읽는 방식입니다. 텍스트 출력만 받아 보면, 모델이 리뷰를 제대로 한 것인지 도중에 실패해서 사과 문장을 돌려준 것인지 셸이 구분하지 못합니다. -p에 --output-format json을 붙이면 답변이 봉투에 담겨 옵니다. 그 봉투에는 답변 본문 말고도 성공 여부와 비용과 세션 ID가 같이 들어 있습니다. 자동화가 판정에 쓰는 것은 답변이 아니라 이 봉투입니다.

    세 번째는 작업이 길어질 때입니다. 리뷰가 오래 걸려 백그라운드로 돌리는 순간, "지금 뭐가 돌고 있나"를 사람의 기억이 아니라 조회 가능한 값으로 물어야 합니다. 세션과 background 작업은 각각 ID를 갖습니다. 그 ID 하나로 목록 조회·로그 확인·중지가 전부 이어집니다.

    네 번째는 CI에 올린 뒤입니다. 이제 내가 짜지 않은 PR에서도 같은 스크립트가 돕니다. 도구를 읽기 전용으로 묶고, 비용과 턴 수에 상한을 걸고, 출력 형태를 schema로 고정하고, 그 고정된 값을 정책 게이트가 기계적으로 판정하게 만듭니다. 이 네 겹이 다 있어야 비로소 자동화라고 부를 수 있습니다.

    2. Lab 1 — 헤드리스 다섯 패턴¶

    이 랩의 목적은 헤드리스 호출을 "한 번 돌려 봤다"에서 "스크립트에 넣어도 되겠다"까지 끌어올리는 것이었습니다. 그러려면 출력 형식·세션 재개·구조화 출력·상한을 한 저장소 위에서 연달아 밟아 봐야 합니다.

    그래서 먼저 격리 저장소를 만들고 두 커밋을 준비했습니다. 실제 Git 로그는 다음과 같습니다.

    $ git log --oneline
382ba39 feat: add currency to charge
939d1f9 chore: cli lab scaffold

    이 저장소를 대상으로 단순 text, --output-format json, stream-json, stdin pipe, 비용 추출, --resume과 --fork-session, --json-schema, --max-turns 초과까지 전부 실행했습니다.

    손이 멈춘 지점은 셋이었습니다. stream-json은 -p와 함께 쓸 때 --verbose를 추가로 요구했고, --json-schema는 파일 경로가 아니라 JSON 문자열을 받았으며, --max-turns 1을 걸었는데 봉투의 num_turns는 2로 찍혔습니다.

    셋 다 도움말 한 줄만 읽고 넘겼으면 CI에서 처음 만났을 종류의 차이입니다. 여기서 고른 방식은 단순합니다. 자동화에 넣을 조합은 반드시 로컬에서 먼저 한 번씩 쳐 보고 그때의 출력을 그대로 기록해 둡니다.

    원본 출력은 각 파트의 "직접 해보기"에 나눠 실었습니다 — 세 출력 형식과 스키마·상한은 Part 2, 세션 재개와 분기는 Part 3, 결과 JSON 집계는 Part 6에 있습니다.

    3. Lab 2 — 로컬 리뷰 봇¶

    이 랩의 목적은 모델의 리뷰 결과를 셸이 문장 해석 없이 판정할 수 있게 만드는 것이었습니다. 사람이 읽고 판단하는 리뷰라면 굳이 자동화할 이유가 없습니다.

    교재 설계대로 git diff HEAD~1..HEAD를 표준 입력으로 넘기고, --json-schema로 판정 구조를 고정하고, CRITICAL이면 exit 1을 내는 스크립트를 만들어 실제로 돌렸습니다. 읽기 전용 도구 제한과 두 종류의 상한을 함께 걸었습니다.

    $ git diff HEAD~1..HEAD | claude -p '아래 diff를 리뷰해서 스키마대로 답해' \
    --json-schema "$SCHEMA" --output-format json \
    --allowed-tools Read Grep --max-turns 5 --max-budget-usd 0.50 \
    --safe-mode > raw.json
$ jq -e '.is_error == false' raw.json > /dev/null
$ jq -r '.result' raw.json > review.json
$ jq -r '.severity' review.json
MAJOR
$ ./review.sh
severity=MAJOR  cost=0.0424638
리뷰 게이트: 통과
$ echo $?
0

    여기서 닫지 못한 게 하나 있습니다. 이번 샘플 diff는 MAJOR 판정이 나와서 exit 1 차단 경로는 실제 모델 출력으로 밟아 보지 못했습니다. 차단 분기는 셸 문법상 동작하지만 실제로 CRITICAL을 받아 낸 기록은 없다는 뜻으로 남겨 둡니다.

    jq -r '.result' raw.json으로 문자열을 꺼낸 뒤 jq -r '.severity'로 한 번 더 파싱한 것도 최선은 아니었습니다. 봉투를 다시 보니 같은 값이 .structured_output.severity에 이미 파싱된 채로 들어 있었습니다(Part 2 참고). 두 단계를 jq -r '.structured_output.severity' 한 줄로 줄일 수 있었다는 뜻입니다.

    그래도 이 랩의 핵심은 확인됐습니다. --json-schema 덕분에 severity 값이 열거형 안에서만 나오므로, 셸은 모델의 문장을 해석할 필요 없이 문자열 비교 한 번으로 통과·차단을 정합니다. jq -e가 게이트 역할을 제대로 했다는 게 그 증거입니다. 자동화에서 고를 것은 "모델에게 잘 설명하기"가 아니라 "모델이 낼 수 있는 값의 범위를 미리 좁히기" 쪽입니다.

    4. Lab 3 — CI 통합¶

    이 랩의 목적은 로컬에서 통과한 게이트가 남의 손이 닿는 자리에서도 같은 판정을 내는지 보는 것이었습니다. 그래서 이번 랩은 격리 실습이 아니라 이 정리를 발행하는 실제 private 저장소에 워크플로를 커밋하고 진짜 PR(#1)을 열어 돌렸습니다.

    claude setup-token으로 받은 토큰을 저장소 시크릿(CLAUDE_CODE_OAUTH_TOKEN)으로 등록하고, checkout → diff 수집 → claude -p(--json-schema+--safe-mode) → jq -e 정책 게이트 → 아티팩트 업로드 순서로 구성했습니다. 실행 결과는 severity: MEDIUM으로 게이트를 통과했습니다.

    실제 저장소를 쓰는 만큼 조심한 부분이 있습니다. 트리거는 PR 작성자가 본인 계정인지로 제한했고 확인이 끝난 뒤 PR과 브랜치는 정리했습니다. 실제 토큰이 걸린 워크플로를 처음 붙일 때는 "누가 이 워크플로를 발동시킬 수 있는가"를 먼저 좁혀 두는 편이 안전하다는 게 여기서 고른 선택입니다.

    원본 로그는 Part 5에 그대로 남겼습니다.

    5. Lab 4 — 스케줄·background¶

    이 랩의 목적은 오래 걸리는 작업을 띄워 두고 나중에 다시 찾아오는 왕복을 실제로 돌려 보는 것이었습니다. 띄우는 것보다 "띄운 걸 어떻게 다시 붙잡는가"가 운영에서는 더 중요합니다.

    claude --bg로 작업을 띄우고 claude agents --json으로 조회한 뒤 claude logs로 출력을 보고 claude stop으로 정리하는 왕복을 실제로 돌렸습니다.

    여기서 예상과 달랐던 게 둘 있습니다. --bg와 -p는 서로 배타적이라 같이 못 쓴다는 점, 그리고 logs가 파싱 가능한 로그가 아니라 터미널 화면 덤프라는 점입니다. 후자는 특히 중요한데, 백그라운드 작업의 결과를 jq로 판정하려던 계획이라면 애초에 성립하지 않는다는 뜻이기 때문입니다.

    대화형 전용 기능도 이 랩에서 같이 닫았습니다. /loop는 세션이 열려 있어야 하는 스케줄러라 -p와 안 맞아서 tmux로 실제 대화형 세션을 열어 확인했습니다. /goal은 반대로 -p 한 번으로도 조건 판정까지 끝까지 돌아간다는 걸 나중에 확인했습니다 — 처음엔 둘 다 대화형이 필요할 거라고 짐작했는데 절반만 맞았습니다. Remote Control도 처음엔 페어링 URL이 안 떠서 막혔는데, 원인이 setup-token 인증(모델 호출 전용이라 Remote Control과 호환되지 않음)이었다는 걸 확인하고 /login으로 바꾸자 정상 동작했습니다. "헤드리스로 안 되면 못 해 본 것"이 아니라 될 것 같은 쪽은 헤드리스로, 안 되는 쪽만 대화형을 열어서 확인한다는 게 이 랩에서 고른 방식입니다.

    원본 출력과 셋의 실측 차이는 Part 4에 정리했습니다.

    직접 해보기¶

    랩을 전부 돌리고 나서 마지막으로 한 일은 교재가 다룬 플래그를 실측 도움말과 한 줄씩 맞춰 보는 것이었습니다. 새로 확인한 대표 항목은 다음과 같습니다.

    $ claude --help
  --bare                                Minimal mode: skip hooks, LSP, plugin
  --bg, --background                    Start the session in the background
  --fork-session                        When resuming, create a new session ID
  --from-pr [value]                     Resume a session linked to a PR
  --json-schema <schema>                JSON Schema for structured output
  --safe-mode                           Start with all customizations ... disabled
  --teleport [session]                  Resume a teleport session
  --tools <tools...>                    Specify the list of available tools

    교재의 핵심 플래그 중 위 항목들은 실측 도움말에 그대로 있었습니다. 5주차 전체를 관통하는 실습이었던 만큼, 교재 표기와 실측 결과를 표 하나로 정리해 둡니다.

    플래그 교재(2026.07) 실측(v2.1.251) 비고
    --bare 있음 동일 공식 문서: 향후 -p의 기본값이 될 예정
    --safe-mode 있음 동일 CLAUDE_CODE_SAFE_MODE=1 설정
    --from-pr 있음 동일 GitHub·GitLab·Bitbucket PR 번호/URL 또는 선택기
    --teleport 있음 동일 웹 세션을 로컬 터미널로 재개
    --remote 있음(웹 위임으로 소개) 도움말엔 안 보임 삭제가 아니라 --cloud의 폐기된 숨은 별칭. Remote Control과는 별개
    --remote-control 교재는 --remote로 뭉뚱그림 --remote-control/--rc로 별도 확인 웹·모바일에서 세션을 원격 조작
    --bg / --exec 있음 --bg는 도움말에 그대로 있음, --exec만 숨겨짐 -p와 --bg는 동시 사용 거부됨
    --json-schema 있음 동일 값은 파일 경로가 아니라 JSON 문자열
    --max-turns 있음 동일(도움말에서 숨겨짐, -p 전용) 도움말 부재 ≠ 미지원의 예외 사례
    --tools/--allowed-tools/--disallowed-tools 있음 동일 우선순위: --tools(가용 집합) 안에서 allow/deny가 세부 규칙
    --restricted, --cloud, --fallback-model, --debug-file, --prompt-suggestions 비중 있게 다루지 않음 도움말에 명시적으로 등장 이번 실측에서 새로 확인

    "도움말에 없다"는 "지원 안 함"과 같지 않습니다. --max-turns와 --exec는 도움말에서 숨겨져 있지만 공식 문서와 실제 실행 모두에서 살아 있었습니다. 반대로 --remote는 도움말에 없는 게 맞지만 완전히 사라진 게 아니라 다른 이름 뒤에 숨어 있었습니다. 도움말의 전체 목록을 기계적 "삭제/추가" 판정으로 보지 말고 안 보이는 항목은 실제로 쳐서 확인하는 습관이 필요합니다.

    흔한 오해 바로잡기¶

    "명령이 도움말에 있으면 그대로 쓰면 된다" — 아닙니다. 이번 랩에서 손이 멈춘 곳은 전부 도움말과 실제 사이의 좁은 틈이었습니다. stream-json이 --verbose를 더 요구하고, --json-schema가 경로 대신 문자열을 받고, --bg가 -p와 충돌하는 것은 플래그 목록만 봐서는 알 수 없습니다. 자동화에 넣을 조합은 한 번씩 손으로 돌려 보고 종료 값을 확인한 뒤에 스크립트로 옮깁니다.

    정리¶

    Claude CLI 자동화는 세 가지 질문으로 시작합니다. 이 입력은 신뢰할 수 있는가, 이 결과를 기계가 판정할 수 있는가, 실패·비용·중단을 누가 관측하는가. 이 질문에 답한 뒤에야 프롬프트와 스케줄을 고릅니다.

    CI를 실제 PR에 붙이는 일, /loop·/goal, Remote Control까지 이번에 전부 실측으로 닫았습니다. 5주차 실습 중 진짜로 재현 불가능한 항목은 결국 없었습니다 — 다만 --teleport는 페어링된 세션을 반대 방향(웹→로컬)으로 불러오는 동작이라 별도로 다시 실행해 보지는 않았습니다.
