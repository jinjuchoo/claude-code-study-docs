    5주차 — Chapter 5: CLI Reference¶

    명령을 외우기보다 실패와 비용까지 자동화가 판정하게 만드는 법에 집중한 주차입니다. Claude Code를 대화창에만 쓰지 않고, 셸 스크립트·세션·CI가 그대로 받을 수 있는 입력과 출력으로 다뤄 봤습니다.

    원본: Claude Code Deep Dive Workshop / Chapter 5 — CLI Reference (9파트, 약 95 슬라이드) 기준 버전: Claude Code v2.1.251 / 2026-08-29 · 교재는 2026년 7월판

    이 주차의 최소 경로¶

    W1~W4를 읽었지만 Claude Code 자동화는 처음이라는 전제로 시작합니다. 이번 주의 첫 성공은 신뢰하는 연습 디렉터리에서 대화형으로 한 번 실행한 뒤, 같은 질문을 -p로 한 번 실행하고 결과를 확인하는 일입니다. 자동화는 그다음 단계입니다.

    먼저 W1의 설치·로그인·안전한 첫 세션을 확인합니다. W2에서 본 worktree는 파일 변경 실험을 분리하는 작업공간입니다. W4의 권한·Hook·MCP는 대화형에서도 적용되던 설정이지만, 사람이 없는 -p 실행에는 승인 대화상자가 없습니다. 이번 주에는 이 세 가지를 자동화의 입력·권한·작업공간 경계로 다시 씁니다.

    아래 1~4단계는 필수입니다. 5~6단계는 필수 완료 뒤에 권장하고, CI는 심화 내용입니다. 각 단계에서 눈으로 확인할 결과가 있어야 다음으로 넘어갑니다.

    1. 대화형 1회 — claude를 실행하고, 현재 디렉터리에서 Claude와 한 번 주고받습니다. 성공 신호는 답변과 세션이 화면에 남는 것입니다.
    2. 최소 -p 1회 — 같은 디렉터리에서 claude -p 'say OK'를 실행합니다. 성공 신호는 터미널에 한 번의 결과가 찍히고 명령이 끝나는 것입니다.
    3. 일반 출력과 JSON 비교 — --output-format json 결과에서 result와 is_error를 함께 봅니다. 답변 내용과 실행 성공은 다른 값임을 확인합니다.
    4. 필드 하나로 분기 — is_error 또는 구조화 출력의 한 필드만 검사해 통과·중단을 고릅니다. 문장을 해석하지 않습니다.
    5. 권장: 세션 재개 — 만든 session_id로 이전 대화를 다시 엽니다. 대화 맥락과 작업 파일은 별개임을 확인합니다.
    6. 권장: 로컬 자동화 — 위에서 확인한 한 호출을 스크립트로 옮기고, 입력·결과 파일·종료 상태를 남깁니다.

    심화: CI — 로컬에서 검증한 읽기 전용 게이트를 CI 러너로 옮깁니다. CI 러너는 PR 같은 이벤트가 있을 때 별도 컴퓨터에서 명령을 실행하는 환경입니다.

    cron, Routines, CI, --bg, OIDC, 외부 게시, 자동 수정은 이 최소 경로를 끝낸 뒤의 주제입니다. 실제 시스템을 바꾸거나 외부에 결과를 보내는 예제는 심화로 읽고, 처음에는 실행 기록을 관찰하는 데 그칩니다.

    회고¶

    이번 주에 가장 크게 달라진 것은 claude -p를 보는 방식이었습니다. 처음에는 터미널에서 답을 한 번 받는 방법으로만 생각했습니다. 하지만 이 명령을 스크립트에 연결해 나온 문장만 쓰면, 정상 종료와 중간 실패가 겉으로 구분되지 않습니다. 둘 다 그럴듯한 한국어 문장을 돌려주기 때문입니다. 다음 단계가 읽어야 할 것은 문장이 아니라 “이 실행이 실패로 끝났는가”, “토큰과 비용을 얼마나 썼는가”처럼 기계가 판정할 수 있는 값입니다.

    --output-format json을 붙이면 이 차이가 보입니다. 사람이 읽을 문장은 result 필드에, is_error, usage, total_cost_usd는 같은 결과 객체에 함께 들어갑니다. 이 객체를 살펴본 뒤부터는 “Claude에게 무엇을 물을까”보다 “다음 단계가 무엇을 보고 판단할까”를 먼저 정하게 됐습니다.

    실측에서 막힌 곳은 대부분 도움말과 실제 동작 사이의 좁은 틈이었습니다. stream-json은 -p와 함께 쓰면 --verbose를 더 요구했습니다. --json-schema는 스키마 파일 경로가 아니라 JSON 문자열을 받았고 --bg는 -p와 아예 배타적이었습니다. 플래그 목록을 정확히 외워도 조합을 실행해 보기 전에는 알 수 없는 점이라, 이번 주 정리는 읽은 내용보다 실행 기록을 중심으로 남겼습니다.

    --fork-session을 원 세션을 보존하는 실험대라고 이해하고 두 대안을 나눠 봤습니다. 하지만 갈린 것은 대화뿐이고 작업 디렉터리는 그대로 하나였습니다. 두 실행의 코드 수정이 한 파일에 겹쳐 들어간 것을 git diff로 보고서야 알았습니다. 대안을 비교하려면 세션뿐 아니라 워크트리도 나눠야 한다는 것을 직접 배웠습니다.

    진단 순서도 바꿨습니다. 설정이 꼬이면 “아무것도 붙이지 않고 돌려 보자”며 --bare부터 떠올리기 쉽습니다. 하지만 이는 문제를 좁히기보다 변수를 하나 더 늘리는 선택이었습니다. “최소 실행으로 좁힌다”고 할 때 --bare와 --safe-mode는 같은 카드가 아닙니다. --bare는 keychain과 OAuth를 읽지 않습니다. 구독 로그인으로 쓰는 환경에서는 사용자 정의만 빠지는 것이 아니라 로그인하지 않은 상태가 됩니다. 설정 문제를 가를 때는 --safe-mode가 맞고, --bare는 API 키를 명시적으로 주는 CI 쪽 카드였습니다.

    CI 랩은 격리 실습 대신 이 정리를 발행하는 실제 저장소에 워크플로를 올리고 실제 PR을 열어 실행했습니다. 뜻밖의 발견도 있었습니다. Claude가 워크플로 자체의 diff를 리뷰하다가, 제가 쓴 run: 스크립트에 ${{ github.base_ref }}를 문자열로 그대로 넣은 것을 GitHub Actions 스크립트 인젝션 패턴으로 지적했습니다. CI 게이트를 만들려던 코드에 정작 그 게이트가 잡을 만한 결함이 있었던 셈입니다.

    /loop와 /goal도 tmux에서 실제 대화형 세션을 열어 직접 입력해 봤습니다. 이름만 보고 같은 기능의 다른 이름이라 생각했지만, 예상과는 거의 반대였습니다. 턴을 새로 시작하며 조건이 채워질 때까지 반복하는 쪽은 /goal이었고, /loop는 같은 프롬프트를 시간 간격으로 다시 실행하는 스케줄러였습니다. 열린 세션이 끝나면 새 대화에서는 끝나지만, 만료 전 task는 --resume·--continue에서 복원할 수 있습니다. /goal은 -p 한 번으로도 조건 판정까지 끝까지 실행됐는데, 이는 나중에 공식 문서 예시를 보고 재현해서 알았습니다.

    Remote Control도 처음에는 페어링 URL이 뜨지 않아 막혔습니다. 이 실습 환경의 setup-token/OAuth 환경변수 인증을 지우고 계정 로그인으로 바꾸자 바로 됐고, 웹에서 보낸 메시지가 로컬 컴퓨터에서 실제로 실행되는 것까지 확인했습니다. 공식 문서가 보장하는 범위는 eligible claude.ai 로그인이 필요하고 API 키 인증은 지원하지 않는다는 점입니다. 토큰의 구현 세부는 일반화하지 않습니다. 이번 주에는 "재현 불가능"으로 남긴 항목이 없었습니다.

    30초 요약¶

    CLI Reference의 핵심은 “Claude에게 무엇을 물을까”보다 “자동화에 무엇을 입력하고, 어떤 신호로 다음 행동을 고를까”에 있습니다.

    Part 1~3은 플래그와 세션을 정리합니다. Part 4~6은 그 위에서 스케줄과 CI, 반복 패턴을 다룹니다. Part 7~8은 환경 차이를 분리해 진단하고 실제 랩의 성공·미완 경계를 남깁니다.

    W6에서는 이 과정을 버리지 않습니다. 셸이 맡은 입력·검증·재시도·관측을 SDK 코드로 옮길 뿐입니다.

    시작하기 전에 확인할 것¶

    -p는 신뢰할 수 있는 현재 디렉터리에서 실행해야 합니다. 가장 자주 놓치는 전제입니다. 대화형으로 프로젝트를 처음 열 때 뜨는 작업공간 신뢰 대화상자가 이 모드에서는 생략됩니다. 사람이 “이 디렉터리를 믿습니까”라고 한 번 확인하던 단계가 없으므로, 스크립트가 어느 경로에서 실행되는지 직접 챙기지 않으면 의도하지 않은 곳에서 실행될 수 있습니다.

    그래서 비대화 실행을 붙이기 전에는 다음 세 가지를 명시하는 편이 안전합니다.

    • 실행 디렉터리 — 사람이 확인해 주는 단계가 없으므로 스크립트가 어디에서 도는지를 코드로 고정해 둡니다. CI 러너처럼 매번 새 작업 디렉터리를 만드는 환경에서는 특히 그렇습니다.
    • 도구 권한 — 대화형이라면 승인 프롬프트에서 한 번 멈췄을 동작도 비대화 실행에서는 물어볼 상대가 없습니다. 허용 범위를 미리 정해 두지 않으면 그 자리에서 어떻게 처리될지가 실행마다 달라집니다.
    • 비용 상한 — 한 번의 호출이 몇 턴까지 갈지는 내가 쓴 프롬프트가 아니라 상황이 정합니다. 상한이 없으면 잘못 걸린 실행 하나가 조용히 오래 돌 수 있습니다.

    마지막으로 인증 상태 명령이 성공했다고 API 호출까지 성공한다고 보지 않습니다. 확인하는 대상이 서로 다르기 때문입니다. 실제로 -p를 한 번 실행해 JSON 결과를 확인하는 것이 가장 확실한 사전 점검입니다.

    학습 목표 체크리스트¶

    • -p의 입력·출력·실패 계약을 설명합니다.
    • 세션을 이어갈 때 -c, -r, --fork-session을 구분합니다.
    • CI에서 권한·비용·결과 형식을 제한합니다.
    • 문제가 나면 safe mode로 사용자 정의를 분리합니다.

    -p 한 번 호출 SDK의 단일 요청 호출
