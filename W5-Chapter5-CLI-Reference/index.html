    5주차 — Chapter 5: CLI Reference¶

    명령 하나를 잘 외우는 것보다, 실패와 비용까지 자동화가 판정하게 만드는 방법에 초점을 맞춘 주차입니다. Claude Code를 대화창으로만 쓰지 않고, 셸 스크립트·세션·CI가 그대로 받아 쓸 수 있는 입력과 출력의 형태로 다뤄 봤습니다.

    원본: Claude Code Deep Dive Workshop / Chapter 5 — CLI Reference (9파트, 약 95 슬라이드) 기준 버전: Claude Code v2.1.251 / 2026-08-29 · 교재는 2026년 7월판

    회고¶

    이번 주에 제가 가장 크게 바꾼 건 claude -p를 보는 눈이었습니다. 처음에는 “터미널에서 답을 한 번 받는 방법”으로만 봤습니다. 그런데 이 명령을 스크립트에 물려 놓고 나온 문장만 받아서 쓰다 보면, 잘 끝난 실행과 도중에 어그러진 실행이 겉으로는 구분되지 않습니다. 둘 다 그럴듯한 한국어 문장을 돌려주기 때문입니다. 다음 단계가 읽어야 할 건 그 문장이 아니라 “이 실행이 실패로 끝났는가”, “토큰과 비용을 얼마나 썼는가”처럼 기계가 그대로 판정할 수 있는 값입니다.

    --output-format json을 붙이면 이게 눈에 보입니다. 사람이 읽을 문장은 result 필드 하나로 들어가고 그 옆에 is_error, usage, total_cost_usd가 함께 담긴 봉투가 나옵니다. 이 봉투를 열어 보기 시작한 뒤로 “Claude에게 무엇을 물을까”보다 “다음 단계가 무엇을 보고 판단하게 할까”를 먼저 정하게 됐습니다.

    실측에서 걸린 곳은 죄다 도움말과 실제 동작 사이의 좁은 틈이었습니다. stream-json은 -p와 함께 쓰면 --verbose를 더 요구했습니다. --json-schema는 스키마 파일 경로가 아니라 JSON 문자열을 받았고 --bg는 -p와 아예 배타적이었습니다. 플래그 목록을 아무리 정확히 외워도 조합을 한 번 돌려 보기 전에는 알 수 없는 것들이라, 이번 주 정리는 읽은 것보다 돌려 본 것 위주가 됐습니다.

    --fork-session으로 원 세션을 보존하는 실험대라고 이해하고 두 대안을 갈라 봤는데, 갈린 건 대화뿐이고 작업 디렉터리는 그대로 하나였습니다. 두 실행의 코드 수정이 한 파일에 겹쳐 들어간 걸 git diff로 보고서야 알았습니다. 대안 비교를 하려면 세션만 가르지 말고 워크트리도 함께 갈라야 한다는 걸 몸으로 배웠습니다.

    진단 순서도 하나 고쳐 잡았습니다. 설정이 꼬였을 때 “일단 아무것도 안 붙인 상태로 돌려 보자”며 --bare부터 떠올리기 쉬운데, 이건 문제를 좁히는 게 아니라 변수를 하나 더 늘리는 선택이었습니다. “최소 실행으로 좁힌다”고 할 때 --bare와 --safe-mode는 같은 카드가 아닙니다. --bare는 keychain과 OAuth를 아예 읽지 않습니다. 구독 로그인으로 쓰는 환경에서는 사용자 정의만 빠지는 게 아니라 로그인하지 않은 상태가 됩니다. 설정 문제를 가를 땐 --safe-mode가 맞고 --bare는 API 키를 명시적으로 쥐여 주는 CI 쪽 카드였습니다.

    CI 랩은 격리 실습 대신 이 정리를 발행하는 실제 저장소에 워크플로를 올리고 진짜 PR을 열어 돌렸는데, 뜻밖의 소득이 있었습니다. Claude가 그 워크플로 자체의 diff를 리뷰하다가 제가 짠 run: 스크립트에 ${{ github.base_ref }}를 그대로 문자열로 넣은 게 GitHub Actions 스크립트 인젝션 패턴이라고 스스로 지적했습니다. CI 게이트를 만들려고 짠 코드에 정작 그 게이트가 걸릴 만한 결함이 있었던 셈입니다.

    /loop와 /goal도 tmux로 실제 대화형 세션을 열어 직접 쳐 봤습니다. 이름만 보고 둘이 같은 기능의 다른 이름인 줄 알았는데, 짐작했던 것과는 반대에 가까웠습니다. 턴을 계속 새로 시작해 가며 조건이 채워질 때까지 스스로 반복하는 쪽은 /goal이었고, /loop는 세션이 열려 있는 동안 같은 프롬프트를 시간 간격으로 다시 실행하는 스케줄러였습니다. 그리고 /goal은 -p 한 번으로도 조건 판정까지 끝까지 돌아갔는데, 이건 나중에 공식 문서 예시를 보고 재현해서야 알았습니다.

    Remote Control도 처음엔 페어링 URL이 아예 뜨지 않아 막혔는데, 알고 보니 이 환경이 setup-token(모델 호출 전용 인증)으로 로그인돼 있어서 애초에 될 수 없는 구조였습니다. 계정 로그인으로 바꾸자 바로 됐고 웹에서 보낸 메시지가 로컬 컴퓨터에서 실제로 실행되는 것까지 확인했습니다. 이번 주는 결국 "재현 불가능"으로 남긴 항목이 없었습니다.

    30초 요약¶

    CLI Reference의 핵심은 “Claude에게 무엇을 물을까”보다 “자동화가 무엇을 입력으로 주고 어떤 신호로 다음 행동을 고를까”입니다.

    Part 1~3은 플래그와 세션을 정리합니다. Part 4~6은 그 위에서 스케줄과 CI, 반복 패턴을 다룹니다. Part 7~8은 환경 차이를 분리해 진단하고 실제 랩의 성공·미완 경계를 남깁니다.

    시작하기 전에 확인할 것¶

    -p는 신뢰할 수 있는 현재 디렉터리에서 실행돼야 합니다. 가장 자주 놓치는 전제입니다. 대화형으로 프로젝트를 처음 열 때 뜨는 작업공간 신뢰 대화상자가 이 모드에서는 생략되기 때문입니다. 사람이 “이 디렉터리를 믿습니까”를 한 번 걸러 주던 자리가 통째로 비는 셈이라, 스크립트가 어느 경로에서 도는지를 스스로 챙기지 않으면 의도하지 않은 곳에서 그대로 실행됩니다.

    그래서 비대화 실행을 붙이기 전에 다음 셋을 명시해 두는 편이 안전합니다.

    • 실행 디렉터리 — 사람이 확인해 주는 단계가 없으므로 스크립트가 어디에서 도는지를 코드로 고정해 둡니다. CI 러너처럼 매번 새 작업 디렉터리를 만드는 환경에서는 특히 그렇습니다.
    • 도구 권한 — 대화형이라면 승인 프롬프트에서 한 번 멈췄을 동작도 비대화 실행에서는 물어볼 상대가 없습니다. 허용 범위를 미리 정해 두지 않으면 그 자리에서 어떻게 처리될지가 실행마다 달라집니다.
    • 비용 상한 — 한 번의 호출이 몇 턴까지 갈지는 내가 쓴 프롬프트가 아니라 상황이 정합니다. 상한이 없으면 잘못 걸린 실행 하나가 조용히 오래 돌 수 있습니다.

    마지막으로, 인증 상태 명령이 성공했다고 해서 API 호출까지 된다고 추론하지 않습니다. 확인하는 대상이 서로 다르기 때문입니다. 실제로 -p를 한 번 돌려 JSON 결과를 눈으로 보는 것이 가장 확실한 사전 점검입니다.

    이 정리의 실습 부분은 2026-08-29에 직접 실행한 결과입니다. 실행 환경: macOS 26.6.2 / Claude Code 2.1.251 / jq 1.7.1-apple.

    Lab 상태 핵심 발견

    Lab 3 — CI ✅ 완료 실제 PR(#1)에서 워크플로가 트리거됨. Claude가 자기 워크플로의 스크립트 인젝션 결함을 스스로 지적.
